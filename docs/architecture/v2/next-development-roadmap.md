# 清理后的开发路线

> 更新：2026-10-16 · 代码基线：`main` 的 `015010703794ebd613c1dce5f899e9ed4879cfeb`。
>
> PR #257、#258 已合并，旧交付、隔离 UsageV2、旧包运行时及重复入口清理完成。本文规划后续实施，不表示 C3—C5 已实现或已发布。

## 方向与完成标准

后续按 C3 资金闭环 → C4 正式接口与凭据生命周期 → C5 安装发布推进。剩余旧财务代码随新业务接管删除，不再单独扩展清理矩阵；C2 的订阅、Provider、有限授权和原周期用量事实直接复用。

Core 继续是业务权威，Gateway 是可选 BFF，Provider 保管代理秘密，Node 负责执行和计量。以当前 native 新安装为开发基线，同批修改契约、Schema 和真实消费者，不增加兼容模式、影子写入或另一套账本。

“完成”要求实际入口、持久事务、失败恢复及相关 CI 一起交付。模型、文档、沙盒结果或一次成功回调不能代替完整业务。

## 第一优先级：C3 支付、资金与退款

### C3-A：冻结资金契约并实现账本基础

- 明确报价、手续费、钱包预留、收入确认和退款的业务含义。金额使用有界整数最小单位，对外使用规范十进制字符串；币种、精度和舍入规则随报价冻结，禁止浮点金额或跨币抵销。
- 定义当前 `PaymentAttempt`、收款事实、资金账户、Journal/Posting 和退款状态机；复用订单 ID、购买证据及安装权威，不复活历史影子记录或隔离工具。
- Billing 拥有资金账户、不可变平衡分录、幂等业务键及余额/保留额投影。已入账事实只能通过新的冲销或调整分录更正，不能覆盖成功交易。
- 统一回调交易号的渠道账户作用域与唯一约束，防止同笔收款同时用于充值和订阅。支付尝试与实际收款分别记录，超时、失败或取消不能抹掉渠道已发生事实。
- 先核对当前账户优先锁序，再为订单、资金账户、收款和退款确定完整锁序；共用 Schema、业务键、事务所有权和契约由同一负责人集成。
- 同步当前迁移、schema/readiness 和安装准入。此批结束仍保持 native 付费入口关闭。

**验收：** 账本平衡、余额充分、唯一业务键、重复与冲突请求、回滚及并发扣款有明确结果；余额完全可由持久分录解释，不从 `User.balance` 读写 native 资金。

### C3-B：接通实际购买与支付

- `NativeOrderLifecycle` 继续拥有 native 订单流转；Subscription 保留购买协调、冻结条款和履约。支付商适配器只负责协议、验签和已验证结果映射，不拥有订单或资金状态。
- 接通钱包预留/消费/释放、全钱包购买、渠道购买及组合支付；充值直接进入同一资金账本。免费订单复用 C2，不生成虚构渠道交易或零金额收款。
- 为渠道请求建立持久操作及幂等键，在 SQL 事务外调用渠道；网络超时保持未知状态，通过原操作查询/恢复，不自动创建第二次收款。
- 首批只接入能够验证金额、币种、收款方和唯一交易号，并明确查询/退款能力的渠道。未满足契约的适配器明确拒绝，不放宽验签或金额检查。
- 同一订单多个尝试成功时，只履约一次；额外收款及取消后的迟到收款进入可解释的待退款/待核对事实。
- 支付事实、资金分录、订单转换和 outbox 在同一事务提交；Worker/Scheduler 从 SQL 恢复，不能把队列投递成功当成最终履约。

**验收：** 实际 API 和已验签的渠道集成覆盖新购、续费、换套餐、充值、重复回调、双成功尝试、取消竞态及队列故障；任何路径不能重复扣款、记收入或开通。

### C3-C：退款、对账与开放付费

- 先冻结退款范围、手续费、钱包/渠道退款归属和退款后的权益政策；通过 Subscription 生命周期执行明确的权益调整，不直接修改 User 旧字段或猜测当前套餐。
- 实现完整退款及契约规定的部分退款，引用原收款和原账本；累计退款不能超过可退金额，重复请求、回调和失败重试保持同一退款身份。
- 将渠道退款请求、未知结果查询、成功确认及补偿持久化；退款请求已接收不等于渠道已退回。
- 提供最小对账查询：订单应收、渠道实收、钱包变动、已退/待退款、未决尝试、履约状态和 outbox 积压。差异可追溯，不靠人工修改余额消除。
- 逐个删除已被接管的旧余额、充值、取消返还和订单支付分支，更新真实 API、Worker、Scheduler、Gateway/SDK 及既有页面消费者。
- C3-A/B/C 的关键链路通过 CI，并具备持久恢复和明确退款规则后，才交付 native 付费准入；规划文档不改变当前免费限定。

**验收：** 一条购买 → 收款 → 开通 → 续费/换套餐 → 取消/退款 → 对账链路闭合；重复、并发和崩溃不会产生第二次资金或权益变化。

## 第二优先级：C4 正式接口与凭据生命周期

| 批次 | 实际交付 | 前置条件 |
| --- | --- | --- |
| C4-A | 以当前领域服务定义并注册正式 `/txapi/*` 服务接口；服务身份、User/Admin 调用者授权、资源归属、幂等、审计和请求追踪 | C3 业务契约稳定；不恢复已删除的 InternalReadOnly 路由、命令或隔离夹具 |
| C4-B | Gateway/SDK 对接正式接口；管理员入口只开放已交付的权限与操作，保持支付回调和 Node 身份独立 | Core 每次重验实际调用者及权限；通道身份不能替代管理员授权 |
| C4-C | Provider 注册与能力、生产证书/信任/密钥轮换和吊销、长期订阅链接的独立撤销及有限渲染 | 复用 C2 的真实发行、轮换、撤销与 PoP 渲染；代理秘密继续留在 Provider |

C4 可以提前做契约设计；涉及支付、退款的入口须消费 C3 已完成的领域能力。正式 API 与现有直连入口共用领域规则，不再复制状态机或新增兼容转发服务。

## 第三优先级：C5 安装与发布

- 与独立 TXBoard-Deploy 固定 Core、Gateway、Provider、Node 的版本及能力组合，交付可重复的 native 新安装。
- 收口 readiness、Worker/队列/调度版本、密钥前置条件、停写排空、正常更新及必要恢复；业务恢复继续依据 SQL 和原始持久证据。
- 选定已支持组合，集中跑一次支付开通、真实 Node 使用、用量结算、续费/撤销、退款及正常更新/恢复；其余协议/平台按独立需求扩展。
- 发布制品、Current 契约、配置和运维说明分别确认。合并开发 PR、自动 dev 镜像和正式发布是不同状态。

不另建安装器，不重建大型本地 Linux 测试环境；旧站自动迁移、HA/Cluster、复杂佣金/提现、营销、通用插件沙箱及新增前端不进入本轮主线。TX-F 继续暂缓且仅允许本地提交、不推送。

## 并行方式与验收成本

1. 先完成 C3-A 的契约、Schema、资金原语和锁序；共享文件不能由多条分支各自发明版本。
2. 基础冻结后，订单/渠道、钱包/充值、退款/对账可按文件所有权并行；公共资金写入仍由同一 Billing 服务拥有，协调者统一集成。
3. 每个业务批次集中运行对应 API、MySQL 资金竞态及必要端到端检查。仅在改变 Node/Provider 协议或实际失败时增加相关 Node/流量检查，不为资金开发重跑完整协议矩阵。
4. 本地只做语法、格式、差异和轻量静态检查。重型任务留在 GitHub Actions，不手工重复已通过的无关检查，不以跳过冒充通过。
5. 以相关功能闭环组织 PR；Schema、契约、业务消费者及必要恢复同批交付，记录仍关闭的能力和实际验收结果。
