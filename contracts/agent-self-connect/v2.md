# Agent Self-Connect Contract v2 — Pairing

Status: additive compatibility layer over Agent Self-Connect v1 and Agent Ops HTTP v1.

## Goal

Allow an administrator to hand an AI Agent one short onboarding prompt containing:

- the version-matched TXBoard self-connect guide URL;
- a short-lived one-time pairing code.

The Agent exchanges that temporary pairing capability for the already-created long-lived TXBoard Agent Token, stores the token locally, configures the existing Remote HTTP MCP endpoint, and performs read-only verification.

The intended flow is:

```text
Admin creates Agent Token
        ↓
TXBoard creates short-lived pairing code
        ↓
Admin copies one self-connect sentence
        ↓
Agent reads version-matched guide
        ↓
Agent redeems pairing code once
        ↓
Agent stores long-lived Agent Token locally
        ↓
Agent configures existing /mcp endpoint
        ↓
read-only verification
```

This is enrollment UX only. It does not create another MCP runtime or another Control Plane.

## Authoritative runtime

The existing Agent Token remains the durable authorization fact.

The pairing record is temporary delivery state only:

```text
MySQL personal_access_tokens
        ↑ durable Agent credential
        │
short-lived encrypted pairing payload
        │
Redis TTL
```

The pairing cache is never authoritative for abilities, target scope, expiry or revocation. Those facts continue to come from the Sanctum Agent Token and Agent Ops runtime.

## Token creation response

The existing Admin endpoint remains:

```http
POST /api/v2/{secure_path}/agent/tokens/create
```

Its response is extended additively:

```json
{
  "data": {
    "id": 42,
    "client_name": "hermes-prod",
    "abilities": ["agent:system:read"],
    "target_scope": {
      "mode": "all",
      "node_ids": [],
      "machine_ids": []
    },
    "expires_at": "2026-10-23T00:00:00+00:00",
    "plain_text_token": "42|...",
    "pairing": {
      "code": "txbp_...",
      "expires_at": "2026-09-23T00:10:00+00:00",
      "expires_in_seconds": 600
    }
  }
}
```

Compatibility requirements:

- `plain_text_token` remains present for existing Admin clients and manual fallback;
- `pairing` is additive;
- if transient pairing storage is unavailable, token creation still succeeds and `pairing` may be `null`;
- pairing creation must never change token abilities, target scope or expiry.

Sensitive token-creation responses must use `Cache-Control: no-store`.

## Pairing code

Format:

```text
txbp_<URL-safe random value>
```

Security requirements:

- generated from a cryptographically secure random source;
- at least 128 bits of entropy;
- default TTL: 600 seconds;
- configurable only within a bounded 60–900 second range;
- one-time redemption;
- treated as a temporary bearer capability;
- never persisted in MySQL;
- never written to logs;
- raw pairing code must not appear in the Redis/cache key.

The production pairing store defaults to Redis.

The cache key is derived from a SHA-256 digest of the code.

## Pairing payload

The transient cache payload may contain only data required to deliver the already-issued Agent Token:

- token id;
- administrator/token owner id;
- encrypted plain-text Agent Token;
- issued-at timestamp;
- pairing expiry timestamp.

The payload must be encrypted with the TXBoard application key before being written to Redis/cache.

Pairing does not add a database migration.

## Redemption endpoint

Public pre-auth enrollment endpoint:

```http
POST /api/v2/agent/pairings/redeem
Content-Type: application/json

{
  "pairing_code": "txbp_..."
}
```

The endpoint does not require an existing Agent Bearer token because its purpose is to obtain one.

It MUST:

- be rate-limited independently from authenticated Agent Ops;
- validate the pairing-code format;
- derive the cache key from the code hash;
- serialize concurrent redemption with a distributed cache lock;
- remove the pairing record as part of redemption;
- decrypt the payload only inside TXBoard Core;
- confirm the referenced long-lived token still exists;
- confirm it is an `agent:` token owned by the expected administrator;
- confirm the long-lived token itself is not expired;
- return the long-lived token only once;
- use `Cache-Control: no-store`.

Successful response:

```json
{
  "data": {
    "plain_text_token": "42|...",
    "token_id": 42,
    "client_name": "hermes-prod",
    "abilities": ["agent:system:read"],
    "target_scope": {
      "mode": "all",
      "node_ids": [],
      "machine_ids": []
    },
    "expires_at": "2026-10-23T00:00:00+00:00"
  }
}
```

A redeemed, expired, missing, corrupted or revoked pairing returns the same generic response class and must not reveal which condition occurred:

```http
410 Gone
```

with a non-secret message such as:

```text
Pairing code is invalid, expired, or already redeemed
```

Transient pairing-store failure returns:

```http
503 Service Unavailable
```

without leaking Redis topology or credentials.

## One-time semantics

The same pairing code must not successfully redeem twice.

Concurrent callers for the same code are serialized by a cache-backed lock. The stored pairing payload is removed before the long-lived credential is returned.

If the long-lived token was revoked before redemption, redemption fails and the pairing is consumed.

## Redis / Octane behavior

Production defaults:

```text
AGENT_OPS_PAIRING_CACHE_STORE=redis
AGENT_OPS_PAIRING_TTL_SECONDS=600
```

The service uses Laravel's cache repository and cache-backed lock. It does not keep pairing state in static properties, singleton mutable arrays or Octane worker memory.

Consequences:

- all Octane workers observe the same Redis-backed pairing state;
- expiry is Redis/cache TTL driven;
- worker restart does not extend pairing lifetime;
- application/image upgrade does not create a second source of truth;
- Redis loss invalidates pending pairings only; durable Agent Tokens remain unaffected.

Tests may replace the cache store with Laravel's `array` store.

## Agent self-connect prompt

When a pairing is available, the primary Admin prompt should be short enough to paste as one instruction, for example:

```text
请按 https://panel.example.com/.well-known/txboard-agent-connect.md 自助接入 TXBoard；一次性配对码：txbp_xxx
```

The long-lived Agent Token MUST NOT be included in that prompt.

The pairing code may be included because it is deliberately short-lived and one-time. The UI must clearly display its expiry.

If pairing issuance is unavailable, Admin falls back to Self-Connect v1 behavior where the guide instructs the operator to place the long-lived token into the Agent's local secret mechanism.

## Agent guide v2 behavior

The version-matched guide keeps the same public path:

```text
/.well-known/txboard-agent-connect.md
```

When the prompt contains a pairing code, the Agent should:

1. detect its current client/runtime;
2. redeem the pairing code against the same TXBoard origin;
3. capture the long-lived token without echoing it to chat/logs;
4. write it to the client's supported local secret/config mechanism;
5. configure `<origin>/mcp`;
6. verify tool discovery and one read-only tool;
7. report non-secret completion details.

The Agent must not use pairing to widen abilities, target scope or approval rights.

## Security boundary

Pairing preserves:

```text
Agent
  -> pairing redemption (credential delivery only)
  -> HTTPS /mcp
  -> MCP Gateway
  -> Agent Ops API
  -> functional ability
  -> target scope
  -> approval / audit
  -> TXBoard domain service
  -> TX-Node typed operation
```

Pairing MUST NOT introduce:

- MCP or enrollment -> direct MySQL;
- MCP or enrollment -> direct Redis;
- MCP or enrollment -> direct TX-Node;
- SSH as a substitute Control Plane;
- Docker as a substitute Control Plane;
- generic remote shell;
- arbitrary remote filesystem access;
- automatic approval;
- automatic permission widening.

Redis is an internal TXBoard implementation detail for transient pairing state, not an Agent-accessible interface.

## Non-goals

Self-Connect v2 does not add:

- OAuth/OIDC device flow;
- refresh tokens;
- per-Agent public-key enrollment;
- persistent pairing database tables;
- reusable invitation codes;
- automatic MCP enablement;
- automatic Agent action approval;
- changes to TX-Node protocol.

Those require separate contracts.
