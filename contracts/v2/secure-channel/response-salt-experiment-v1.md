# SC-v2 response salt experiment v1

Status: Verified B6.4 offline local engineering candidate. See [fixed-source evidence](../../../gateway/docs/sc-v2-response-salt-verification.json). No Gateway HTTP route, Core callback or production key is added. Existing B6.1–B6.3 and Gateway v1 bytes remain unchanged.

The candidate uses the response derivation pattern in [RFC9458 section 4.4](https://www.rfc-editor.org/rfc/rfc9458.html#section-4.4), using domain-separated application labels rather than claiming OHTTP wire compatibility. HPKE request info is `txboard.sc-v2-response-salt/1/request`; the exporter context is `txboard.sc-v2-response-salt/1/response`. The HPKE suite stays P-256/HKDF-SHA256/AES-256-GCM. Export 32 bytes, generate a fresh 32-byte response nonce using WebCrypto CSPRNG, and derive key32/nonce12 using HKDF-SHA256 with salt `enc65 || response_nonce32` and ASCII info `key` / `nonce`. AES-GCM AAD is a uint16-length tuple of label `txboard.sc-v2-response-salt/1/aad`, the unchanged B6.1 response AAD, and the 32 nonce bytes.

Closed response envelope is `{request_digest,kind,status,response_nonce,ct}`. Canonical unpadded base64url encodes the nonce. Metadata/digest/status/kind/salt are authenticated; swapping responses or changing salt fails. The request has the same structural fields as the old experiment but a distinct HPKE info label, so old/new contexts cannot silently interoperate. No caller-supplied response salt or RNG override is exposed; each recipient closure remains single-use, including errors and failures.

Independent recipient openings of an identical request generate independent random response salt and derive separate response material. This addresses the old deterministic key/nonce reuse caused by duplicate owner reconstruction, under CSPRNG and HKDF assumptions. It does not authenticate a sender, stop business replay, guarantee entropy after a broken/cloned RNG or establish a shared owner. Redis loss/HA, admission, durable business idempotency, key discovery/rotation/revocation, encrypted transport error policy and independent protocol audit still require separate evidence before network/business adoption. No test result overrides those gates.

Acceptance requires unchanged old vectors, fixed new framing and derivation references, independent Python HKDF/framing checks, multiple duplicate recipients with distinct actual encryption material, negative/tamper/expiry/single-use checks, and Node/Chromium role interoperability.
