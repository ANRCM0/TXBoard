# 开发与批次验收流程

2026-10-15 用户确认：可以完成一个或多个相关阶段后，统一测试、集中修复。该约定覆盖此前每条小切片都独立跑整套回归、提交和推送的开发节奏；生产发布与数据迁移门禁继续适用。

## 执行顺序

1. 明确本批可用功能、涉及组件和接口边界。一个完整功能或几个相关阶段可以合为一批；不要将无关功能堆到同一次验收。
2. 连续实现功能。复用现有业务与内核实现，契约明确、文件不重叠的工作可分派代理；实现期间以必要的语法、编译和明显错误检查为主。
3. 本批功能完成后，一次性确定受影响范围并集中验收：新增功能、主要业务链路、直接受影响的已有行为。
4. 汇总问题并集中修复，只复测修复相关部分。仅在新改动、实际失败或未解决问题确有需要时扩大范围；达到本批标准就收尾。
5. 审查最终差异，将本批内容提交并推送主题分支，通过 PR 请求审阅，核对对应提交的远端 CI；依赖就绪且审阅通过后由维护者合并。跨仓批次分别提交关联 PR，未验收的独立改动不混入。

2026-10-15 用户进一步确认多团队通过 PR 参与；任务可提前开 Draft 协调，但不增加逐小修改全量验收。角色、跨仓依赖和合并条件见[多团队开发方案](multi-team-development.md)。

## 检查范围

| 时机 | 默认范围 |
| --- | --- |
| 文档、注释修改 | 差异、引用与表述一致性；不启动业务环境或运行应用全量测试 |
| 日常实现 | 必要的语法、编译、类型与明显错误检查；发现具体问题时做最小复现 |
| 一个功能或多个相关阶段完成 | 集中验证新增行为、主要链路和受影响回归，复用适用的已有证据 |
| 准备发布、切换生产权威或重大迁移 | 按实际改动与发布契约集中执行协议/内核矩阵、复杂故障和恢复验收 |

权限、扣费、支付和数据库写入等关键改动，在开发过程中保留与改动直接相关的必要检查；这些检查不自动扩展为整仓或所有协议验收。实际业务缺陷、可能丢数据或权限绕过应及时处理，不能为凑批次继续堆叠依赖它的工作。

完整协议矩阵、双内核组合、复杂故障注入和备份恢复边缘场景，默认集中到发布验收或相关实现发生变化时。协议已有支持时，增加验收覆盖应明确称为测试或集成工作，不记为新协议开发。

已有 CI 检查继续按仓库配置执行；通过批次末尾提交推送减少重复触发，不以删测试、跳过 required checks 或关闭发布门禁代替调整节奏。纯文档不改变运行时测试结论，也不为了记录一个 CI 结果反复修改被测试组件、触发相同门禁。

## 代理、证据与汇报

- 代理按实现边界分工，不要求每个代理各自启动完整环境或跑同一套全量测试；协调者在批次末尾统一集成和验收。
- 在确需真实数据库、进程或恢复验收时，固定本批源码并记录关键结果；日常小修改不逐项新建整套快照。使用隔离合成数据，保留失败现场，不并发清理共享数据库。
- 汇报以已完成的可用功能、实际问题和剩余工作为主。区分已实现、本地验证、远端 CI、发布验收和已发布；不能把延后测试的功能表述为已经生产验收。
- 合仓不改变运行权限与发布边界；默认分支合并和镜像发布仍受既有门禁约束。TX-F 继续暂缓，只允许本地提交、不推送。
