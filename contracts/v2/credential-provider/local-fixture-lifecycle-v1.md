# Local Credential Provider Fixture Lifecycle v1

> B4.2 local/testing evidence only. Default off. This extends the [fixed synthetic runtime](local-fixture-runtime-v1.md); it does not revoke live Subject authorization, uninstall a v1 plugin or prove Node convergence.

Core records a permanent subject revocation fact and its original operation in one SQL transaction before private IPC. The registered provider row is the common fence for issuance, dispatch, revocation and disable. Fact versions are allocated monotonically by Core under the provider registration lock; the revocation scope is the corresponding provider/epoch/Subject (`provider-subject/v1`). A private tombstone rejects a lower version for that Subject, without rejecting a delayed legitimate fact for another Subject solely because its allocated sequence is smaller. Callers provide only the expected current Subject auth version and an allow-listed reason. Subject fields, historical usage and money evidence remain unchanged. New issuance and its later dispatch both use current reads to reject a recorded shadow revocation. Historical successful issue receipts remain historical evidence and do not assert current credential validity.

`revoke(FixtureScope, businessKey, input, deadlineAt)` accepts only `expected_subject_version` and `reason_code=operator_revoke|provider_disable`. One permanent revocation per provider/Subject is supported. The fact includes its version, effective timestamp, canonical input/hash and operation reference. Same-key replay must match the original logical input; a different key cannot replace the fact. Query/revoke retain current provider epoch, script identity, operation/profile grants and original resource scope checks even while disabled. A timeout, lost response or uncertain Core finalization leaves the original operation unknown; recovery only queries that operation. Missing private history is not a successful cleanup and never causes reissuance or a second revoke dispatch.

The private runtime atomically removes the synthetic secret, appends the revoke operation receipt and retains the issue receipt plus a permanent subject tombstone. Neither the issue nor revoke operation history is deleted. Tombstones prevent subsequent issuance in the private fixture. Core-known successful issuance binds its original nonsecret operation/credential references into the revoke snapshot; missing or mismatched private history remains unknown rather than reporting an empty successful cleanup. A receipt confirms only the trusted fixture's private cleanup. It is not a Node ACK, authentication result, backup destruction proof or power-loss durability proof.

`disable(providerId, businessKey)` durably closes issuance first, records `disabling` and freezes the greatest recorded issue ID. `cleanup(providerId, businessKey, limit, deadlineAt)` processes an ordered prefix at a hard limit of 1..32 records; each IPC still has the existing finite byte/time bounds. Unknown issue operations are queried with their original ID and block cursor advancement until explained. Known issued subjects are permanently revoked; an existing revoke is queried instead of replaced. Each cursor advancement requires a validated successful private revoke receipt. Incomplete/unknown/rejected operations, source growth or missing revocation evidence block completion. A disabled provider permits scoped query/revoke recovery but cannot issue. Lifecycle replay keeps the original key/context, cursor and facts; a conflicting key is refused.

The state is `enabled → disabling → disabled`. `fixture_cleanup_complete` is true only after the frozen issue prefix and all registered fixture operations pass the completion checks. Completion and later status calls validate operation/fact identities, canonical hashes and successful cleanup receipts; a stored disabled label alone cannot hide damaged evidence. Finite fixture history reads have a 512-operation ceiling with a 513-row sentinel and fail closed above it. Private state has hard limits of 128 issued subjects, 128 tombstones and 256 operations. `node_convergence=not_implemented` is always explicit, and no state is called uninstalled or purged. There is no enable/reset-tombstone operation. Cleanup retains private nonsecret operation/tombstone history and Core audit evidence. An unknown absent issue remains blocked for explicit investigation; this slice offers no override that fabricates completion.

Migration `000009` adds dedicated `tx_credential_provider_shadow_lifecycle` and `tx_credential_provider_shadow_revocation` records with restrictive new-domain references and refuses nonempty rollback. Existing registration/script digests are never silently upgraded. A stored registration for the previous runtime digest fails `RUNTIME_UNAVAILABLE`; the local verification uses clean isolated registrations. A production runtime upgrade protocol remains a separate gate.

The runtime remains a trusted fixed independent PHP process under the parent's OS identity. File modes and PHP restrictions do not form an OS sandbox. Production authentication, separate identities, secret transport, Node leases/receipts, offline convergence and PluginManager integration remain unimplemented. No caller can select a command, URL or private path. Both local fixture and isolated-copy flags, local/testing environment, current grants and resource scope remain required.

Verification on 2026-10-12, PHP 8.4 / Linux: `FixtureLifecycleTest` passed 23 tests / 189 assertions on SQLite with three MariaDB-only tests skipped, and all 26 tests / 219 assertions on MariaDB 11.4.12. The combined Provider group passed 43 tests / 309 assertions on SQLite with five skips, and 48 tests / 366 assertions on MariaDB with no skips. Eight independent Core sessions shared one durable revoke ID, one Core fact and one private cleanup. A replay that queried before the creator dispatched could temporarily remain unknown; final query converged without another revoke. Two separate session-barrier tests held the uncommitted disable or revocation registration fence and verified issuance could not complete before commit, then returned `PROVIDER_DISABLED` or `REVOKED`. Other cases cover response loss, post-commit timeout, Core finalization and fact-recording rollback, missing private operation/acknowledged issuance history, altered grants/hash/version, batch limits, unknown cursor blocking, tombstone persistence and absence of secrets from SQL/DTO/logs.

The full API gate used committed Core `8543668ccf7c53174f4ce1e9f4d0f25856fe2855` plus only the nine B4.2 files in a fresh ext4 archive, with matching locked vendor and isolated Redis databases 16/17. It passed 744 tests / 5484 assertions, with 19 engine-specific tests skipped and no failures or warnings. The public `.env.example` supplied the fixture environment; no actual operator configuration was copied. These checks validate the described local fixture scope, without proving production cleanup, backups or Node convergence.
