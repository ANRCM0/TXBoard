# Isolated local registration over Internal mTLS v1

Status: Current / verified isolated B5.11. Fixed-source gates and real SDK/HPKE/Redis/TLS1.3/MariaDB integration passed; see [verification evidence](../../../docs/architecture/v2/internal-isolated-registration-verification.json). This fixed operation uses synthetic accounts on the existing local/testing boundary; production registration remains the native TXAPI flow.

`auth.register`, contract version `"1"`, requires the `user-gateway` service identity, no Authorization header (including an empty header), the global Internal gate, `core_shadow.isolated_copy=true` and the independent exact-true default-off `CORE_INTERNAL_REGISTER_ENABLED`. Audit actor is `0`. The existing proof binds the exact method, path, body and absent actor; nonce admission is not registration idempotency.

The closed signed input contains required strings `email` (254 characters maximum) and `password` (1024 maximum), optional `invite_code` (128), `email_code` (128), and existing CAPTCHA strings (4096 each). Unknown, duplicate, missing and wrong-type fields are rejected. The original trim/empty normalization, shared `ThrottleRequests(10,1,'')` and `AuthRegister` validation run before delegation. The normalized email must end with the exact case-sensitive `@example.test`. No actor, role, plan, balance, IP, callback or URL can be supplied. Core sees the local boundary IP, not an authenticated end-user IP.

The dispatcher calls the existing `AuthController::register`, `RegisterService`, `UserService` and `AuthService`. A request-local RegisterService subclass supplies a CAPTCHA adapter without rebinding global services. The adapter requires a real settings-cache array and agreement between SQL, cache and the loaded registration policy. Known enabled CAPTCHA is rejected without contacting a provider; unknown policy or dependency/drift returns safe 503. This is a point-in-time policy check, not a lock/fence against later trusted hooks or concurrent configuration changes.

Native invite consumption, whitelist/alias restrictions, stop-register, verification code, trial plan, IP quota, hooks, password hashing and Sanctum issuance remain authoritative. Their original order and transaction boundaries are preserved. Invite consumption can precede a failed user save. An after-register hook, cache error, session error, audit failure, deadline or lost reply can leave an account or token committed while the caller receives an error. This operation adds no all-or-nothing transaction, automatic retry, recovery, compensation or business idempotency.

HTTP201 success is exactly `data={auth_data: Bearer...}` and `meta={current_only:true,slice:"internal-isolated-registration/1"}`, with private/no-store headers. Password, verification/invite code, email, private subscription token, secure path and hook exception details are excluded from the response and technical audit. Credential-bearing exceptions are rendered inside the dispatcher before global reporting; trusted plugins' own logs remain their responsibility. Native conflict 409, registration rejection 422 and quota/throttle 429 remain distinguishable from service authentication/rate failures.

Gateway uses its separate local/testing `GATEWAY_INTERNAL_REGISTER_ENABLED` flag, configured Internal mTLS, HPKE with nonce replay protection and Redis limiter. Only the existing encrypted `/gateway/v1/secure/auth/register` route is enabled by this flag; full account workflows stay disabled. The SDK's existing registration DTO and success shape remain compatible. A strict HTTP201 envelope is required. Once selected, no native fallback or retry occurs, including unknown outcomes; service identity/rate failures are dependency failures rather than end-user credential or quota failures.

Acceptance requires native account/token and trial/invite/code tests, closed input/default gates, current-policy drift, shared throttle and service proof failures, request/actor restoration, safe unknown outcomes, Gateway policy/HPKE/replay/DTO tests, and real loopback TLS1.3 plus Core/Gateway/SDK/Redis synthetic integration. External CAPTCHA, production mail and production registration activation are not part of this gate.
