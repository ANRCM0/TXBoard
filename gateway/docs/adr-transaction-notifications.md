# ADR：交易邮件模板与可靠投递（GW-312）

- 状态：**已提出，待评审**
- 日期：2026-10-11
- 责任：**TX**（TXBoard Laravel 主仓库实现：通知服务扩展、交易事件、模板渲染、队列投递）+ GW（Gateway 仅透传事件标识、不渲染模板、不持凭据）+ SDK（交易通知的站内只读展示，不新增邮件发送能力）
- 关联任务：[task-backlog.md](./task-backlog.md) GW-312（本文档）；上游依赖 GW-301（只读通知 `GET /notices` 已实现）、GW-302/303（订单幂等，`idempotency_keys` 唯一约束）、GW-305（交易状态机：`0 pending → 1 paid / 2 cancelled`，终态锁定）、GW-306（支付回调沙箱，重复回调吸收）、GW-307（注册/邮箱验证码邮件，已实现默认关闭）；同级 GW-310（快速购买）、GW-311（公开支付目录）可独立交付
- 前置依赖：M2 安全基础与 M3 交易闭环（GW-302～306/309）先行验收；**GW-312 只消费已验收的交易事件，不参与交易决策**
- 依据：[airbuddy-design-reference.md](./airbuddy-design-reference.md) §6 借鉴点 E（"复用 TXBoard 通知体系"映射新增 GW-312）与 §9 安全否决清单（不复制 SMTP 明文密码邮件）

## 1. 背景与问题

- 需求（借鉴点 E 原文）：AirBuddy 独立发送注册通知（含可定制模板）。TXBoard-Gateway **不另建独立 SMTP 服务**，避免双份邮箱密码与配置漂移。
- 目标：在 TXBoard 既有通知服务上，为**四类交易事件**提供邮件模板与可靠投递：
  1. 订单创建成功通知（`order.created`）
  2. 支付成功通知（`order.paid`）
  3. 订单取消通知（`order.cancelled`）
  4. 退款通知（`order.refunded`）
- 现状与边界：
  - Gateway 已有只读通知适配（`GET /gateway/v1/notices`，SDK `notices.list`，`Notice` DTO），站内通知已存在；**交易邮件是站内通知的邮件镜像通道**，两者共用同一事件源与同一去重键。
  - 交易写路径（GW-304/305/306）全部经 Laravel 权威执行并落 `idempotency_keys`；Gateway **零业务状态、零邮件凭据、零模板**。
  - GW-310 快速购买成功后同样只产生"用户 + 订单"（`order.create` 幂等行），其邮件语义与普通订单完全一致，无需新模板类型。
- 核心风险（任务验收原话，[task-backlog.md](./task-backlog.md) GW-312）：
  1. **凭据扩散**：出现独立 SMTP 配置/管理员邮件凭据 → 明文密码邮件风险（借鉴点 C 不变量 1 已否决管理员代建用户邮件）；
  2. **模板注入（XSS）**：远程模板 URL 或未转义占位符渲染出攻击载荷；
  3. **重复投递**：同一支付回调重复发送邮件（事件去重失败）；
  4. **投递不可靠**：SMTP 瞬时故障丢信、无重试、无死信监控；
  5. **副作用耦合**：SMTP 故障回滚/阻断已完成的合法交易。

## 2. 决策（Decision）

采用 **事件驱动 + 复用 TXBoard 通知服务 + 队列可靠投递** 方案，六条决策：

### D1：单点邮件出口，零 Gateway 凭据

- 全部交易邮件由 **TXBoard（Laravel）通知服务**统一发送；Gateway **不持有 SMTP 账号、不渲染模板、不生成正文**（借鉴点 E 原话："网关只传必要事件标识，不承担敏感业务邮件正文生成"）。
- Gateway 侧本次变更为**零代码**：不新增路由、不新增上游 operation、不修改策略表。SDK 侧也不新增邮件能力（邮件由后端独立发送，不经过客户端）。
- 若未来需要"通过 Gateway 触发邮件"，也只允许透传**事件类型标识**（如 `order.paid`），正文/收件人/模板全部由 Laravel 决定。

### D2：事件源 = 交易状态机终态迁移（含幂等行）

- 邮件事件**只在交易终态迁移点产生**，且与幂等/状态机绑定（借鉴点 E："与真实订单状态机绑定"）：

| 事件 | 触发点 | 前置状态守卫 | 幂等关联 |
| --- | --- | --- | --- |
| `order.created` | `order.create` 幂等行 `succeeded` 提交后 | 订单落库 `status=0 pending` | 同 `idempotency_keys` 行 |
| `order.paid` | 支付回调验签 + 状态条件 UPDATE `status=0→1` 成功（GW-306） | 仅回调首次推进 | 回调幂等行 |
| `order.cancelled` | `order.cancel` 幂等行 `succeeded`（GW-305） | 仅 `status=0` 可取消 | cancel 幂等行 |
| `order.refunded` | 退款状态迁移（TX 侧既有或新增退款终态） | 退款幂等行 | 退款幂等行 |

- **不产生事件的情形**：支付失败（可重试，非终态）、`ORDER_REJECTED`、`LOGIN_REQUIRED`、幂等重放（返回首次快照不产生新事件）。

### D3：模板安全——转义 + 字段白名单 + 禁止明文凭据

- 模板渲染**强制 HTML 转义**：所有用户可控/订单派生字段（`trade_no`、`plan_name`、金额、时间、用户名等）经转义函数渲染（`htmlspecialchars`/等价），模板本体只允许受控占位符语法（如 `{{order.trade_no}}`），**禁止在模板中直接拼接**。
- **字段白名单**：模板只能引用白名单 DTO 字段（§4.2），白名单外字段一律不可达（编译期校验模板变量引用）。
- **禁止明文密码/长效凭据**：邮件正文绝不包含登录密码、可直接使用的长效 token、完整用户密钥（借鉴点 E 原话 + 借鉴点 C 否决理由）。首次设置密码必须使用**短期一次性安全链接**（短 TTL、单次消费、绑定用户与操作）。
- **不泄露敏感信息**：邮件不含完整账号余额快照以外的他人数据；`trade_no` 为订单标识可包含（非凭据）；不含上游 API 原文、内部错误堆栈。
- **远程模板**：模板只能来自 TXBoard 后台配置（数据库存储、可审查），**禁止把任意远程 HTML URL 当可信动态模板执行**（借鉴点 E 原话）；模板变更留审计。

### D4：可靠投递——队列 + 指数退避重试 + 死信

- 发送走 **异步队列**（Laravel Queue），与交易事务解耦：交易提交不等待邮件投递。
- 重试策略：指数退避（如 1s → 5s → 30s → 5min → 30min），上限 5 次（可配）；达到上限进 **死信队列（DLQ）** 并告警。
- **去重**：队列任务与投递均以**事件去重键**为准（§5），天然吸收"同一回调重复入队"。
- 投递监控：`emails_sent_total{template,status}`、`emails_dlq_total`、投递延迟直方图；告警规则与现有 13 条 Prometheus 规则同库管理（DEP 侧）。

### D5：投递失败不回滚交易（副作用隔离）

- 借鉴点 E 验收信号原话："**SMTP 故障不回滚已完成的合法交易**"。邮件投递失败（含 DLQ）**绝不**影响订单状态、幂等行、支付结果。
- 事务边界：邮件入队在**事务提交之后**（避免"订单回滚但邮件已发"）；队列任务失败只影响邮件，可事后重放（DLQ 手动/定时重投）。

### D6：不替代站内通知

- 交易事件同时写站内通知（`notices` 表，现有 `GET /notices` 读取）与邮件镜像；邮件投递失败时站内通知仍在（用户可自查）。
- 邮件为**附加通道**，站内通知为准；允许站点策略单独关闭邮件（`mail_enabled` 开关）而不影响站内通知。

## 3. 四类交易邮件的模板设计

### 3.1 订单创建成功通知（`order.created`）

- 时机：`order.create` 幂等行 `succeeded` 提交后入队。
- 用途：告知用户订单已创建、待支付（含 `trade_no` 与支付入口链接）。
- 内容要点：套餐名、周期、金额、`trade_no`、支付链接（站内订单页，非支付商密钥）、创建时间。
- 不含：密码、token、支付商配置、内部错误。

### 3.2 支付成功通知（`order.paid`）

- 时机：GW-306 支付回调验签 + 状态 `0→1` 迁移成功后入队（回调幂等行去重，重复回调不重复发）。
- 内容要点：套餐名、实付金额、`trade_no`、开通状态（"已支付，开通中"）、订单页链接。
- 不含：回调原文、验签细节、上游 API 标识。

### 3.3 订单取消通知（`order.cancelled`）

- 时机：`order.cancel` 幂等行 `succeeded`（GW-305，仅 `status=0` 可取消）后入队。
- 内容要点：`trade_no`、取消时间、套餐名、取消原因（若为用户主动取消则"您已取消该订单"）。
- 不含：优惠券核算细节、内部拒绝码原文。

### 3.4 退款通知（`order.refunded`）

- 时机：退款终态迁移（TX 侧退款流程幂等行 `succeeded`）后入队。
- 内容要点：`trade_no`、退款金额、退款去向（原支付渠道）、到账预计时间（文案模板，不含渠道密钥）。
- 不含：支付商账户信息、内部对账数据、明文凭据。

> 模板正文与措辞由 TXBoard 后台配置并可审查；上述"内容要点"是**安全白名单边界**，不是文案终稿。

## 4. 安全设计细节

### 4.1 模板渲染管线（防 XSS）

```text
模板（DB 存储，后台可审查，仅 {{variable}} 占位符）
  → 变量白名单校验（§4.2，未知变量渲染期拒绝）
  → 变量值注入前统一 html 转义（含引号、`<>&"'`）
  → 白名单标签允许列表（a/p/br/strong 等）或纯文本优先
  → 输出（HTML 邮件 + 纯文本备件）
```

- 负例：用户昵称/套餐名/备注含 `<script>`、`{{}}` 嵌套、超长字段 → 转义后安全或按长度截断；模板引用白名单外字段 → 拒绝渲染并告警（不静默输出空值）。
- 禁止：字符串拼接模板、`eval`/远程模板 URL 执行、未转义直接输出。

### 4.2 事件 DTO 白名单（模板可引用字段全集）

```ts
// 交易邮件事件 DTO（Laravel 侧，模板变量以此为准；Gateway/SDK 不接触）
type TransactionEmailEvent = {
  event: 'order.created' | 'order.paid' | 'order.cancelled' | 'order.refunded'
  event_id: string          // 去重键（§5）
  user_id: number           // 仅服务端路由收件人，不进正文
  to_email: string          // 仅服务端路由，不进正文变量白名单
  trade_no: string
  plan_name: string
  period: string
  amount_cents: number      // 模板内格式化为货币
  created_at: string        // ISO8601
  site_name: string
  order_url: string         // 站内订单页相对路径
}
```

- 白名单外字段（余额快照、内部错误、上游原文、任何凭据）**不可被模板引用**；收件人邮箱只用于 SMTP 路由，不作为正文变量。
- 金额一律以 `amount_cents` 整数传入，模板侧格式化，避免浮点精度与注入。

### 4.3 明文密码禁令（验收硬条件）

- 邮件正文**永不包含**：登录密码、密码重置原文、长效 access token、refresh token、完整用户密钥/私钥、SMTP 凭据。
- 需要用户设置/重置密码时：发送**短期一次性安全链接**（TTL ≤ 15min、单次消费、绑定 user_id + 用途），链接失效后要求重新发起；链接本身不是凭据（等价 GW-302/307 一次性挑战模式）。
- 负例测试：模板尝试引用密码/token 字段 → 编译期白名单拒绝；渲染产物 grep 无任何已知凭据字段名。

## 5. 可靠投递设计

### 5.1 去重键（事件去重，防重复邮件）

- 去重键：`email_dedupe_key := SHA-256(event_id)`，其中
  - `order.created` / `order.cancelled`：`event_id = trade_no ‖ ":created" / ":cancelled"`（每订单每事件唯一，幂等重放同键）；
  - `order.paid`：`event_id = trade_no ‖ ":paid" ‖ callback_idempotency_key`（回调幂等行决定，重复回调同键）；
  - `order.refunded`：`event_id = trade_no ‖ ":refunded" ‖ refund_idempotency_key`。
- 落库：`notification_emails`（或既有通知表扩展）加 `dedupe_key` **唯一约束**；入队前先插入占位行（与 GW-302 幂等表同构：唯一约束即去重权威），冲突即视为重复投递直接返回（不发信）。
- 不依赖 Redis 去重（借鉴点 E 验收：持久化权威）；Redis 可作为"已在队列"的次级提示，但唯一约束为准。

### 5.2 队列与重试

```text
交易终态迁移（事务内）→ 提交后入队 job（含 event DTO，无凭据）
  → worker 取 job → 查 dedupe_key（唯一约束先占位）→ 渲染模板 → SMTP 发送
       ├─ 成功 → 状态 sent，记录投递时间
       ├─ 瞬时失败（SMTP 5xx/超时/连接错误）→ 释放 job，指数退避重试（≤5 次）
       └─ 上限耗尽 → DLQ + 告警（邮件失败，交易不受影响，D5）
```

- 重试退避：`base=1s`，倍数 5（1s→5s→30s→5min→30min，可配）；抖动 ±20% 防重试风暴。
- **幂等重试**：重试与首次发送共享同一 `dedupe_key`；"发送成功但响应超时"的场景靠 dedupe 行 `sent` 状态避免二次发送（与 GW-302 三态同构：`queued → sending → sent/failed_retryable`）。
- 队列积压/worker 宕机监控（队列深度、最老 job 年龄告警）。

### 5.3 与现有幂等机制的关系

- **不新建第二套幂等**：交易幂等仍是 GW-302 `idempotency_keys`（唯一约束权威）；邮件去重是**下游镜像**的独立小表（`notification_emails.dedupe_key`），键由交易幂等行派生——幂等行不重复迁移，邮件事件自然不重复入队，dedupe 表是双保险。
- Gateway 侧零参与：邮件事件只在 Laravel 侧交易事务提交后产生，不经 Gateway、不经 SDK。

## 6. 故障注入 E2E（验收测试矩阵）

| 场景 | 注入方式 | 期望行为 |
| --- | --- | --- |
| 重复支付回调 | GW-306 沙箱重复回调同一 `callback_idempotency_key` | 订单仅迁移一次（`0→1` 守卫），**邮件仅一封**（dedupe 同键） |
| 100 并发同键下单 | GW-303 沙箱 | 恰 1 单落库，`order.created` 邮件恰一封 |
| SMTP 首次失败后成功 | 队列 worker 前 2 次 mock SMTP 5xx，第 3 次成功 | 指数退避重试后投递成功，交易状态不受影响 |
| SMTP 持续失败 | mock SMTP 全部 5xx | 5 次重试后入 DLQ + 告警；订单/支付状态**不回滚**、不阻塞 |
| 队列 worker 宕机重启 | 重启 worker | 重启后未完成任务恢复重投；dedupe 保证不重复发 |
| 去重键冲突（重放） | 手工重放入队同 `event_id` | 唯一约束冲突，零发送 |
| 模板注入 | 模板或变量含 `<script>`/`{{}}`/白名单外字段 | 转义输出或拒绝渲染；产物无 XSS 载荷、无白名单外字段 |
| 明文凭据禁令 | 模板尝试引用密码/token 字段 | 编译期白名单拒绝；邮件产物 grep 无凭据 |
| 事务与邮件耦合 | 事务回滚（如库存不足） | 邮件未入队（提交后才入队），无"订单回滚但已发信" |

- 证据产物：每场景的测试用例 + CI 记录 URL（TXBoard 主仓库 CI）；沙箱邮箱收集件（Mailhog/类工具）截图留档。

## 7. 验收标准

1. **无独立凭据**：TXBoard 邮件发送复用既有 SMTP 配置；Gateway/SDK 无任何 SMTP 凭据、管理员邮件账号；配置漂移检查（无第二份 mailer 配置）。
2. **四类事件全通**：`order.created` / `order.paid` / `order.cancelled` / `order.refunded` E2E 全绿（沙箱）。
3. **去重**：重复回调/并发同键/重放入队三类场景，同一业务事件**最多一封邮件**（业务策略允许多封时才可配）。
4. **重试与 DLQ**：瞬时故障按退避重试成功；持续失败进 DLQ 告警；队列深度与投递延迟有指标。
5. **故障不回滚交易**：SMTP 故障/队列积压不影响订单状态与支付结果（负例断言存在）。
6. **模板安全**：XSS 注入用例产物安全；明文密码/token 字段被白名单拒绝；远程模板 URL 执行被禁止。
7. **SPF/DKIM/DMARC**：邮件域名单独验证（借鉴点 E）；配置检查入发布检查单。
8. **站内通知不受影响**：邮件通道关闭时 `GET /notices` 站内通知照常。

## 8. 被否决的备选方案

| 备选 | 否决理由 |
| --- | --- |
| Gateway 独立 SMTP 服务/凭据 | 双份邮箱密码与配置漂移；借鉴点 E 明确否决；扩大 Gateway 攻击面 |
| 管理员代建用户 + 明文密码邮件（AirBuddy 原实现） | 借鉴点 C 不变量 1 已否决；明文密码 = 凭据泄漏 |
| Gateway 渲染邮件正文 | 违反"网关不承担敏感业务邮件正文生成"边界；模板与业务规则复制进 Gateway |
| 远程 HTML URL 作为可信动态模板 | 借鉴点 E 明确禁止；RCE/XSS 风险 |
| Redis 去重替代持久化去重 | 借鉴点 E 要求持久化权威；Redis 丢状态即重复发信 |
| 邮件发送同步嵌在交易事务内 | SMTP 慢/故障阻塞甚至回滚合法交易；违反 D5 |
| 邮件失败重试无限次 | 重试风暴；必须有上限 + DLQ + 告警 |

## 9. 与相邻任务的边界

- **GW-302/303/305/306**：交易幂等与状态机仍是唯一交易权威；GW-312 只在其终态迁移点消费事件，**不改**任何交易逻辑、幂等键、状态机。
- **GW-304/310**：订单创建入口（普通/快速购买）产生的 `order.create` 幂等行同一事件语义，快速购买不新增邮件模板类型。
- **GW-307**：注册/邮箱验证码邮件已实现（默认关闭）；GW-312 的交易邮件与验证码邮件共用同一通知服务与同一队列基础设施，但模板与去重键独立。
- **GW-301**：站内通知只读接口不变；交易邮件是镜像通道，不改 `Notice` DTO 与 `GET /notices` 契约。
- **GW-311**：公开支付目录只影响展示，不影响邮件事件。

## 10. 风险与回滚

- **风险**：邮件内容泄露（模板误引白名单外字段）→ §4.2 编译期白名单 + 负例测试；模板变更需审查 + 审计日志。
- **风险**：DLQ 积压无人处理 → 告警 + 定时重投任务 + 积压指标。
- **风险**：邮件被当垃圾邮件拦截 → SPF/DKIM/DMARC 验证 + 发送域名信誉监控。
- **回滚**：站点 `mail_enabled` 开关关闭邮件通道（站内通知保留）；`notification_emails` 表与队列任务可独立清理/暂停；**回滚邮件不影响任何交易数据**（D5 副作用隔离的必然结果）。
- **未验收**：本 ADR 为设计文档，未改任何代码/CI/测试；TXBoard 主仓库实现（事件、模板、队列、E2E）与 GW-306 支付沙箱、GW-303 事务幂等验收仍是前置。Gateway 基线维持 346/346 + SDK 32/32（本次纯文档变更）。

## 11. 未决问题（评审输入）

1. 退款事件（`order.refunded`）是否属于当前范围（TXBoard 是否已有退款终态与幂等行）？若无，退为"预留事件类型"，实现顺序后移。
2. 是否需要在邮件中携带"支付入口深链"（站内订单页相对路径已含，是否需要绝对 URL）？
3. `notification_emails` 表：新建独立表 vs 扩展既有通知表？倾向独立小表（dedupe_key 唯一约束 + 状态机），避免污染站内通知读路径。
4. 重试上限 5 次 / 退避基数是否与 TXBoard 现有队列配置对齐（避免两套重试策略漂移）？

## 附录 A：事件枚举与去重键（契约冻结草案）

```text
order.created     dedupe = SHA-256(trade_no ‖ ":created")
order.paid        dedupe = SHA-256(trade_no ‖ ":paid" ‖ callback_idempotency_key)
order.cancelled   dedupe = SHA-256(trade_no ‖ ":cancelled")
order.refunded    dedupe = SHA-256(trade_no ‖ ":refunded" ‖ refund_idempotency_key)
```

- 与 GW-302 幂等 operation 的关系：邮件事件不进入 `idempotency_keys` 的 operation 枚举（它不是交易写操作）；其去重键由交易幂等行派生，`notification_emails.dedupe_key` 唯一约束是投递层权威。
