# TXBoard 用户前台钱包充值（Native TXAPI）

## 目标

这是**用户本人在线充值钱包**，不是管理员手动补款，也不是购买套餐。支持用户在 Web 用户前台输入金额、选择已有支付方式、完成支付并查询余额和充值流水。独立 TX-Node、Gateway 与**新增第三方支付适配**全部后置。

## 用户流程

1. 登录后的“钱包充值”页面 `/#/wallet`（侧边导航及个人资料余额处可进入），展示钱包余额（整数分），充值记录和可充值支付方式。
2. 用户输入 ¥1.00–¥5,000.00，最多 2 位小数，前台转换成整数分；选取现有已启用的验证型支付渠道。钱包余额、佣金余额互相独立。
3. `POST /txapi/billing/recharges` 需要用户身份、金额 `amount_minor`、`payment_method_id` 以及 `Idempotency-Key: UUID`。事务内锁定用户、校验金额、限制最近 24 小时的未支付请求和保存流水，返回独立 `WR...` 交易号。**创建时不加余额**。
4. `POST /txapi/billing/recharges/{tradeNo}/checkout` 调用已有 PaymentService/支付插件，支持老接口约定的二维码或跳转结果。返回地址指向 `/#/wallet`。
5. 现有 `/api/v1/guest/payment/notify/{method}/{uuid}` 和原生 `/txapi/payment/webhook/{method}/{uuid}` 共享原签名验证。验签成功、交易号和支付渠道匹配、**插件明确提供已验证的实付金额**且等于 `amount_minor + fee_minor` 后，单事务中锁定充值行与用户行，仅增加用户 `balance` 的充值净额，不增加佣金、不发放套餐。
6. 重复同一已验证回调返回成功但不重复加款。不同支付交易号、其他钱包/订单已经使用的支付渠道交易号、错误金额、错误支付渠道、错误签名均不能入账。
7. `GET /txapi/billing/wallet`、`GET /txapi/billing/recharges`、`GET /txapi/billing/recharges/{tradeNo}` 供前台查询余额、本人列表和状态。支付状态轮询仅以数据库完成状态为准。

## 安全设计

- 当前 v2_user.balance 为有符号 32 位 SQL INTEGER，创建充值单与最终入账均检查上限 2,147,483,647 分；接近上限的账户不得发起新充值，付款后若其他操作先占用了余额空间，回调将拒绝自动入账并需对账处理。
- 金额在 HTTP/数据库以整数分表示；前台输入使用字符串拆分而非浮点乘 100，支付费率与现有订单 checkout 逻辑一致；手续费由用户额外支付，但**不会变为钱包到账金额**。
- 充值订单单独记账（`v2_wallet_recharge`），包含唯一商户订单号、`(user_id, request_key)`、`(payment_id, callback_no)` 唯一约束；跨订单付款交易号另行查重。旧订单结算也校验钱包流水，避免顺序重放。
- 只有现有 **EPay、AlipayF2F** 两类已验证实付金额的支付渠道可用于钱包充值，其他插件在补齐可靠 signed amount 语义之前不开放本功能。未知或未提供已验证金额的通知拒绝充值；付款界面并不能构成到账证明。
- 不支持通过用户前台上传“支付成功”凭据来加余额；不提供管理员代充值入口、不把钱包充值伪造成套餐订单。
- 充值流水是永久历史关联：在用户曾有充值记录时禁止无损硬删除该用户；订单/充值均使用行锁保证余额变动不会丢失。
- 为避免支付平台已收款但用户点击取消的资金风险，**当前不允许前台取消充值流水**。创建多个未付款单只受 24h 阈值限制，用户可以从记录继续支付；对于超出上限的异常支付需人工对账。
- 当前仅完成**已存在适配器**的测试性集成，未验证真实支付商沙盒/签名动态配置和 1Panel 上线对账，生产启用前必须独立验证。

## 发布检查

- SQLite/MySQL：UUID 幂等、每用户数据隔离、金额范围、手续费、不存在渠道、恶意回调、重复回调、支付状态/余额、账户删除保护。
- Web：用户路由、导航、余额展示、元→分转换、支付方式、二维码/跳转处理、轮询与充值列表。
- 部署：备份恢复与迁移回滚、支付提供商签名和金额返回字段、Webhook 代理及路由可达性、支付迟到事件与对账。

## 后续
