# Kernel configuration and revocation application v1 (Candidate)

Node retains both embedded sing-box and Xray kernels. Core remains the desired configuration/authorization source. A reported applied state requires the selected kernel to have completed the actual operation. This basic correctness slice follows native snapshots and does not activate production Usage-v2, Provider or SC-v2.

Sing-box Reload may perform only supported updates to the current runtime. Changes to outbound topology, DNS, protocol/inbound identity or other unsupported runtime construction settings must return an explicit full-restart requirement, or complete a verified full reconstruction. The Service stops the uncertain/old kernel, retains sampled native counters, reconstructs from the full desired config/users and confirms hashes only after success. Routing errors are propagated; keeping old routing and returning nil is forbidden. Inbounds absent from the new desired configuration cannot remain open. User-only updates continue to preserve existing authenticated identity, replay history and tracker registration; they do not duplicate tracker attachment or silently discard accumulated counters. Published rules and concurrent connections must not race.

Xray Add/Remove/Update operations validate all candidate memory users before mutating where possible, propagate operation errors, and update local user bookkeeping/limits only after a complete success. A partially mutating error leaves the operation unconfirmed and causes the Service to stop/rebuild from authoritative desired users rather than claim rollback or successful revocation. Kernel capability flags must describe real established-connection termination. If per-user strong close is unavailable, removing or replacing a user's credential requires a verified stop/reconstruction so established streams do not continue under revoked authority. This may disrupt other users and must be documented; do not advertise hitless strong revocation without evidence. A failed reconstruction cannot leave an uncertain old instance serving. Restart counters and native report batches retain their original bookkeeping semantics.

Configuration reconstruction on the same port must release the old listener before binding the replacement. Success is proven by actual protocol authentication and origin routing, not a config hash alone. A failed/occupied target port remains pending and retries through the existing desired/applied mechanism. Kernel errors/logs must not expose credentials or raw secret configuration.

Acceptance: actual sing-box VLESS/VMess traffic switches from old to new custom outbound destination and rejects disallowed routing; invalid route/outbound returns failure and does not mark applied; concurrent route/client updates pass race; old protocol/inbound ports/tags do not remain usable; unchanged user updates preserve meters. Actual Xray supported protocol tests prove established stream closes on user remove/UUID replacement, revoked credentials cannot authenticate, unaffected/current users remain or recover under the declared restart policy, partial operation/conversion failures do not advance applied state, and identical desired config/users can recover after a fault. Both kernels require independent full race/vet/release build and Core/Node integration gates.

Finite offline authorization, persisted Core application revisions, complete live Machine/Workerman control, full protocol coverage and global migration/drain completion remain separate unfinished requirements.
