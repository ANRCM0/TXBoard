# Isolated password recovery over Internal mTLS v1

> 已退役（2026-10-16）：本文保留旧隔离切片的历史协议和验收说明。对应 Core/Gateway 运行入口、配置、SDK 原型消费者、夹具及专属 CI 已移除；下文 Current/local-testing 状态仅描述当时实现。正式 Internal API 仍属 C4 待交付，不提供旧路径或旧版本兼容。见 [当前清理边界](../../../docs/development/core-cleanup.md)。

Status: Current / verified isolated B5.12, local/testing synthetic accounts only. See [fixed-source verification](../../../docs/architecture/v2/internal-isolated-password-reset-verification.json). Native `/txapi/auth/password/forgot` remains authoritative.

The fixed `auth.password.reset`, version `"1"`, requires `user-gateway` service identity, an absent Authorization header, exact signed body/proof admission, the global local Internal gate, `core_shadow.isolated_copy=true` and independent exact-true default-off `CORE_INTERNAL_PASSWORD_RESET_ENABLED`. Neither registration, login nor email-code flags enable it. Technical actor is `0`; no visitor ID, role or IP claim is accepted.

Closed input is required string `email` (254 characters), `password` (1024), `email_code` (128), and optional existing CAPTCHA strings (4096). Original trim/empty normalization, shared native 10-per-minute throttle and real `AuthForget` validation run. The normalized recipient must end with exact `@example.test`. Unknown/duplicate fields and types are refused before native execution. A request-local CAPTCHA adapter requires a known flag and SQL/cache/loaded agreement; enabled CAPTCHA returns native 400 without calling a provider, unavailable/unknown/drifting policy returns safe 503.

The original `AuthController::forgotPassword` and `LoginService::resetPassword` execute unchanged: shared per-email 15-second cache lock, original failed-code budget (three in 300 seconds), current User lookup, password hash/algo/salt update, native save result, revocation of all existing Sanctum sessions, trusted after-reset hook, then code deletion. The existing code is shared with registration/recovery. The lock's lease expiry, cache operation return values and all original transaction boundaries remain unchanged.

This is not a broad SQL transaction or a new idempotency protocol. Password can be committed before session deletion, hook or code deletion fails; expired locks do not fence SQL. Native false token/code delete returns may not prove revocation/consumption. Audit/deadline/lost response can conceal a completed reset. No retry, compensation, automatic fallback or newly issued session is added. Successful reset returns HTTP200 `data={ok:true}`, exact `meta={current_only:true,slice:"internal-isolated-password-reset/1"}`, private/no-store headers, and excludes password/code/email/token from delivery and technical audit. Dispatcher renders credential-bearing exceptions before global reporting and restores the request/facade/guards.

Gateway and SDK add only the explicit encrypted `password-reset` HPKE operation and `/gateway/v1/secure/auth/password-reset` route. Existing operation AAD bytes stay unchanged; the new AAD uses this new route and the existing single-shot `-` session segment. A separate `GATEWAY_INTERNAL_PASSWORD_RESET_ENABLED` local flag, Internal mTLS, HPKE/replay store and Redis limiter are required with full account workflows disabled. SDK `auth.resetPassword` is additive, POST has no retry, and no plaintext reset route is registered. Service failures are dependency errors; native code/quota failures retain their own statuses.

Acceptance must prove current account password/session/code behavior, original code lock/budget and shared throttle, closed transport/proof/default gates, safe partial outcomes, Gateway/SDK encryption and wrong-operation/replay rejection, and actual Redis/MariaDB/TLS1.3 integration. Production reset, external mail/CAPTCHA, universal account routes and full B5/B6 remain gated.
