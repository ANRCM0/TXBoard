# Legacy registration creation evidence v1

Status: Current isolated slice. Covers only the actual new User save in native RegisterService. Validation, registration policy, before hook, invitation handling and UserService defaults retain their original order. Installer/bootstrap and trusted direct-create writers remain outside scope.

Strict default-off `LEGACY_REGISTRATION_CREATION_SHADOW_ENABLED` requires local/testing, the existing capture context and explicit isolated-copy gate. Disabled mode delegates the original save directly, without an added transaction, context validation or evidence SQL. Enabled mode rejects an outer transaction and encloses only the actual new User INSERT and initial evidence in one SQL transaction. Native saving cancellation returns false and creates no evidence. After-commit Observer runs after this transaction and before the original registration-after hook.

The existing immutable `tx_legacy_user_creation_shadow` table also accepts the separate fixed policy `user.register`, version `registration-creation-shadow/v1`. A guest ticket has no authenticated User actor; after INSERT its stored actor_id is bound to the actual newly persisted User ID. No email, password, UUID, Token, invitation secret, grant, financial journal, mapping or fabricated before-state enters the evidence. Exactly the same 15 canonical nonsecret fields are read from SQL. Existing Admin records keep their version, hashes, ticket shape and dedicated verifier. Policy and enablement gates remain independent.

`core:registration-creation-shadow-verify --user=<id> --isolated-copy` performs bounded SELECT-only checks in its own fresh transaction. It validates the registration policy/version, self binding, canonical initial/context/content hashes, current endpoint and at most the first later captured event. It cannot certify a whole chain or a migration gate. Admin and registration verifiers refuse the other's policy.

Invitation consumption precedes this save transaction and retains original non-atomic semantics: an evidence failure can roll back User/evidence while leaving an invitation consumed. Email-code cleanup, IP counters, registration-after hook and session issuance remain outside it. A failure after commit can hide a committed account; there is no automatic retry or compensation. Trusted hook external effects and Observer changes are not silently included in the initial snapshot. Reappearance, later source changes and missing sources stay explicit; independent history and all writer coverage remain unproven.

Acceptance requires native guest policy/validation, independent default-off gates, exact initial and trial-plan values, saving cancellation, original invitation side effects, atomic User/evidence rollback, observer timing, policy separation, Admin regression and real MySQL session visibility. Production migration and frontend work remain deferred.
