# ADR：应用层加密威胁模型与协议（GW-401）

- 状态：**已提出，待评审**
- 日期：2026-10-11
- 责任：GW + 安全审查
- 关联任务：[task-backlog.md](./task-backlog.md) GW-401（本文档）、GW-402（密钥发布/轮换/吊销）、GW-403（封装/解封与 AAD）、GW-404（Redis 抗重放）、GW-405（灰度协商与禁止降级）、GW-406（性能/故障注入/安全复核）、GW-407（可选响应体加密）
- 前置依赖：M2 多实例安全基础（GW-201 威胁建模、GW-213 可信入口、GW-202 Redis 安全态）已完成代码交付
- 现状依据：[app-crypto-preview.md](./app-crypto-preview.md)、`apps/gateway/src/services/crypto.ts`

## 1. 背景与问题

- 当前 Gateway 已实现 HPKE 密文登录/注册/邮箱验证码**技术预览**（PR #6/#7 合并），但它是"先有代码后补设计"：没有正式威胁模型、没有独立密码学审查、没有密钥轮换与吊销流程。
- TXBoard 的部署形态是：浏览器主题 → 边缘反代（1Panel/Nginx）→ Gateway → Laravel。该链路上存在 TLS 终止点之外的中间层：反代访问日志、CDN、宿主机抓包、Gateway 自身日志、代理层可注入的响应内容。
- 需要回答三个问题才能决定 M4 是否推进：
  1. **存在哪些 TLS 覆盖不到的真实威胁？**（值得为它们付复杂度代价）
  2. **哪些数据必须加密、哪些保持明文？**（密文可见边界，避免过度加密破坏可观测性与上游兼容）
  3. **用什么协议、什么库、什么密钥生命周期？**（且全部可评审、可回滚）

## 2. 决策（Decision）

1. **在 TLS 之上叠加应用层 HPKE（RFC 9180）请求体加密**，范围严格限定为三类凭据/敏感提交操作：`secure/auth/login`、`secure/auth/register`、`secure/auth/email-code`。
2. **算法套件**：`DHKEM(P-256, HKDF-SHA256) + HKDF-SHA256 + AES-256-GCM`（RFC 9180 Base KEM + KDF + AEAD），与 `@hpke/core` 实现一致。
3. **AAD 绑定上下文**：协议版本 ‖ HTTP 方法 ‖ 固定操作路径 ‖ kid ‖ ts ‖ nonce。密文无法跨操作路径、跨密钥版本、跨时间重放。
4. **公钥发现端点** `GET /gateway/v1/crypto/key` 返回 `kid` + 压缩公钥（base64url）+ suite + scope，支持双密钥窗口（当前 + 未过期旧密钥）。
5. **私钥永不进入镜像与日志**：Docker 文件 Secret 挂载（`GATEWAY_HPKE_KEY_FILE`，绝对路径，必须存在；缺失或非法直接 fail-hard，绝不重启时生成临时密钥）。
6. **抗重放依赖 Redis**：`kid:nonce` 原子 `SET NX PX`（121s），Redis 不可用对加密写 **fail-closed 503**，不做进程内回退。
7. **TLS 不可豁免**：HPKE 只保护"浏览器到 Gateway"这一段；Gateway→Laravel 内部走私网 HTTPS；应用层加密不是 TLS 的替代品。
8. **不加密响应体**（响应加密是 GW-407 的独立决策，本文档范围之外）；响应明文经私网 HTTPS 传输，其安全性由 TLS 保证。
9. **灰度与兼容**：`GATEWAY_HPKE_MODE=disabled|optional`；`optional` 下旧主题继续走明文端点，`secure/*` 端点本身只接受密文——不存在"静默降级明文"路径（GW-405 验收）。

## 3. 威胁模型

部署链：`浏览器/主题 SDK → 边缘反代（日志/CDN/可达注入） → Gateway（日志/多副本） → Laravel（私网）`。
信任边界：**浏览器与 Gateway 之间不互信于中间任意一层**；Gateway 与 Laravel 之间为私网内互信。

| # | 威胁 | 威胁主体 | 现有控制（TLS 之外的缺口） | 本文档对策 | 残余风险 |
|---|---|---|---|---|---|
| T1 | **代理/中间层可见性**：反代或 CDN 能看到完整请求体明文（密码、邮箱、验证码） | 反代运维、CDN 供应商、宿主机抓包者 | TLS 只保护传输通道；在 TLS 终止点之后（反代）请求体是明文 | 请求体 HPKE 密封，只有 Gateway 持私钥；反代看到的是 `{kid,ts,nonce,enc,ct}` 乱码 | 反代仍可见路径、kid、密文长度与时间（T1-残余见 §4） |
| T2 | **日志泄露**：反代访问日志、CDN 日志、崩溃转储、错误追踪（Sentry 类）落盘明文凭据 | 任何能读日志的人 | Gateway 自身已脱敏（GW-205/214），但反代与 CDN 日志不在 Gateway 控制内 | 请求体密文不落任何中间层日志；Gateway 侧脱敏规则明令禁止记录 `enc/ct/nonce` 原文 | 日志仍含操作路径、kid、大小、时间（元数据不可加密，见 §4） |
| T3 | **前端代码注入 / XSS 后窃取**：恶意或被篡改的第三方主题 JS 读取用户填写的密码明文 | 恶意主题、供应链投毒 | 与传输无关——恶意 JS 在浏览器内运行时凭据就是明文的 | SDK 先 HPKE 密封再提交，恶意脚本拿不到明文密码；AAD 绑定固定路径使偷走的密文无法改投到其他端点 | 恶意脚本仍可在提交前 hook DOM 输入框（输入拦截）；仍需主题白名单与 CSP（M5 范围） |
| T4 | **算法降级 / 密文移植**：攻击者把捕获的密文改头换面投到别的端点，或诱导客户端用弱算法 | 中间人 | AAD 绑定版本+方法+路径+kid+ts+nonce；kid 不匹配 400；enc/ct 有长度与 base64url 校验 | 任意篡改 → AES-256-GCM 认证失败 → 400 `Invalid encrypted request`（GW-403 负例测试） | 无（假设实现正确，需 GW-406 独立复核） |
| T5 | **重放**：捕获一次合法密文，在窗口内重复提交撞库/刷验证码 | 中间人、恶意客户端 | Redis `kid:nonce` 原子占用 + ±60s 时间窗；重复 → 409；Redis 故障 → 503 fail-closed | 单副本只放行一次；跨实例共享同一 Redis | Redis 故障切主/丢数据窗口内理论上可重放一次（GW-406 故障注入项，Redis HA 验收前置） |
| T6 | **密钥材料泄露**：私钥落镜像、落 git、落日志、被日志收集器抓走 | 镜像供应链、CI、宿主机 | 私钥只经 Docker Secret 文件挂载；`.dockerignore` 排除 `secrets/`；容器 UID 1000 + `chmod 600`；缺失密钥 fail-hard 不生成临时密钥 | 泄露后可吊销 kid 并从发现端点移除（§6.4），窗口外密文全部失效 | 吊销前已捕获密文在 ±60s 内仍可用（单次、低成本，可接受） |
| T7 | **时钟偏差**：客户端/服务端时钟不同导致合法请求被拒或被放大窗口 | 部署环境 | ±60s 窗口；时间源偏差是可观测运维问题 | 拒绝范围对客户端明确为 400 `Expired encrypted request`；窗口不可配置放大 | 严重偏差客户端不可用（退化到明文端点仍可用——login 兼容端点存在） |

**威胁模型结论**：T1/T2 是本方案解决的**真实且已验证**的缺口（明文凭据穿过不受 Gateway 控制的日志层）；T3 提供**深度防御**而非完整防护；T4/T5 由 AAD + nonce 机制关闭；T6/T7 由密钥生命周期管理控制。**若无这些威胁则不引入应用层加密**——这正是"opt-in、默认 disabled"的原因。

## 4. 密文可见边界

### 4.1 必须加密（请求体全部）

| 字段 | 位置 | 理由 |
|---|---|---|
| 密码（login/register） | 密封请求体 | 最高敏感；明文绝不越过 TLS 终止点 |
| 邮箱（register/email-code） | 密封请求体 | PII；同时防反代日志留存 |
| 验证码（email-code） | 密封请求体 | 一次性凭据，重放价值极高 |
| 注册附带字段（邀请码、确认密码等） | 密封请求体 | 与密码同级敏感度 |

### 4.2 保持明文（密文信封与元数据——不可也不应加密）

| 字段 | 明文原因 |
|---|---|
| `kid` | 反代/客户端需要路由与密钥版本标识；本身无秘密 |
| `ts` | 反代限流、审计需要时间戳；窗口校验需要 |
| `nonce` | 重放占用键的一部分；无秘密价值 |
| `enc`、`ct` | 密文本身就是"公开密文"——安全假设是只有私钥持有者可解密，不假设密文保密 |
| HTTP 方法、路径 | 路由必需；路径已固定白名单（AAD 绑定同一路径） |
| 请求大小/时间分布 | 网络层元数据，任何加密方案都无法消除（流量分析残余风险，如实声明） |
| 认证响应、Token | **不加密**（GW-407 之前）：响应走私网 HTTPS，安全假设是 TLS；明文响应不落入反代日志由 Gateway 脱敏 + 私网拓扑保证 |
| 公钥发现响应 | 公钥本就可公开，无保密需求 |

### 4.3 边界原则

- **最小加密原则**：只加密凭据提交体。对 GET 类只读操作不做应用层加密——收益为零而破坏缓存与可观测性。
- **AAD 的代价**：密文严格绑定固定路径。这意味着密文**不可跨端点、跨版本、跨时间复用**——这是特性（防移植）而非限制；代价是 SDK 每次操作前需重新发现当前 kid（已实现：`publicKey()` 与 SDK 自动发现）。
- **明确声明**：本方案不隐藏"谁在何时向哪个端点提交了多少字节"的元数据。需要元数据隐私的方案（如洋葱路由）超出本 ADR 范围。

## 5. 对比 TLS-only：为什么还需要应用层加密

| 维度 | TLS-only | TLS + HPKE（本方案） |
|---|---|---|
| 中间层明文暴露 | 反代/CDN/宿主机在 TLS 终止后可见**完整明文请求体**（含密码） | 任何中间层只见密文；明文只存在于浏览器内存与 Gateway 内存 |
| 日志泄露面 | 反代/CDN 访问日志天然记录 body（若开启）或至少可被配置记录；错误追踪平台可能捕获 | 中间层日志里没有任何可读凭据（enc/ct 不可读，日志只落元数据） |
| 前端注入窃取 | 恶意 JS 直接读取 DOM 输入即得明文 | 恶意 JS 拿不到提交前的明文（只拿到密文，且密文不可二次使用） |
| 端到端信任 | 信任链 = 每台中间机 + 每份日志 | 信任链 = Gateway 私钥保管方；中间机数量与质量不再相关 |
| 性能 | 基线 | 每请求一次 P-256 ECDH + AES-256-GCM，亚毫秒级（客户端）+ 亚毫秒级（服务端）；p95 增量 < 2ms 量级，GW-406 实测验收 |
| 复杂度成本 | 无 | 密钥生命周期（发现/轮换/吊销）、Redis 依赖、SDK 分支、独立密码学审查 |
| 失败模式 | TLS 握手失败即断 | Redis 故障对加密写 fail-closed（**可用性下降**）；`disabled` 模式零影响 |

**结论**：TLS-only 的缺口是结构性的——它保证"通道不被窃听"，但不保证"明文不穿过我们不控制的日志层与故障转储"。本方案的交换是：**用可审计的密钥生命周期与一次密码学审查，换取凭据在整条部署链上不再以明文形式出现**。这是 opt-in 的，旧主题不受影响。

## 6. 密钥生命周期

### 6.1 公钥发现

- 端点：`GET /gateway/v1/crypto/key`（`cryptoKey` 策略，公开、可缓存由部署层决定）。
- 响应（`KeyDiscoveryResponse`）：
  ```
  { protocol: "HPKE-RFC9180",
    suite: "DHKEM(P-256,HKDF-SHA256)+HKDF-SHA256+AES-256-GCM",
    keys: [ { kid, publicKey, scope, expiresAt? }, ... ] }
  ```
- `kid` = `SHA-256(序列化公钥)` 前 24 个十六进制字符；换密钥自动换 kid，**kid 即内容寻址**。
- `scope`：`login-only`（默认）或 `account-workflows`（开启 register/email-code 时）。SDK 据 scope 决定是否可提交对应操作。
- 响应**绝不含私钥、不含 `d` 分量**；公钥为压缩序列化（65 字节 → base64url）。
- SDK 每次加密操作前发现当前 key（不长期缓存公钥），保证轮换即时生效。

### 6.2 私钥安全存储

| 环境 | 载体 | 要求 |
|---|---|---|
| 开发/测试 | 本地文件 Secret（`secrets/hpke-key.json`） | `.dockerignore` 排除 `secrets/`；`chmod 600`；绝不提交 git |
| 生产（当前） | **Docker 文件 Secret**：`GATEWAY_HPKE_KEY_FILE`（绝对路径，如 `/run/secrets/hpke_key`） | 挂载只读；容器 UID 1000 可读、其他 UID 不可读；宿主目录不进镜像构建上下文 |
| 生产（目标） | KMS/Vault 托管（如 1Panel 侧接 Vault/KMS 签发或信封加密） | 私钥不出 KMS；Gateway 用 KMS 信封加密 JWK 落盘，启动时解密加载；**当前未实施**，列入 GW-406 前置 |

**硬性规则（写入代码断言）**：

- 未提供 `GATEWAY_HPKE_KEY_FILE` 或文件不存在/非法 → 启动直接 fail，**绝不生成临时密钥**（临时密钥会让重启后历史密文全部失效且 kid 漂移，破坏客户端）。
- `GATEWAY_HPKE_MODE=disabled` 时完全不加载密钥材料，零攻击面。
- 私钥内容禁止出现在任何日志、错误消息、`/metrics`、`/readyz` 输出中（错误信息只报"invalid key file"级别的事实，不回显内容）。
- 多实例必须共享同一私钥文件与同一 Redis（同 kid、同 nonce 空间），否则单实例无法解另一实例收到的密文。

### 6.3 密钥轮换（双版本窗口）

目标：**轮换期间零客户端感知、零密文丢失**。

1. **生成新密钥**：`node scripts/generate-hpke-key.mjs` 只新建不覆盖；得到新 JWK。
2. **部署新私钥为"当前"**，旧私钥降级为"旧密钥"：
   - `GATEWAY_HPKE_KEY_FILE` → 新私钥（当前版本，无 `expiresAt`）
   - `GATEWAY_HPKE_PREVIOUS_KEY_FILE` → 旧私钥
   - `GATEWAY_HPKE_PREVIOUS_KEY_TTL_MS` → 旧密钥窗口（默认 86_400_000 = 24h；最小 60s，最大 7 天）
3. **窗口行为**（`crypto.ts` 已实现）：
   - `publicKey()` 同时返回当前 kid 与未过期旧 kid → SDK 优先用当前，回退用旧的，轮换即时对新客户端生效；
   - `open()` 先尝试当前 kid，再尝试未过期旧 kid → 轮换前提交的密文在窗口内仍可解密；
   - 旧密钥过期后从发现端点移除、解密拒绝 → 窗口外密文自然失效。
4. **窗口长度选择依据**：覆盖 SDK 缓存/离线重放的最大延迟（建议 ≥ 24h）；支付/长事务场景可加大，但每加大一倍，旧私钥泄露的暴露面也加大一倍——这是可调的安全-可用性权衡。
5. **轮换记录**：每次轮换记运维审计（时间、新 kid 前 12 位、窗口时长、操作人），不记私钥。
6. **回滚**：把旧密钥文件换回 `GATEWAY_HPKE_KEY_FILE` 即恢复；轮换本身不涉及数据迁移，回滚成本为零。

**未实施（GW-402 范围）**：目前 `crypto.ts` 已支持双窗口代码路径，但**尚无自动轮换调度、轮换审计落库、kid 吊销登记**——本次 ADR 为它们定义目标行为。

### 6.4 密钥吊销

触发条件：私钥疑似泄露、合规要求、算法降级预警。

1. **从发现端点移除 kid**：Gateway 重启/热加载时只加载受信 kid；被吊销 kid 立即从 `publicKey()` 的 `keys` 列表消失 → 新客户端无法再用它加密。
2. **窗口外拒解密**：吊销即把该 kid 的 `expiresAt` 置为过去（或直接不加载对应私钥）→ `open()` 抛 `Unknown encryption key` 400。
3. **灰度降级**：吊销瞬间，仍持有旧发现的客户端会短暂提交被拒密文 → 客户端 SDK 行为是**重新发现 key 后用新 kid 重试一次**；失败则报错，**不静默降级明文**（GW-405 验收项）。
4. **吊销与旧客户端**：无法强制所有已部署旧主题立即刷新公钥发现；因此吊销对"已捕获密文"无防御力（密文不依赖发现端点）——**吊销不是"让历史密文失效"的手段**，它只阻止新密文生成。历史密文的防御是 nonce + ±60s 窗口（T5）。
5. **多副本一致性**：吊销是配置变更（文件/env），必须随 Gateway 全副本滚动生效；未生效副本仍能解被吊销 kid 的密文——部署顺序与 `rollout` 演练纳入 GW-402 验收。

### 6.5 生命周期总览

```
生成 → 加载（fail-hard，无临时密钥） → 发布（kid 入发现端点）
  → 轮换（新当前 + 旧窗口） → 旧窗口过期（自然失效）
  → 吊销（移除 kid + 拒解密，不追溯历史密文）
```

| S6 | 无算法降级路径：`secure/*` 端点只接受密封请求，明文提交 400；`optional` 模式下旧主题不被断线 | GW-405 验收项 | 待 GW-405 测试 |
| S7 | 私钥不出镜像/不出 git/不出日志：`.dockerignore` + fail-hard + 日志断言审查 | `docker-deployment.md` + S6 类断言 | 待人工走查 |
| S8 | 双窗口轮换演练：生成新密钥→部署→旧密文窗口内仍解→窗口后拒→回滚恢复 | GW-402 验收项 | 未做（代码路径已存在） |
| S9 | 时钟偏差演练：客户端 ±90s/±300s 偏差下行为符合预期（拒绝明确、不放大窗口） | GW-406 故障注入 | 未做 |
| S10 | 性能增量：HPKE 加解密 p95 增量 < 2ms（基准对比明文端点） | GW-406 压测 | 未做 |
| S11 | 独立密码学审查：第三方或独立于实现者的安全审查通过（含 AAD 设计、nonce 空间、时间窗取值） | GW-406 硬性前置 | **未做——M4 Go/No-Go 的阻断项** |
| S12 | 依赖审计：`@hpke/core` 版本锁定、无已知高危 CVE、SBOM 可复现 | GW-103/207 | 部分（lockfile 已有；SBOM 待补） |

**Go/No-Go 判据**：S1–S12 全绿（或 S11 独立审查明确书面通过）才向愿意 opt-in 的主题开放加密端点；S11 不通过则继续 TLS-only，且**不阻塞**任何非加密功能。

## 8. 被否决的备选方案

| 备选 | 否决理由 |
|---|---|
| **共享对称密码（PSK：浏览器与 Gateway 预共享一把 AES 密钥）** | 密钥分发是死结：浏览器代码公开 → 任何拿到页面的人拿到 PSK → 加密等于无；前向保密为零（一把钥匙泄露 = 全部历史密文可解）；无法按用户/会话撤销。HPKE 的公钥封装天然解决"公开信道上的保密" |
| **路径/参数哈希（把敏感参数 `SHA-256` 后放路径或查询串）** | 哈希不是加密：密码/邮箱的熵有限，彩虹表/暴力可逆（尤其邮箱空间小、验证码 6 位可秒破）；且把敏感材料放进 URL → 落进所有反代访问日志，**比明文更糟**（还多一个"看起来安全"的假象）；无法抗撞库侧信道 |
| **自制加密（自己拼 ECDH + AES，或非标准组合）** | 密码学原语实现极难做对（nonce 复用、常量时间、编码陷阱）；RFC 9180 + `@hpke/core` 已被广泛审计；自制方案无法通过独立审查（S11），且违反"依赖成熟库"的工程原则 |
| **只用 TLS，声称已足够** | 见 §5：TLS 终止点之后明文凭据穿过不受控日志层，缺口是结构性的；无法用配置修补 |
| **全流量应用层加密（所有 GET 也加密）** | 收益为零（GET 无敏感请求体，响应本就不加密），破坏缓存、CDN、可观测性；违背最小加密原则 |
| **响应体加密（本次一起做）** | 需求未论证（响应是只读 DTO、无凭据），且引入响应密钥派生/nonce/兼容新问题；列为 GW-407 独立决策，先证明需求再实现 |
| **Signal Protocol / 双棘轮** | 为"长连接双向消息流"设计，本场景是"无状态一次性请求"，棘轮状态管理纯属过度工程；HPKE base 模式正合适 |
| **客户端长期存私钥** | GW-402 验收明令禁止；浏览器无法安全保管私钥 |

## 9. 验收标准（输入 GW-402～GW-406）

1. 本文档 §3 威胁模型与 §4 边界表经安全评审签字。
2. `GET /gateway/v1/crypto/key` 返回结构符合 §6.1，永不回显私钥分量（负例断言：响应 body 不含 `d`、不含 `private` 字样）。
3. 私钥加载 fail-hard 测试：缺失/非法 key 文件时进程拒绝启动（不生成临时密钥）。
4. 双窗口：部署旧密钥+新密钥后，用旧 kid 加密的请求在窗口内 200、窗口后 400；发现端点窗口期内返回 2 个 kid、窗口后 1 个。
5. 吊销：kid 移除后新密文提交 400 `Unknown encryption key`；客户端重新发现后重试成功；无静默明文降级。
6. 性能：HPKE 模式相对明文基线 p95 增量实测值记录在案。
7. Redis 断连时加密写 503 且零上游调用（fail-closed 断言）。
8. 独立密码学审查报告归档（S11）。

## 10. 风险与回滚

- **风险：过度加密损害可观测性** → 边界表（§4）限定加密范围，元数据明文可观测；日志只落 kid/nonce/ts。
- **风险：Redis 成为加密写的新单点** → fail-closed 语义明确（宁可拒服务也不放明文/防重放失效）；Redis HA（AOF/切主演练）是 GW-406 前置，未达标前加密端点保持 `optional` 且敏感操作限流。
- **风险：轮换失误导致旧密文集体失效** → 窗口 ≥24h + SDK 提交前重新发现 kid；轮换文档化（§6.3 步骤 1-6）。
- **风险：SDK 缓存公钥过久** → 约定"每次加密前发现"，发现端点失败不缓存过期 kid（SDK 行为属 GW-403/405 验收）。
- **回滚**：`GATEWAY_HPKE_MODE=disabled` 即完全摘除加密路径，旧主题走明文兼容端点；ADR 与 GW-402+ 的实现可独立回滚，不影响任何只读接口与 TLS 基线。

## 11. 未决问题（评审输入）

1. 生产私钥载体是否现在就引入 KMS/Vault 信封加密（§6.2 目标态），还是继续 Docker Secret 至 M4 结束？建议后者，KMS 列入 M4 后的运维任务。
2. 旧密钥窗口默认 24h 是否匹配所有主题的 SDK 发现频率？需要各主题适配器刷新策略确认（M5 输入）。
3. 独立密码学审查的承担方与时点（内部安全组 vs 外部审计）——GW-406 排期依赖此决策。
4. 响应体加密（GW-407）是否在 M4 内启动需求论证？本文档立场：不阻塞本 ADR，单独评审。
