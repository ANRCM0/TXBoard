# Commerce Shadow v1

> B1.3 foundation: isolated-copy evidence and financial opening entries. Existing OrderService, WalletRechargeService and User writers remain authoritative. This slice does not enable payment attempts, fulfillment, refunds or a ledger balance authority.

All seven tables use the dedicated `tx_commerce_shadow_*` namespace. They are migration evidence, separate from future authoritative money/order tables. Capture and reconciliation JSON identify `mode=isolated_shadow` and `legacy_authority=retained`; scanning or matching evidence cannot publish an authority transition.

`core:commerce-shadow --isolated-copy --run=<key> --snapshot=<operator-copy-key> --currency=<ISO> --limit=<1..1000>` freezes User and Order high-water IDs and scans users before orders. Resuming the same run requires the identical snapshot key and explicit currency. Supported currencies are USD, CNY, EUR, GBP, HKD, SGD, CAD, AUD, NZD and TWD; the existing balances and order amounts are already minor units and are never multiplied by 100. `--retry-user=<id>` and `--retry-order=<id>` retry individual exceptions inside the frozen high waters. Completion of scanning does not establish reconciliation or authority cutover.

The operator must use a quiesced, isolated copy. Each aggregate is captured in a database transaction: lock User first, then the relevant legacy Order and new money accounts in ascending account ID. Shadow maps and ordered accounts use locking current reads; immutable journals/postings use shared current reads, so MariaDB REPEATABLE READ cannot replay against an obsolete pre-lock snapshot after another session commits. Wallet and commission sources are read again before committing. Existing snapshots never change; a changed source or damaged shadow becomes an unresolved exception. This is a per-aggregate transaction boundary, not a claim that separate resumable chunks share one global database snapshot. Read-only reconciliation and a later migration fence/change-capture gate are required before any authority switch.

| Table | Meaning |
| --- | --- |
| `tx_commerce_shadow_user_opening` | Immutable per-user/currency money source, hash, opening journal references and capture boundary. |
| `tx_commerce_shadow_order` | Immutable per-order source and derived amount evidence; no fabricated historical Terms, provider verification or fulfillment. |
| `tx_commerce_shadow_money_account` | Immutable user wallet and commission accounts, and separate system migration clearing accounts for each purpose and currency. |
| `tx_commerce_shadow_money_journal` | Immutable posted opening journals; unique business type/ref/idempotency key. |
| `tx_commerce_shadow_money_posting` | Immutable positive minor amounts with debit/credit side. Composite account/currency and journal/currency foreign keys prevent cross-currency postings. |
| `tx_commerce_shadow_checkpoint` | Durable bounded cursors, source high waters and immutable run context. |
| `tx_commerce_shadow_exception` | Retryable unresolved/resolved evidence and retained attempts. |

New internal foreign keys restrict deletion; no foreign key blocks legacy User, Plan or Order deletion. DDL supports additive replay and refuses rollback after any new table has data. Published Eloquent records reject update/delete. Application transactions enforce at least two positive postings and balanced debit/credit in each currency; read-only reconciliation checks persisted posting identities, amounts, hashes and totals, including tampering through direct SQL. No account balance projection is introduced.

A positive wallet opening credits the user's wallet liability and debits the currency's wallet migration clearing account. Commission uses its own user liability and commission clearing account. Zero balances have an opening snapshot but no journal or zero posting. Negative, null/unknown, float, malformed or overflowing balances block capture. These are opening entries only: retained recharge and commission tables continue to be audit evidence, and historical receipts/income are not synthesized again.

Order `total_amount` is external amount still due after discounts, surplus and wallet deduction. `balance_amount` was already deducted by order creation: pending/processing evidence retains that predebit; cancellation restores it through the old writer; completed/discounted evidence describes the original consumption. It is not added to the wallet opening or booked as a second expense. `surplus_credit` is excess surplus credited only by legacy fulfillment. Surplus applied is `surplus_amount-surplus_credit`; reconstructed item net is `total_amount+balance_amount+surplus_applied`, and reconstructed gross adds `discount_amount`. These derived values are explicitly labeled reconstruction, with `legacy_snapshot_unknown` Terms; current Plan never supplies historical quotes or grants. Nullable raw fields remain distinguishable from derived zero.

The old free checkout calls `paid(trade_no)` without a provider. A zero-due order therefore has no provider collection evidence, even when a callback marker or paid timestamp exists. Positive-due legacy payment markers are unverified evidence, never a new payment attempt or journal. `handling_amount` is the external fee; recharge `amount_minor` is credited principal and `fee_minor` is external fee. Duplicate nonempty callbacks scoped to the legacy payment ID are checked against both orders and recharges using bound queries. Unknown callback scope, ambiguous surplus ownership or invalid amounts block capture.

Trade and callback references are retained only as domain-separated opaque SHA-256 digests; no raw provider/config credentials, UUID, token, request key or callback payload is persisted or returned. Amounts, database IDs and version counters use canonical decimal strings in JSON; timestamps use safe UTC seconds. Error reports contain fixed codes, never exception text or source secrets.

`--reconcile=user|order --cursor=<id>` returns `read_only=true`, `scope=current-user-order-evidence` and bounded per-object, per-field differences. The ordered ID union includes legacy source, shadow and exception IDs across currencies and runs, including resolved exception-only records, deleted sources, absent shadows and evidence above the run's frozen high water. Each branch fetches at most `limit+1` distinct IDs before the combined union is again limited to `limit+1`; exceptions in multiple currencies cannot consume the sentinel and prematurely end pagination. It inspects at most `limit` and returns explicit `after_cursor/next_cursor/cursor/has_more`. Exactly `limit` remaining IDs yields `has_more=false`; an empty page never implies that earlier pages were clean. `cursor` remains an alias of `next_cursor` for existing callers.

Every page independently checks the complete run context and original capture timestamp, run completion, both current source high waters against their frozen high waters, and all unresolved commerce exceptions regardless of currency, aggregate type, page cursor or originating run. These checks produce `global_issues/unresolved_count`. `page_ok=true` requires both no global issue and no difference on the current page. JSON also returns explicit public `snapshot_key/currency`, a context integrity hash, checkpoint version, both frozen and observed source high waters, counts and per-row differences. The CLI exits unsuccessfully when `page_ok=false`, including a matching/empty page blocked by incomplete scanning, source growth or off-page exceptions. A successful CLI page may still have `has_more=true`; a deployment gate must consume both aggregate types from cursor zero through `has_more=false`, retain every page failure and validate the expected run context.

Optional CLI `--snapshot/--currency` on reconciliation compare the returned public context with the operator's expected copy/currency and fail with `COMMERCE_CONTEXT_CHANGED` even on an empty page. The context hash is a digest of the currently stored valid allow-list context, not a previously signed immutable copy identity; direct SQL replacement by another valid snapshot label cannot be detected from that digest alone. A deployment gate must compare `snapshot_key` with its fixed release/copy identity.

Reconciliation owns a fresh, independent SQL transaction and refuses an existing outer transaction with `COMMERCE_RECONCILE_OUTER_TRANSACTION_UNSUPPORTED`, so its union cannot inherit an older MariaDB MVCC discovery view. Its checkpoint and inspected source/shadow/opening records retain locking/current-read semantics; source ID discovery/global counts use that page's fresh ordinary view. Order inspection preserves User before Order locks and rejects a changed owner. It never prelocks Orders or exceptions during ID discovery. It does not change snapshots, checkpoints, exception state, balances or legacy records; SELECT row locks are not business writes. Query logs and before/after snapshots verify this boundary.

Each page is a separate observation on a quiesced isolated copy, not one atomic snapshot across pages. Later pages detect new high-water rows, new exceptions and differences in subsequently inspected rows, but changing an already inspected row without moving the high water can escape a forward-only scan. A second scan alone is not a writer fence or proof against all drift. The deployment adapter must retain the quiesced-copy requirement and unfinished legacy writer/change-capture gates. The scope verifies current source/shadow evidence and ledger records referenced by user openings; it does not prove all superseded/orphan private journals/postings or financial history. Source field differences and opening ledger damage are blocking evidence; a matching page does not validate the entire production migration. See [Core model](../../docs/architecture/v2/core-domain-model.md) and [Core evolution](../../docs/architecture/v2/core-evolution.md).

Verification of the final dedicated shadow namespace on 2026-10-12: `CommerceShadowTest` passed 25 cases / 184 assertions on SQLite, with the independent-session test explicitly skipped; MariaDB 11.4.12 passed all 26 cases / 200 assertions in the dedicated local `txboard_concurrency_test` database. Before any shadow entry exists, eight independent sessions each begin a transaction and freeze an empty-journal MVCC read view. A barrier opens only after all eight snapshots are established. Concurrent replay then produces one user opening, one order shadow, two balanced shadow journals and four shadow postings; waiting sessions see committed evidence through ordered locking/shared current reads. Tests also exercise wallet predebits, cancellation evidence, discounted/excess surplus, free orders, exact large integers, duplicate order/recharge callbacks, transaction rollback, source changes, SQL tampering, immutable models, composite currency foreign keys, legacy deletion, additive DDL replay, refusal of destructive rollback and absence of live money/order-item/payment-attempt tables. Production-copy rehearsal, payment races/refunds, incremental capture/fences, account balance authority and authority cutover remain separate gates.

Read-only pagination gate verification on 2026-10-12: the expanded `CommerceShadowTest` passed 37 cases / 364 assertions on SQLite with one MariaDB-only case skipped, and all 38 cases / 380 assertions on MariaDB 11.4.12. Additional cases cover empty, exact and multiple sparse pages; distinct exception-only IDs across currencies; unresolved exceptions outside the requested page/type/run; incomplete runs; growth in both sources between pages; subsequent-row field changes; deleted sources and missing shadows; invalid context; expected CLI copy/currency; and rejection of an outer transaction. Complete user/order scans at a one-row page size recorded only SELECT statements, while snapshots of every fixture source and commerce shadow table remained identical before and after. These results validate the stated current-user-order-evidence scope on the isolated local test databases.
