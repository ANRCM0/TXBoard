# 多团队开发与 PR 协作方案

2026-10-15 用户确认：后续团队通过 Pull Request 参与开发。本方案适用于 TXBoard（后续 tx-core）和独立 TXBoard-Deploy；沿用[批次开发与集中验收](development-workflow.md)。当前目标是基于已有实现并行交付基础功能，完整 v2 模型和生产迁移继续按各自门禁推进。

## 团队分工与负责人

以下为职责划分，实际团队账号、领域负责人和替补审阅人尚待维护者登记；不是已经建立的 GitHub Teams 或 CODEOWNERS。前期同一团队或维护者可兼任多个角色。

| 工作线 | 主要目录/领域 | 职责与边界 | 默认审阅角色 |
| --- | --- | --- | --- |
| Core 业务 | `api/` 内账户、套餐、订单、支付、权限与账务 | 复用 Core 服务与事务；不另建订单、额度或余额权威 | 对应业务领域负责人 |
| 节点与网络 | `node/`，Core 内 Node/Machine 控制及流量接口 | Node 执行与计量；Core 负责授权政策和结算；内核依赖升级单独说明 | Node 负责人；改 Core 协议时加 Core 负责人 |
| Gateway | `gateway/`，与其关联的 Internal API | 接口适配、身份传递与入口策略；Core 每次重新鉴权；不直接写 Core 数据库 | Gateway 负责人；改 Core 接口时加 Core 负责人 |
| 安装与交付 | TXBoard-Deploy，主仓镜像构建及运行参数 | 三组件安装、配置、启停、更新和恢复；不重写业务账本 | Deploy 负责人；改镜像接口时加相关组件负责人 |
| 接口与集成协调 | `contracts/`、共享 DTO、数据库迁移、根 CI 与发布规则 | 协调跨团队变更、登记依赖、集中集成验收与发布组合 | 相关双方负责人及集成负责人 |

Core 的业务领域可以继续细分负责人，但当前共享 User/Order/流量等模型仍有耦合。模型、权限中间件和通用业务服务的修改不能只按文件目录自行认领。新前端留在 TX-F 暂缓开发，继续只本地提交、不推送；产品 Agent/MCP 不恢复。

任务或 PR 中填写本批负责人、涉及目录和预计交付，维护者按上述职责指定实际审阅人。在负责人名单确定前，由维护者手动分配；不创建含虚构账号或无效占位符的 CODEOWNERS。

## PR 开发流程

1. **确定任务与基线**：说明目标、范围、关联契约和依赖 PR。通常以维护者确认的默认分支为目标；尚未合入的依赖可使用明确的集成分支或 stacked PR，必须注明 base 和依赖，不把历史审阅分支当作默认稳定基线。
2. **独立开发**：每个任务使用独立 checkout/worktree 与分支，例如 `feat/node-<topic>`、`fix/core-<topic>`、`docs/<topic>`。有写权限者推送主题分支；外部团队使用 fork PR。不要多人共写同一分支/工作目录，未经协作者协调不强推共享分支。
3. **可选 Draft PR**：跨团队契约或依赖需要提前讨论时使用 Draft。Draft 中列出待完成项，不因开 Draft 就反复进行全套验收。日常只做必要检查，完成一个功能或多个相关阶段后集中测试修复。
4. **提交可审阅 PR**：使用仓库 PR 模板，描述实际行为、影响组件、契约/数据库变化和验证结果。一个 PR 对应一项连贯交付，可以包含多个相关阶段，不按每个小修复拆 PR，也不混入无关功能。
5. **审阅与修复**：至少一名非作者的领域审阅人批准。跨团队契约需生产者与消费者双方确认；账务、权限、迁移和发布相关变更加入对应领域或集成负责人审阅，可由符合角色的人兼任。实质修改后重新确认受影响部分。
6. **集中集成验收**：复用适用证据，统一跑本批主要链路与受影响回归，汇总问题集中修复，只复测相关部分。完整矩阵及复杂恢复按关联批次或发布安排，不能把延后范围写成已通过。
7. **合并与发布**：非 Draft、依赖就绪、审阅意见处理、相关 CI 成功且已配置的 required checks 满足后，由维护者/获授权集成负责人合并。默认使用 merge commit，保留已有约定；合并权限不授予作者自审自合。发布另按版本及镜像门禁执行。

后续源码、契约和协作文档变更都走主题分支 → PR → 审阅 → 合并，不直接推送默认分支。已有审阅分支可继续推送准备工作；只有分支推送不表示 PR 已创建、审阅通过或允许发布。工具权限不足时保留分支与可审阅说明，明确报告阻碍，不代替维护者绕过流程。

## 公共变更与跨仓依赖

| 变更 | 协调方式 |
| --- | --- |
| HTTP/Internal API/Node 协议、DTO、错误码与鉴权 | 先明确 Current 与 Target；在契约 PR 或同一连贯 PR 中确定生产者/消费者变化，不静默改变现有语义；双方审阅 |
| 数据库表、共享模型和 migration | 在任务/PR登记迁移文件名与目标表，由 Core 负责人协调顺序；不修改已应用迁移、不并发占用相同编号，不把隔离影子模型当作生产权威 |
| 镜像、启动参数、健康检查与安装器能力 | 主仓与 Deploy PR 互相引用，记录所需版本/能力及固定镜像；消费者合并/启用前确认实际支持的产物，不能假设功能分支已发布镜像 |
| 根 CI、依赖锁、公共工具和发布 | 指定集成负责人审阅；依赖升级与业务需求无关时独立提交，不混入大范围格式化或顺手重构 |

同仓变更尽量在一个可审阅 PR 内原子完成；跨仓不能假设同时合并或三个镜像原子发布。先合入可独立工作的生产者或契约准备，再接消费者；不具备安全过渡路径时，将依赖保留在 Draft/集成分支，集中验收后按已确定的发布顺序启用。互相引用 PR 和精确源码/镜像版本，避免以浮动 `latest` 证明兼容。

## 环境、CI 与交付节奏

每个团队使用专用合成数据库、Redis 前缀和测试目录，不共用可任意清空的环境，不提交秘密、数据库备份和私密日志。需要真实环境验收时按批次固定源码并记录关键结果；纯文档只检查差异和引用，不启动业务环境。协调者统一安排跨团队测试，不要求每个团队重复全矩阵。

保留现有 required checks 和发布门禁。先用批次末尾推送减少重复触发；如果后续调整 CI 路径/依赖筛选，作为独立 PR 审阅，不把缺席或被跳过的工作流记为成功。fork PR 不获得发布凭据，不以不可信 PR 代码接触生产密钥；需要权限的验收由维护者在隔离环境安排。

每批汇报：完成的可用功能、关联 PR/依赖、实际问题、待补验收和发布状态。PR 合并与正式发布分别记录；当前审阅分支和历史 CI 证据不能证明默认分支已经具备相同能力。

## 维护者接入事项与当前状态

| 事项 | 当前状态/下一步 |
| --- | --- |
| 团队分工、PR流程和批次验收规则 | 本方案已定义；实际人员由维护者分配 |
| 两仓贡献指南、PR描述模板、行为约束 | 随本批交付；合入对应分支后使用 |
| CODEOWNERS | 尚未配置；确认真实账号/团队及访问权限后，以独立 PR 添加路径规则 |
| 默认分支保护或 ruleset | 本批未修改远端设置；维护者核实强制PR、非作者批准、实质更新后的复审、禁止任意直推/强推及管理员例外 |
| Required checks | 按实际工作流依赖和路径触发登记；本批不改现有检查，不把不会运行的工作流设为所有PR无条件必需 |
| 合并和发布权限 | 维护者分配最小必要权限；团队贡献权限不自动包含默认分支直推、合并或生产发布 |
| 首批接入 | 先选择边界明确的Core、Node、Gateway或Deploy任务试运行PR协作，再按实际冲突调整领域分工 |

上述为协作约定与待办；文档、模板本身不能强制 GitHub 权限或审批。未核实的远端设置不宣称已启用。本批不创建团队、邀请成员或修改保护规则。
