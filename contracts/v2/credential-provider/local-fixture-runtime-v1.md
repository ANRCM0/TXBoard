# Local Credential Provider Fixture Runtime v1

> B4.1 local/testing foundation. Default off. This implements synthetic issue/query evidence only; it does not authorize a Node, install a v2 plugin, import legacy credentials or replace PHP Plugin Package v1.

The Core adapter registers a fixed project-owned `synthetic-fixture-v1` executable identity, provider ID, instance epoch, operation grants and the `synthetic-v1` profile. The caller cannot select a command, URL, working directory or storage path. The registered script digest must match before invocation. Changing an existing provider epoch or registration is refused. The only accepted operator scope is the explicitly named local fixture grant; issue/query also bind the requested Subject and registered provider. The service has no HTTP route and does not treat an untrusted caller-supplied authorization label as authentication.

The process loads no Laravel or v1 plugin code. Its environment is replaced, with no Core DB/Redis credentials, and its PHP startup configuration is disabled. Provider-owned fixture secrets come from `random_bytes` and are persisted only in the private fixture state. Public credential and subject references use independent random values, not hashes of those secrets. No secret is emitted on stdout/stderr, included in a Core DTO, persisted in Core SQL or sent to a Core logger. Core records only allow-listed inputs, operation identity/hash, stable status/error codes and validated nonsecret receipts.

This is a trusted local executable running under the same OS identity as its parent. A 0700 directory and 0600 file do not stop Core or another process with that identity from reading them. Environment removal, PHP file/network restrictions and byte/time limits are defense in depth; they are not an OS sandbox or proof that an adversarial executable lacks host access. Separate service identities, authenticated transport, OS/network/container restrictions and production resource budgets remain open gates. Existing PHP v1 plugins remain trusted in-process code.

Both `credential_provider_fixture.enabled=true` and `core_shadow.isolated_copy=true` are required, and the application must be local/testing. Absence returns `CAPABILITY_UNAVAILABLE` without starting a process. Requests and responses have 4096-byte limits, finite UTC deadlines at most five seconds away, and a wall execution budget at most two seconds. The adapter starts a fixed argv array with no shell, discards diagnostics, and rejects unexpected response fields, provider/epoch/operation identity mismatch, unsupported profiles or malformed references. Failure never reports raw transport text or filesystem paths.

Core persists an operation before IPC. A provider-private file lock and atomic state replacement commit the synthetic credential and its idempotent receipt together. Core success is stored afterward. These fixture checks prove process-restart persistence; power-loss durability and backup recovery remain unverified. After the recording transaction commits, dispatch locks and rechecks the current registered epoch and operation/profile grants, retaining that registration lock throughout bounded IPC. A grant change committed before dispatch takes precedence over its previous registration object. Unknown recovery requires the query grant; it cannot use an issue grant to bypass query revocation. A timeout, response loss, process failure or uncertain Core finalization leaves a durable unknown operation. Replaying such an operation performs query with its original operation ID; it does not issue again. Provider query after restart returns its original receipt. An absent private operation remains unknown and requires explicit investigation; changing the epoch is not a recovery mechanism. A same key with different canonical input hash is rejected. One fixture issuance per provider/Subject is allowed. Query is scoped by the registration, operator grant and original Subject, and exposes no secret-search or export operation.

The JSON envelope version is `credential-provider/local-fixture/1`. IDs and versions are canonical decimal strings; timestamps are finite safe integers. The allow-listed issue input carries a Core-existing Subject, expected auth version, fixed profile, finite not-before/expiry and Core-resolved subscription/Terms IDs. New issuance rechecks Subject revocation/version/ownership and current subscription/Terms under locks immediately before IPC. The current projected Terms must still be effective, and credential expiry must fit its known bounds; a projection that expires after recording prevents dispatch. It preserves the Subject and all legacy fields; receipt storage does not bind a credential for live authorization. Query accepts only a known Core operation reference in the same provider/Subject scope and epoch, including safe recovery after Subject revocation. Parse/render/delivery/rotate/revoke/import are explicitly unsupported. There is no production credential format, authentication algorithm, custom encryption or secret delivery channel.

Core shadow schema uses `tx_credential_provider_shadow_registration` and `tx_credential_provider_shadow_operation`, with database uniqueness and restrictive internal references. History rollback is refused. See [CredentialProvider target contract](README.md), [Plugin Platform v2](../../../docs/architecture/v2/plugin-platform.md) and [Plugin Package v1](../../plugin-package/README.md).

PHP 8.4 / Linux fixture verification: SQLite 20 tests passed with 120 assertions; two MariaDB-only concurrency cases were skipped. MariaDB 11.4.12: all 22 tests passed with 147 assertions. Eight independent Core sessions with the same key produced one Core operation and one private issuance; eight competing keys for one Subject produced one success and seven binding conflicts. Each IPC invocation launched an independent PHP process. Tests verified cleared Core environment, rejected Core file reads/disabled PHP network functions, private file modes and absence of the synthetic secret from Core SQL/results/logger calls. These PHP restrictions are evidence about this fixed trusted script only, not an OS isolation claim. Response loss, timeout after private commit, and Core finalization failure recovered the original receipt through query after process restart; an absent private operation was never issued during recovery. Current registration grant revocation, Subject revocation and Terms expiration after operation recording prevented dispatch. A fixed committed Core snapshot plus these Provider files passed the full API suite: 698 tests and 5012 assertions, with 16 engine-specific skips. Input/output size limits, malformed/wrong-identity responses, operation/profile/epoch scope and schema replay/rollback checks passed. Native table-name, documentation path and diff checks passed. Windows permissions, power-loss durability, malicious-runtime isolation, production identity/authentication and Node delivery remain unverified.

The local verification entry point is `cd api && php artisan test --filter=FixtureProviderTest`. MariaDB cases additionally require `CORE_PROVIDER_TEST_MYSQL=1`, database connection variables and exclusive use of the disposable `txboard_concurrency_test` database; the suite refuses any other MySQL database name. Its cleanup touches only the named shadow fixture tables. The service entry points are `register(providerId, epoch, operationGrants, profileGrants)`, `issue(FixtureScope, businessKey, input, deadlineAt)` and `query(FixtureScope, operationRef, deadlineAt)`; no HTTP, plugin lifecycle or production writer is wired to them.
