# Subscription Terms Shadow v1

> Retired: 2026-10-16. The isolated mutation service and its tests have been removed.
> Current purchase/renewal uses native fulfillment; reset uses the native
> lifecycle service. The read-only Terms timeline remains shared by Subscription
> and UsageV2. Historical database records and the text below are retained for
> reference only. See [Core cleanup](../../docs/development/core-cleanup.md).

> B1.4 isolated-copy domain slice. Legacy User, orders and resets remain authoritative. No legacy writer, route, worker or provider is connected to these mutations.

`SubscriptionTermsTimeline` resolves immutable Terms and immutable transitions into half-open intervals. An outgoing transition caps the predecessor at the earlier of its original end and transition time; the successor begins exactly at that time. The resolver rejects missing ownership, duplicate versions, forks, cycles, disconnected histories, invalid intervals and stale tip pointers. A pre-existing gap remains a gap. `at` excludes an interval's end; `covers` accepts a usage interval ending exactly at that end, but rejects one crossing into the successor. Period creation Terms may differ from the currently effective Terms while remaining in the same subscription.

`resolve`, `at` and `covers` accept an optional final `currentRead` boolean. SQL adapters holding subscription locks within an existing transaction pass `true`; this makes all subscription/Terms/transition reads current even if that transaction already has an older MariaDB consistent view. The resolver does not acquire batch or grant locks. Mutation services require their own fresh transaction, so accepted evidence cannot inherit an older caller read view; they reject an existing outer transaction.

`SubscriptionTermsShadowService` requires `core_shadow.isolated_copy=true` and local/testing environment. Operations carry a business key, expected subscription/period versions, immediate `effective_at=now`, and an explicit policy version. Locking order is User, persistent slot, subscription IDs in ascending order, then period IDs in ascending order. Current reads after these locks avoid stale MariaDB snapshots. Identical requests return the original immutable result before checking now-stale versions; a different request under the same key is rejected. A dedicated `tx_subscription_terms_shadow_operation` preserves request/result hashes and internal restrictive references. It never publishes an authority epoch.

Terms, transitions and period histories each have a 1,000-row processing limit. Reads fetch at most 1,001 rows to detect overflow before projection work; `TERMS_PERIOD_HISTORY_LIMIT` refuses a longer period history without mutation. After User/slot/subscription locks, an already stored business operation is validated and replayed before loading period history, so this limit never prevents returning its original frozen result. A new business key still fails closed.

`advance` supports renew, limits, quota, price evidence and explicit admin edits within the same subscription. Renewal uses the actual legacy UTC Carbon `addMonths` algorithm and configured overflow behavior, with existing calendar month counts; conversion from perpetual, inactive renewal and cross-plan upgrade are excluded. Limit or price evidence changes keep expiry, reset anchors and counters. A quota change appends a signed `quota_change` adjustment and updates the same period's budget in the same transaction. Unknown/null quotas and unknown period boundaries block mutation. Original Terms, transition ranges, period creation Terms, reset anchors and all accumulated counters remain unchanged. Quote evidence contains only allow-listed currency/amount/code/hash fields; it is not a payment or historical contract.

`reset` requires a verified legacy reset trigger and exact policy version. It closes the old period without losing its original counters, starts a new period at that boundary with zero new counters, increments the reset count, and calculates the next boundary using the frozen Terms reset method and billing timezone plus current expiry anchor. A scheduled reset must occur at its recorded due boundary; late or unknown boundaries require a separately verified policy. This makes extra allowance an explicit reset consequence. A normal renewal, price change or new Terms version alone never grants it.

Old rules were inspected in [OrderService](../../api/app/Services/OrderService.php), [TrafficResetService](../../api/app/Services/TrafficResetService.php) and [User editor](../../api/app/Http/Controllers/Txapi/Admin/UserEditorController.php). Active same-plan renewal usually preserves u/d; new purchase, onetime purchase, perpetual-to-calendar conversion and configured order events can explicitly reset. The editor changes group on plan changes but does not silently adopt Plan quota. Reset dates use the resolved method and expiry anchor with calendar clamping; no 30/365-day substitution is used here. Current PlanRevision references remain null.

Before changing a boundary, the service verifies accepted B3 batch evidence, including pending/processing/retry/quarantined records and settled entries. Any already accepted interval beyond the new boundary that refers to the affected subscription blocks mutation. Corrupt/unavailable evidence or a bounded scan overflow blocks it as unknown, rather than guessing attribution. The slice does not reverse-lock B3 batches/grants while holding subscription locks. A later B3 adapter must enforce this projected timeline when issuing/freezing grants; it must not require period creation Terms to equal later grant Terms. This slice does not claim that adapter or a live migration fence is installed.

All database IDs, versions and byte values are canonical decimal strings in JSON. UTC timestamps remain safe integers. SQL/transaction failures roll back Terms, transition, quota adjustment, period projection and operation evidence together. Original legacy User/Order/Plan fields remain untouched. Production-copy migration, legacy writer cutover and general cross-plan upgrades remain separate gates. See [Core model](../../docs/architecture/v2/core-domain-model.md) and [Core evolution](../../docs/architecture/v2/core-evolution.md).

Verified with PHP 8.4 and SQLite: 23 tests passed, 143 assertions; four MariaDB-specific cases were skipped. MariaDB 11.4.12: all 27 tests passed, 192 assertions. The 1,001-period fixture fails closed before timeline or projection work; an original completed reset still replays its frozen result after history grows beyond the limit, while a new business key is rejected. Eight independent sessions competing with the same expected versions produced one transition and seven version conflicts. Eight independent sessions replaying the same business key produced one Terms successor, transition, adjustment and operation result. A deterministic old consistent-view test reproduced stale ordinary timeline reads and verified the current-read path sees the committed successor; a separate process was observed waiting on the User row lock before pending B3 evidence committed, then refused the boundary change. Injected final-operation failures rolled back both advance and reset aggregates. Calendar reset dates were compared directly with the existing TrafficResetService, including month-end/leap-year clamping and configured timezone. Native table-name and documentation path checks passed. These are local isolated-copy checks, not a production cutover validation.
