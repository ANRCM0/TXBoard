# Core 新功能开发与维护

> 状态：开发流程设计草案；日期：2026-10-17。
>
> 本文补充[小内核与业务模块设计](../architecture/v2/core-kernel-modular-design.md)，说明后续功能如何落点、实现和验收。它不表示新 Kernel、所有能力接口、开发模板或依赖检查已经实现。
>
> 当前开发仍遵守 [Native 基线](native-development-baseline.md)：复用现有权威服务，不增加历史版本兼容，不放宽权限、事务与恢复约束；重型验收默认 CI。

## 1. 日常开发原则

**大多数新功能应修改所属业务模块，而不是修改 Kernel。**

小内核不是永久冻结整个 Core。订阅、资金、节点等业务模块可以持续增加能力；稳定的是职责、调用与数据边界，不是所有接口签名永远不变。

- 不要求每个功能创建新模块、插件、接口、Repository 和事件。
- 模块内只有一个实现、没有隔离需要的内部类可以直接使用。
- 功能需要跨域时，调用明确业务用例或登记的 SQL-only 参与者，不直接改另一域的表。
- 新增外部提供方优先实现已有协议端口；协议做不到的新业务不能由 adapter 伪装支持。
- Kernel 的调整需要真实共享需求和依赖审查；套餐、计费及退款规则不因被多个入口调用就进入 Kernel。
- 新功能不必等 K5 才开始：先在现有 native owner 内开发，按实际触及边界逐步接入新契约，不另起第二套业务实现。

## 2. 功能应该放在哪里

| 功能类型 | 正常落点 | 一般不应该改动 |
| --- | --- | --- |
| 新增套餐规则、订阅生命周期行为 | Subscription 的应用用例与规则 | Kernel、具体支付协议 |
| 新增付款、退款或折抵政策 | Billing；涉及权益时使用受控跨域参与 | 插件直接写账、HTTP 自己计算金额 |
| 新增支付渠道 | 当前支付插件包、adapter、声明和契约检查 | 订阅算法、账本算法、Core 渠道 switch |
| 新增邮件/消息提供方 | 通知业务所需的协议适配 | 订单/订阅权威、Kernel |
| 新增业务统计 | 对应模块的有界只读查询/投影 | 写状态机、自动修账、余额权威 |
| 新增 API/CLI 入口 | 当前注册入口及输入输出适配，调用同一用例 | 复制价格、权限、状态和恢复逻辑 |
| 独立的新业务领域 | 有独立规则与数据责任的第一方模块 | 仅为一个小功能建立独立运行时或数据库 |
| 真正共享的基础机制 | 先评估现有宿主/模块设施，再按需提取 Kernel 契约 | 通用 `invoke`、万能基类、共享可变状态 |

如接口尚未落地，按[当前领域说明](../../api/app/Domains/Subscription/README.md)调用现有权威服务，不编写对不存在的目标类的运行时代码。抽取接口时由原实现直接满足，或仅在确有转换时建立 adapter。

## 3. 每个功能的短说明

先用一份足够短的功能说明回答关键问题，不要求每个小功能写长篇 ADR：

```text
功能目标：
所属业务模块 / 实际消费者：
支持与明确不支持的范围：
入口、actor、权限和资源归属：
输入、输出和稳定错误：
复用的公开业务能力 / 需要新增的能力：
数据责任、事务 owner 和版本前置：
业务键、重放、超时与失败恢复：
Schema / 外部契约 / 配置变更：
本地静态检查与相关 CI：
发布依赖、停用行为和数据恢复限制：
```

纯展示功能的无关项可以标不涉及。跨域权限、资金、用量或秘密边界变更必须明确回答相关项；只有改变重要架构决策时才增加 ADR。

## 4. 一条可重复的开发流程

已有纵向示例：原生 HTTP 与 Internal API 的账户读取共用
[AccountQueries](../../contracts/v2/core-account-read-ports-v1.md)。业务查询放在 Identity，
订阅事实委托 Subscription；入口各自认证当前 actor 并做协议映射，不让 Internal API
为读取数据实例化 HTTP Controller。该 K4 子集仍是待本提交验收的候选，不代表所有入口都已统一。

1. **定位 owner 与规则。** 先区分业务变化、协议变化或入口变化；核对原实现与真实消费者。
2. **确定最小契约。** 复用已有用例；必要时新增窄接口/DTO，定义权限、错误、业务键和完成程度。公开协议变化先同步契约。
3. **实现一个纵向切片。** 从真实入口到权威行为及结果，包含必要数据约束；不要先造一批无消费者接口。
4. **接入外部能力与恢复。** 网络留在 SQL 事务外；保留原操作证据。影响多域时明确唯一提交负责人。
5. **增加针对性检查。** 普通功能覆盖相关行为；写功能覆盖并发、幂等、越权和失败；不要每次重复所有协议矩阵。
6. **集中交付。** 静态检查后按正常授权流程提交候选、通过 Draft PR 的相关 CI，修复并复测；非作者审阅、合并和发布分别记录。

开发、候选推送或 CI 成功不自动授权主线合并和生产发布。当前可同步调整源码与消费者，不需要为旧开发版本增加双写、别名或 fallback。

## 5. 示例一：增加订阅到期提醒

这是通知业务扩展，不是修改订阅生命周期：

- 先定义提前多久、发给谁、哪些订阅状态可提醒、续费后如何取消/替换未发送提醒。
- 通过 Subscription 的受限只读查询获得当前目标；缺少必要查询时由 Subscription 增加明确公开能力，而不是通知模块任意查询/修改订阅表。
- 通知用例生成自己的持久投递意图和业务键，绑定订阅、到期版本/时点、规则及接收目标，避免扫描/重试重复创建。
- Worker 经邮件/消息适配器投递；网络失败按原意图恢复。若渠道不支持幂等或查询，不承诺网络 exactly-once。
- 执行前核对提醒仍有意义及目标仍获授权；不携带代理凭据或无关个人信息。

主要改动应是必要的订阅只读能力、提醒用例、投递适配和相关检查。通常不修改 Kernel、支付、账本或订阅 Terms。持久投递机制按真实需要复用，不强塞进金融或 credential work 表。

## 6. 示例二：增加一个支付渠道

当前已有[支付插件开发指南](payment-plugin-development.md)和 [payment-starter](../../contracts/plugin-package/examples/payment-starter/)，不必等新 Kernel：

- 实现当前包及 `native-payment-provider/1` 契约，替换 starter 的身份与协议，并如实声明能力。
- 完成冻结参数、checkout、通知验证、query 与 ACK；不支持项保持明确拒绝。
- 验证金额、币种、商户、交易身份、禁用恢复和包版本，不创建任何订单/账本/权益事实。
- Core 继续完成 receipt、结算和履约；新增渠道不需要增加 Core 渠道 switch。

现有契约只支持的 checkout/币种/退款范围不能被新插件声明扩大。若新渠道依赖当前尚不支持的网络建单或原路退款，应先设计并实现正式契约及 Core 工作流，而不是在 adapter 中暗藏副作用。

## 7. 示例三：增加流量加购包

这是核心业务规则变化，不能当普通通知插件开发：

- 先决定加购是否立即生效、作用于哪个周期、是否叠加、何时失效、退款如何处理，以及明确不重置已用量的语义。
- Subscription Catalog/购买负责商品和冻结权益，Billing 负责真实资金及幂等接受。
- 履约通过 Subscription 与 Usage 的受控事务参与修改配额/调整证据；不能让支付插件或 API 直接增加 User 额度。
- 保留原已用量、预留与历史周期；追加和纠正使用明确证据，不能清零或改挂旧批次。
- CI 覆盖重复支付/履约、并发加购、周期切换、配额溢出和失败回滚等直接受影响行为。

这是未来功能示例，不表示本设计已经决定加购政策或实现该能力。正常情况下仍无需修改 Kernel，也不必建立新的微服务。

## 8. 可维护性的具体约束

### 8.1 模块公开面

每个模块维护短 README：负责什么、公开用例、数据责任、事务约束、外部依赖和测试位置。模块内重构可以自由进行；跨模块只能依赖登记公开面，不从其他模块深层内部类随意取工具函数。

模块接口应窄而明确。不要把每张表暴露成通用 CRUD，也不要让插件调用 `setBalance`、`setSubscriptionStatus` 或任意 `postJournal`。复用业务动作，不是复用越权写库入口。

### 8.2 测试与静态约束

有三类检查：纯规则的确定性测试、端口/适配器契约测试，以及当前数据库和真实消费者的集成检查。mock 通过不代表锁序、资金原子性或真实协议已验证。

K1 开始建设最小依赖检查，K5 收口；这些新增检查目前属于设计目标，不宣称已经生效。对现有难以立即拆开的依赖登记理由和范围，阻止继续扩大，而不是把全部例外永久忽略。

本地只做必要语法、差异和轻量静态检查；数据库、网络、真实进程/流量、race 和完整构建默认走对应组件 CI。

### 8.3 变更与停用

当前开发期允许同批破坏性调整 Schema、接口与配置，但必须同步实际消费者和针对性检查。后续正式发布后，版本协作与数据迁移策略需另行明确，不能把当前开发规则当作永久删除生产数据的授权。

新增可选功能要定义停用行为：阻止新请求不等于可以丢弃持久意图、真实收款、未结算流量或历史秘密恢复材料。代码回退也不自动回退已提交业务数据。

## 9. 开发体验的交付要求

架构阶段还应交付以下开发支撑，而不只交付抽象类：

| 项目 | 实际用途 | 阶段 |
| --- | --- | --- |
| 模块/公开入口/数据 owner 地图 | 新需求能定位到正确模块 | K0 |
| 一个真实的端口化业务示例 | 展示完整输入、授权、实现、装配、测试，而非空模板 | K1 |
| 外部能力接入指南与契约检查 | 新提供方可以复用明确流程；支付已有 starter 应继续使用 | K2 |
| 事务参与和锁序示例 | 跨域功能不误用外层事务或独立提交 | K3 |
| 入口映射、错误和恢复规范 | 新 API/CLI 不复制业务规则 | K4 |
| 生效的依赖检查、CI 分工与维护文档 | 功能增加后仍能发现边界退化 | K5 |

新建通用业务脚手架只在真实试点稳定后考虑；不要求每个功能生成固定数量文件或经过固定七层。

完成定义：功能具有明确 owner、真实消费者、正确业务结果、失败恢复和相关验证；后续维护者能看懂它改动了什么事实、为何安全，以及哪些行为不支持。
