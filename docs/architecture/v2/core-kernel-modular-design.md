# Core 小内核与业务模块详细设计

> 状态：Target / Draft，待评审；日期：2026-10-17。
>
> 用户确认的方向是“小内核、业务模块通过能力接口与适配层协作”。本文给出这一方向的具体设计，不表示目录重组、接口实现、事务重构或多租户已经完成。
>
> 源码基线：本地 `main` 提交 `85b0eac62f73f636efe736548e968535c561ced3`；业务实现说明见[当前基线](current-progress.md)。本轮仅检查本地代码与契约，不核验远端 CI、生产环境或发布。

## 1. 设计结论与适用范围

采用 **模块化单体 + 小 Kernel + 领域能力接口 + 当前协议适配器**：

- Core 产品继续拥有账户、订阅、订单、资金、用量和授权的唯一持久业务权威。
- Kernel 是 Core 内部的一小部分，不包含套餐、续费、退款或节点计费算法。
- 业务模块以代码和契约边界组织，默认同一版本发布、使用同一业务数据库，不拆成微服务。
- 适配层隔离当前接口、框架和外部提供方的差异，不复制业务规则。
- 支付渠道、通知和外部集成可以扩展；订阅、账本等必选业务域不支持热卸载。
- 先复用已有 native 实现，再按真实依赖提取接口；不建立一套平行“新 Core”。

本文默认一个安装对应一个运营方，运营方管理多个终端用户。它不是多个独立商户共享同一库的多租户产品。`installation_id` 不是 `tenant_id`，单有效订阅也不是租户数量限制。

### 1.1 当前能力不是待重写清单

当前基线已经包含正式订阅、共同权益、支付尝试、真实收款、账本、钱包退款、升级折抵、Provider 和有界服务接口。不能根据旧 C1 工作目录或带有历史名称的模型基类判断“这些能力尚未实现”。

| 已有边界 | 本设计处理 |
| --- | --- |
| `Domains/Subscription/Services` | 保留发布、建单、履约、生命周期、权益与凭据协调算法；逐步增加精确的公开契约 |
| `Domains/Billing` | 保留资金事实、锁序、付款裁决、退款和恢复；不另建余额服务或通用入账 API |
| `Domains/UsageV2` | 保留接收、预留、结算、Session/Period 归属和证据验证 |
| `Domains/CredentialProvider` 与独立 Provider | 保留协议适配与代理秘密的进程边界 |
| `Domains/Installation` | 保留持久安装、admission、epoch 与就绪状态，不由 Kernel 另造全局开关 |
| 当前 Plugin/Theme/Payment Registry | 保留专有运行时与包生命周期，不再建一个平行模块注册中心 |

依据：[订阅领域说明](../../../api/app/Domains/Subscription/README.md)、[业务与扩展边界](core-extension-boundaries.md)、[Native 开发基线](../../development/native-development-baseline.md)。

### 1.2 明确不做

本设计不引入历史版本兼容、legacy/shadow 双轨、旧插件适配、自动旧库转换、通用插件沙箱、任意动态业务加载、分布式事务、服务网格或多数据库微服务。也不恢复 Agent/MCP、不开发新前端、不在 Core 内重建安装器。

当前开发允许同步修改源码、Schema、接口与真实消费者；这不授权删除未知数据、覆盖金融证据、降低鉴权或将现有状态伪装成新安装。

## 2. 术语和硬决策

| 名称 | 本文含义 |
| --- | --- |
| Core 产品 | API、Worker、Scheduler、领域实现及必要基础设施组成的业务控制中心 |
| Kernel | 与具体业务、Laravel、数据库和外部协议无关的最小公共类型与契约 |
| 业务模块 | 有明确业务规则、数据责任和公开用例的第一方代码单元，不等同于插件包 |
| 能力接口 / Port | 对输入、输出、权限、事务、幂等和错误语义的明确约定 |
| 适配器 / Adapter | 实现能力接口或转换当前协议；只能翻译和委托，不能产生另一套业务事实 |
| 兼容层 | 用户设想中的能力接入层；本项目具体采用当前协议适配，不承诺历史版本兼容 |
| 事务参与者 | 只在指定宿主事务中运行的内部 SQL 能力，不是对外应用入口 |
| 扩展插件 | 当前包契约管理的 Payment、Theme、通知等扩展，不自动获得业务权限 |

设计硬决策：

1. 业务依赖能力契约，不直接依赖某个渠道协议或任意插件类。
2. Kernel 不依赖业务模块；模块专属契约留在所属领域，不全部搬入 Kernel。
3. 同一份事实只有一个权威；派生视图不得反向写回。
4. 接口抽取默认保持现有业务语义、数据库和事务所有者。
5. 所有网络调用在业务 SQL 事务之外；未知结果沿原操作恢复。
6. 当前必选模块随 Core 版本发布，不能运行中任意替换、停用或卸载。
7. “支持某能力”“当前已配置”“当前健康”“调用者获授权”是四件事。
8. 框架接口、领域公开接口和对外 HTTP 协议分别管理，不要求同名同版本。
9. 不因本方案扩大当前支付币种、退款目的地或 Node 协议支持范围。
10. 无真实隔离或替换价值的转发类不应新增。

## 3. 总体分层

```text
用户 API / 管理 API / Internal API / CLI / Scheduler / Worker
                    |
          身份认证、输入解析、入口策略
                    |
         领域公开用例 Contracts + Services
                    |
        业务规则、状态机、持久证据及恢复决策
                    |
       所需能力接口 / 明确的事务内参与接口
                    ^
                    |
       SQL、Provider、支付渠道、通知等适配实现

Kernel: 不可变上下文、时间、错误分类等最小公共契约
Composition Root: 由 Laravel 宿主显式装配以上实现
```

依赖关系与运行时调用方向不同：业务依赖 Port，Adapter 实现 Port；运行时通过已注入的实现完成调用。不能将所有调用改成 `CompatibilityManager::invoke($name, $payload)`。

### 3.1 各层可以依赖什么

| 层 | 允许 | 禁止 |
| --- | --- | --- |
| Kernel | PHP 基础类型、必要标准接口 | Eloquent、HTTP Request、Redis、业务模型、具体 Provider |
| 纯领域规则 / 值对象 | Kernel、本域值对象与规则 | 容器定位、网络、环境变量、直接 SQL |
| 应用服务 | 本域规则、公开契约、内部事务能力、必要宿主设施 | 任意插件类、跨域任意表写、客户端声明的权限 |
| 当前 SQL 实现 | 本域持久化及经登记的跨域参与 | 隐式修改其他模块状态、网络 I/O、独立提交参与事务 |
| 入站适配器 | 认证、DTO 解码、调用公开用例、协议响应映射 | 自己算订单价格、余额、到期或流量归属 |
| 出站适配器 | 当前渠道 SDK、SQL/HTTP/邮件等实现 | 接管 Core 业务状态机、抬高已验证能力范围 |
| 装配层 | 显式依赖绑定、版本/能力检查、scoped 生命周期 | 用请求参数选择类、运行时回退到旧权威 |

并不要求第一批把所有现有 `DB::` 调用搬出应用服务。优先保证对外公开契约和不可绕过的业务边界；只有存在测试隔离、领域所有权或替换需要时，才提取专门存储接口。纯计算策略与外部协议应优先分离。

## 4. 业务模块职责

逻辑边界先于文件移动。第一版沿用 `app/Domains`，不新建一套与它平行的业务框架。

| 模块 | 核心责任 | 对其他模块提供 | 不负责 |
| --- | --- | --- | --- |
| Identity / Account | 用户身份、会话、封禁、管理员资格与授权事实 | 当前 actor/账户状态及受控身份操作 | 订阅额度、订单价格、钱包余额 |
| Subscription | Catalog、发布 Offer、购买协调、订阅/Terms/Slot、生命周期、共同权益、Access 协调 | 目录、购买用例、权益快照、生命周期、凭据与链接操作 | 渠道收款验证、任意账本分录 |
| Billing | 订单支付状态、attempt/receipt/allocation、账本、钱包、退款、升级现金预算、恢复 | Checkout、查询、取消、退款、只读对账及内部支付证明 | Provider 协议秘密、独立的订阅规则 |
| Usage | Session/批次接收、原周期预留、结算和计量证据 | 批次回执、用量读取、受控周期参与能力 | 按当前套餐猜历史归属、重新授予访问 |
| Network | Node/Machine/Group/Route、目标身份、授权签名、应用状态 | 节点管理、完整有限授权、撤销覆盖信息 | 自行决定付款或订阅权益 |
| CredentialProvider adapter | Core 与独立 Provider 的受限协议和信任转换 | 非秘密协议结果、元数据、操作回执 | 保存或向普通 Core DTO 返回代理秘密 |
| Installation | 安装身份、Schema/epoch、准入与就绪 | 每次读写/工作项的持久准入判断 | 商业套餐、用户角色、租户计费 |
| Extension Runtime | Plugin/Theme 生命周期、包校验、只读库存、具体扩展发现 | 当前 Registry/Lifecycle、受限 Payment 实现 | 订单/资金/权益第二权威、通用执行通道 |
| Content / Support / Notifications | 公告、知识库、工单、通知投递 | 各自范围内的用户支持能力 | 绕过购买和退款用例修改业务事实 |

Catalog 和 Access 先作为 Subscription 的逻辑子边界，不立即拆独立进程、数据库或插件。Billing 内的 Ledger/Wallet/Refund 也不因类多就拆成独立服务。

### 4.1 领域公共接口与消费者端口

- 模块对外提供的用例契约由能力提供方维护，例如 Subscription 的权益查询。
- 需要替换外部实现的出站端口由消费业务定义，例如支付协议能力、Provider 元数据传输。
- 两个第一方模块已经共享合适契约时直接依赖契约，不再两边各造一个镜像接口和中间转发器。
- 字段形状或安全语义确实不同才设置转换适配器。
- 稳定 DTO 不携带 Eloquent Model、Query Builder、Laravel Request、数据库连接或可调用 Closure。

### 4.2 业务操作与数据责任

数据责任不等于“只有一个文件能写一张表”。必须区分拥有规则的模块和同事务内被授权的参与者：

| 数据/事实 | 规则所有者 | 允许的协作 |
| --- | --- | --- |
| 用户身份、封禁、会话 | Identity | 其他模块读取当前身份；不直接更改角色 |
| Revision/Offer/购买条款 | Subscription Catalog / 购买协调 | Billing 引用冻结价格和证据，不改报价 |
| Subscription/Terms/Slot | Subscription | Billing 升级接受调用 SQL-only 履约参与者 |
| Order 状态 | 购买、Billing、履约按状态转换分别负责 | 使用已登记转换，不各自提供任意 `setStatus` |
| UsagePeriod 生命周期 | Subscription 当前实现 | 周期创建/关闭/配额调整与 Terms 同事务 |
| UsagePeriod 累计量和预留 | Usage | 接收/结算按原周期更新；订阅转换消费并保护这些事实 |
| 钱包、资金分录、退款、现金 claim | Billing | 外部只能请求明确业务操作，不能任意 `postJournal` |
| AccessSubject 与 Provider 操作引用 | Subscription Access 协调 | Provider adapter 返回协议结果，Core 重验归属和版本 |
| Node 授权版本与目标 | Network | 消费共同权益和 Provider 非秘密材料承诺 |

未来若将周期存储整体归入 Usage，必须用同事务 `UsagePeriodParticipant` 接入订阅转换；不能先改 Terms、异步再改 Period。现有受控共享写入先登记，不在目录重组时直接禁止或拆散。

## 5. Kernel 的最小内容

建议在现有 `app/Core` 下新建 `Kernel` 子目录；`Core/Http` 仍是宿主 HTTP 设施，不因此变成纯内核。

| 契约/类型 | 用途 | 限制 |
| --- | --- | --- |
| `Clock` | 注入业务时间，便于确定性检查 | 不替代签名租约、高水位或服务器可信时钟策略 |
| `InvocationContext` | 不可变执行 ID、来源、请求关联和可信 actor 引用 | 客户端不能反序列化得到可信上下文；角色快照不是永久授权 |
| `ActorRef` | 区分 User/Admin/Service/Node/系统任务及外部回调的来源引用 | 持有引用不代表已授权；支付回调另由领域验证冻结渠道身份，不携带原始 Token |
| `FailureCategory` | 统一输入错误、拒绝、冲突、依赖未知等分类 | 保留领域稳定错误码；未知提交状态不能映射为“未发生” |
| `OperationRef` | 关联持久业务操作和恢复状态 | 不代替每个领域的真实幂等键及唯一约束 |
| `CommitScope`，后续按需 | 为内部参与者携带宿主事务身份和准入范围 | 不能通过 HTTP 创建；不能表示任意 SQL 权限；未提取前不添加空壳 |
| 公共审计/事件头，后续按需 | 共用 actor、执行 ID、版本和非秘密关联 | 事件 payload、持久化和完成证据仍归领域 |

不预先添加 `BaseEntity`、万能 `Repository<T>`、`AbstractBusinessModule`、反射事件总线、全局 Service Locator 或任意 SQL/Shell 能力。

接口表示可替换能力，`final` 值对象表示业务数据。抽象类仅复用确有两个实现需要、语义稳定的代码；不要求所有模块继承共同父类。

## 6. 接口设计

具体约束见 [Core Module Ports v1 草案](../../../contracts/v2/core-module-ports-v1.md)。该草案是进程内设计，不注册新的 HTTP 入口。

### 6.1 三类接口必须分开

| 类型 | 调用方 | 事务语义 | 示例 |
| --- | --- | --- | --- |
| 公开应用用例 | API、CLI、Worker、其他明确协调者 | 按原契约拥有 fresh transaction 或完整持久工作流 | 发布、建单、履约、暂停、退款 |
| 内部事务参与者 | 已登记的同进程事务 owner | 加入同一连接/事务，不自行提交、不做网络 | `SubscriptionFulfillmentService::applyLocked()` |
| 外部协议能力 | 持久意图提交后的驱动器 | 事务外调用；结果可能 unknown，需回执验证 | Payment query、Provider issue/query/revoke |

同一个接口不同时提供以上三种隐含语义。公共方法不能因“底层已经有事务”就猜测是否加入事务。

### 6.2 优先收口的能力

1. `EntitlementQueries`：统一账户展示、Node 授权和订阅分发所需的非秘密权益。
2. `PublishedPurchaseCommands`：使用已发布 Offer 创建订单，复用原永久业务键和冻结购买证据。
3. `SubscriptionLifecycleCommands`：显式暂停、恢复、撤销、到期、重置；不提供任意状态更新。
4. `BillingCommands / BillingQueries`：Checkout、查询、取消、钱包退款、对账；Ledger 内部原语不外露。
5. 当前 `NativePaymentProviderInterface`：复用现有真实扩展点，不平行发明另一个 Payment Gateway 框架。
6. Provider transport/metadata 能力：保持非秘密协议结果与独立交付通道。

没有数据形状转换的现有 Service 可以直接实现接口；只有协议或依赖隔离需要时才新增 Adapter。已经存在的 `Subscription/Services` 不再复制回 `App/Services/Subscription`。

## 7. 事务与跨模块一致性

### 7.1 一个用例只有一个提交负责人

保留当前 `NativeBillingTransaction::run()`、`SubscriptionFulfillmentService::fulfill()` 等公开入口对外层事务的拒绝。不得先在 Controller 加 `DB::transaction`，再调用这些入口。

涉及多个模块时选择其一：

- 使用现有公开用例的完整事务与持久恢复过程。
- 由明确协调者开启事务，调用显式 SQL-only 参与者；提交和回滚只由协调者决定。

后一种路径当前已经用于升级接受：资金事实与 SQL 权益替换必须原子完成。不是把多个独立提交的方法顺序执行即可。

### 7.2 原子边界矩阵

| 用例 | 同一事务必须提交的内容 | 事务外及恢复 |
| --- | --- | --- |
| 目录发布 | Revision/Offer 及当前发布关系 | 展示缓存失效，不能影响历史购买 |
| 建单 | 冻结购买、订单、幂等；升级时包括来源报价/claim 等原有证据 | 不在建单事务中请求支付网络 |
| 普通收款接受 | 真实 receipt、journal/posting、唯一 allocation、订单转换、履约 work | 持久 work 驱动履约；收款成功不等于已可连接 |
| 升级收款/免费接受 | 金融或免费接受证据、升级预算、订单/订阅 SQL 转换 | 提交后凭据同步，失败不得重复接受现金或生成新权益 |
| 普通履约 | 订单完成、Subscription/Terms/Slot/Period、永久履约回执、凭据同步意图 | Provider 网络与 Node 收敛在提交后 |
| 钱包退款 | 来源预算、退款回执、退款 journal/postings 与钱包投影 | 不改变权益、订单或任何履约 work |
| 生命周期/重置 | 状态/Terms 相关边界、旧周期关闭/新周期、原操作回执及同步意图 | 不能异步补建周期后才保证一致 |
| 用量接收 | 完整冻结归属、接收证据、原周期预留、恢复索引 | Redis 只是唤醒；未提交不得返回持久 ACK |
| 用量结算 | 明细、原周期累计、预留释放、批次终态及相应投影 | 不重新读取当前费率重算历史 |
| Provider 操作 | 先提交持久意图；网络返回后另事务验证并提交结果 | unknown 沿原操作 query，不盲目换键 |
| Node 授权 | 有界准备；外部元数据查询后重验身份/Terms/Period/版本并提交签名证据 | 元数据 I/O 不持 SQL 锁；失败不延期旧租约 |

### 7.3 锁序与当前读

- 每个公开事务先检查当前持久安装准入；身份和安装信息不能只读一次后永久缓存。
- 账户相关流程沿现有 account-first 规则；订阅锁含 User、Slot、排序订阅及历史。
- 金融操作在记账前锁定本次所需资金账户的完整并集，沿现有稳定顺序，不能记完一部分才发现需逆序获取另一账户。
- Node 授权的目标锁沿现有账户/Subject/回执之后的位置；不能为了“Network 模块优先”改成节点先锁。
- Terms 变化遵守当前边界契约，不反向获取 batch/grant 锁来制造新的循环。
- MySQL RR 下用于裁决、重放和最终校验的 current locking read 不能被通用 Repository 隐式替换成普通快照读。
- 事务重试仅限没有外部副作用的 SQL 阶段；支付/Provider 网络不能随 SQL deadlock 自动重发。

不在 Kernel 定义一个凭空推导的全局“万能锁序”。实施时按现有真实路径维护锁依赖图、连接身份和参与者前置条件；修改锁图须做针对性并发 CI。

### 7.4 减少模块循环的目标

当前购买/资金/履约有真实协作，不能把它假画成已经无环。目标是：

```text
Purchase/Payment Coordinator
    -> Billing 资金验证与接受参与者
    -> Subscription SQL 履约参与者
    -> 各领域持久回执/同步意图
```

协调者属于明确业务用例，不放入 Kernel。Billing 提供经过原事务校验的接受证据，Subscription 消费证据而非回调一个可再次开启事务的支付入口。证据必须绑定事务、安装、账户、订单和购买 hash，不能仅传 `paid=true`，并明确区分：

- `FreeAcceptanceProof`：免费或折抵后净额为零的购买，绑定原永久免费 checkout 记录；没有虚构 allocation、支付 receipt 或 journal。
- `PaidAllocationProof`：绑定真实 allocation 及其资金证据；纯钱包引用 capture journal，不要求外部 receipt，渠道/混合支付包含对应真实收款及资金分配。

两种路径继续共享原 `order.fulfill/<orderId>` 履约身份；升级还须带原冻结报价与预算证明，不能因免费就跳过来源校验。

该调整只有在复用现有 `applyLocked()` 并通过一致性检查后才落地；第一阶段保持现有调用链，不为了依赖图整洁改写交易语义。

## 8. 保持当前产品政策

抽象层不得默默改变以下政策：

| 场景 | 当前设计应保持的语义 |
| --- | --- |
| 套餐变更 | 已发布版本和已购买条款保持不可变；新报价与销售状态分开 |
| 有效订阅 | 当前一个持久 Slot；暂停保留占位，不借新建订阅绕过限制 |
| 续费/换套餐 | 按冻结购买规则产生后继 Terms；不因新 Terms 无条件赠送新周期 |
| 暂停/恢复 | 不默认延长有效期；恢复仍检查封禁、到期、归属及版本 |
| 到期/撤销 | 不把已结束实例直接改回 active；撤销访问与保留历史账务并行 |
| 重置 | 旧周期保留，新周期独立；原周期已接收及未决用量不能清除或改挂 |
| 当前支付 | 有界 CNY、无手续费、当前插件支持的 checkout/query；不宣称任意渠道和币种 |
| 钱包/混合付款 | 固定资金来源分配；免费订单没有虚构支付尝试或收款 |
| 钱包退款 | 仅退原用户钱包，部分及全额均 `entitlement_effect=none`；撤销需独立授权操作 |
| 升级折抵 | 真实现金 claim 与非现金 carry 分开；共享退款来源预算，非现金不能变现 |
| Provider | 代理秘密留在独立 Provider；Core 只持非秘密引用、版本和有限交付证明 |
| Node/用量 | 保持现有有界协议/平台范围；原批次身份、Session/Period 和授权高水位不重贴 |

精确规则以 [Subscription](../../../contracts/v2/core-subscription-v1.md)、[Wallet/Refunds](../../../contracts/v2/native-wallet-refunds-v1.md)、[Upgrade Credit](../../../contracts/v2/native-upgrade-credit-v1.md)、[Native C2](../../../contracts/v2/native-c2-runtime-v1.md) 及真实代码为准。

当前发现一处文档冲突：[Payment Settlement](../../../contracts/v2/native-payment-settlement-v1.md) 的 Durable fulfillment work 段仍有全额退款取消履约的旧句子，与当前退款代码、钱包契约及[责任矩阵](core-extension-boundaries.md)相反。本设计采用后者的“退款不改权益或 work”；该旧句需单独校正，不能据此更改现有退款行为。

## 9. 幂等、事件与持久恢复

### 9.1 不另建万能幂等中心

现有订单、支付、退款、订阅操作和用量批次各有不同的业务身份与永久证据。Kernel 只统一描述和错误分类，不重建一套缓存 claim 表取代它们。

- request/execution ID 用于追踪，不自动等于业务键。
- 同业务键、同规范输入按原回执返回；同键异输入明确冲突。
- 重放仍检查调用者当前权限与资源归属；已撤销权限不能因命中过去响应绕过授权。
- 退款等原本跨来源或跨 actor 仍要求唯一的键，不得被统一接口缩窄作用域。
- 超时、503、连接中断不证明未提交；调用方沿原键查询，不换键重发。
- 发布接口时明示幂等作用域、永久/保留期限、hash 内容、响应重放和损坏证据处理。

### 9.2 统一工作规范，不强制统一物理表

保留 Billing work、免费 checkout work、Subscription/credential outbox 和 Usage outbox 的领域责任。Billing work 可能在订阅创建前存在，不能强行复用要求 subscription 外键的表。

可共用的只是执行规范：有界扫描、原操作身份、租约/fencing、重试预算、非秘密错误、完成证明与指标。完成证明由领域提供；队列消费成功或 HTTP 200 不代表业务完成。

提交顺序：

```text
业务 SQL + 持久意图/回执 -> COMMIT
                         -> 尝试发送唤醒
                         -> worker 读取持久记录
                         -> 幂等执行/验证结果
                         -> 提交完成证明
```

通知、邮件、缓存刷新允许重复投递并需去重；资金记账与用量结算通过事务和业务唯一约束避免重复生效。不宣称跨网络 exactly-once。

处理中的工作项崩溃后由原记录恢复。隔离/损坏记录保留证据，不以“重试次数用完”自动删除、释放资金或退还用量预留。

## 10. 适配层设计

### 10.1 入站

HTTP、Internal API、CLI、队列与定时任务只做各自的认证/解析/输出，并调用同一公开业务能力。安全前置条件属于边界的一部分，不能把 Controller 中已存在的鉴权删除后直接暴露 Service。

当前正式服务入口保持 `/txapi/internal/native/v1/{domain}/operations/{operation}`，使用已编译 allow-list。此处允许固定 operation 分发，不等于 Kernel 内允许按字符串调用任意方法。

应用用例内仍检查当前账户、资源归属、安装和业务状态；管理员身份、管理员路径、显式服务 permission、Node/Machine 凭据各自独立。服务 mTLS 不代替最终 actor。

来源：[Native Internal API](../../../contracts/v2/native-internal-api-v1.md)。

### 10.2 出站

| 适配点 | 保留的业务契约 | 适配器处理 |
| --- | --- | --- |
| SQL | 指定读写一致性、事务参与、唯一性、金额/版本表示 | 当前数据库访问，不让业务依赖任意 Query Builder |
| Payment | 冻结 dispatch、协议事实、原身份 query/verify | 当前支付插件接口、渠道签名与协议 ACK |
| Credential Provider | 发行/查询/撤销、元数据和非秘密回执 | 有界 mTLS 请求、严格 codec、原 operation 恢复 |
| 通知 | 通知意图、收件对象及非秘密模板数据 | 邮件/消息提供方，失败不回滚已提交资金 |
| Node transport | 固定节点身份、授权版本、有限租约和回执语义 | REST/WSS 协议；不得因传输变化扩展授权 |

无法满足某项能力时返回明确 unavailable/unsupported，不通过旧 API、临时 UUID、当前商户配置或内存状态降级。

### 10.3 支付插件生命周期

适配器抽象不能删除当前永久金融 pin：有历史 dispatch 的包禁止破坏性升级/卸载。停用阻止新 checkout，但原 dispatch 的有限验证和 query 恢复仍遵守冻结版本和配置。

不新增旧 `PaymentInterface` adapter，也不把随包支付渠道搬回 Core 的渠道 switch。现有 PHP 插件仍是可信进程内代码，接口和依赖规则不是技术沙箱。

来源：[当前支付插件契约](../../../contracts/v2/native-payment-provider-v1.md)。

## 11. 数据、读取与缓存

- 保留现有 `tx_*` 原生表与规范证据；接口抽取不等于数据库改名或数据搬迁。
- 不为每个模块创建一张状态表；运行时能力、是否已安装等尽量由真实运行时派生。
- 写入经过模块用例或登记参与者；后台报表可用受控只读投影，不借查询服务更新“修复”数据。
- 跨域查询返回限定 DTO，不返回可继续加载其他关系的 Eloquent 对象。
- 读 API 不隐式创建钱账户、不执行 reset、不刷新凭据；必要修复是显式受权命令。
- 新模块公开 JSON 默认用规范十进制字符串表达金额、bytes、bigint 数据库 ID 和版本；安装 UUID、业务键等保留各自格式，时间使用契约规定的 UTC 秒，不引入 float。现有 wire 必须严格保留各自 Current Schema 的类型，例如签名 Node DTO 中明确规定的正整数 `user_id` 仍为整数；不能以“统一 DTO”为由改坏签名和真实消费者。若要变更 wire，须另作生产者/消费者同批协议变更。
- 展示缓存可以按版本失效；支付裁决、权益授予、准入、撤销、高水位和退款预算不能只靠缓存。
- 权益展示允许携带观察时间；Node 签名授权必须在提交时重验事实。不能将上一次展示 DTO 直接签名为新授权。
- 当前 `consumed_bytes` 已含持久预留；新 DTO 若拆分已结算/预留，必须同次锁定读取且只计一次。Node 的访问授权和 Usage Session 继续绑定同一签名 payload，不能由两个各自“最新”的查询结果拼接。
- 后续若采用读副本，只能用于明确允许陈旧的数据；权限、结算及事务重放保持主库/当前读要求。

## 12. 装配、版本与进程生命周期

### 12.1 装配点

使用现有 Laravel ServiceProvider 体系显式绑定接口和实现。实例选型来自受控配置/当前 Registry，不来自请求传入的类名、路径或 URL。

建议新增一个小的 `CoreCapabilitiesServiceProvider` 负责本轮真实新增接口的绑定；它不是通用模块加载器。不需要新服务发现系统、DSL 或模块容器。

### 12.2 生命周期

| 对象 | 生命周期 |
| --- | --- |
| 不可变 codec/纯规则 | 可共享，禁止保存 actor、PDO 或可变请求状态 |
| actor/context、授权判断、事务参与上下文 | 每请求或每工作项重新创建，结束即释放 |
| 安装 admission/epoch | 逐事务/工作项按当前规则验证，不能永久缓存成功 |
| 插件已加载代码 | 受包版本、mutation fence 和 worker 重启约束 |
| Provider/HTTP 客户端 | 可复用连接设施，但不能混用身份、接收者或配置快照 |

Octane、Workerman 与队列 worker 都需显式处理以上作用域，不能只验证传统短请求 PHP。

### 12.3 版本

PHP 模块接口随 Core 版本协调变化；开发阶段同步修改全部真实消费者，不为旧开发分支长期并行维护接口版本。对外 wire schema、支付包和 Provider 协议继续各自显式标记版本及验证范围。

必选模块不健康时拒绝相关 readiness/业务；可选通知插件失败只使通知能力降级。SQL 或安装准入失败不得因为“插件隔离”而返回健康。

## 13. 权限、秘密与多租户

### 13.1 权限不由接口名称决定

一般用户/管理员调用顺序为：认证真实来源 -> 解析闭集输入 -> 当前操作授权 -> 事务内检查归属/状态 -> 执行业务 -> 脱敏输出与审计。

`InvocationContext` 记录认证结果的引用，不是可以由客户端自填 `role=admin` 的授权票据。上下文不能跨请求/工作项复用；敏感写入按当前存储状态重新验证。

Worker 通过限定系统任务身份和原持久意图执行，不把任意管理员 bearer 长期存入任务。用户请求的管理员工作在受理时鉴权并保存来源；执行仍检查安装、目标状态和任务规定的授权约束，不能靠“来自队列”自动放行。

支付通知使用独立的 `VerifiedPaymentIngress` 来源：由冻结渠道/商户/dispatch 的协议验证建立，而不是用户或管理员 bearer。记录真实收款与允许用户新购买是不同授权路径；账户封禁、订单取消或渠道停用后的已验证迟到收款仍按原安装准入和金融契约留存，不能用于履约的金额进入明确负债。不得给所有端口统一套“用户被封禁即丢弃回调”的 middleware。重复回调同样重验原来源及证据，不依赖用户会话。

### 13.2 秘密分类

代理凭据属于独立 Credential Provider；支付恢复所需的加密商户快照按支付契约保存；Core 会话/服务密钥和订阅链接验证材料各用自己的边界。这三类不能因为统一 `SecretProvider` 就混用。

公开 DTO、事件、审计和诊断不得包含 bearer、代理秘密、完整支付配置或订阅链接原文。正常认证/一次性发行响应是明确授权的专用例外，不成为通用 DTO 字段。

### 13.3 多租户是单独项目

如果未来一个安装服务多个独立运营商，先设计 tenant 身份、跨 tenant 管理政策、表唯一约束、资金/渠道账号归属、缓存/队列/对象存储命名空间、配额与隔离测试，再接入 Kernel 上下文。

当前不添加默认 `tenant_id=1`、客户端 tenant header 或没有查询约束的空 TenantContext。迁移到多租户不是增加一个接口参数即可完成，也不把每个终端用户当作运营商租户。

## 14. 可观测性与故障行为

建议以现有审计和领域回执提供：执行 ID、操作名、actor 类型/引用、安装、目标、原业务键引用、版本、结果、是否重放、非秘密错误、耗时。日志不复制完整业务 payload。

| 故障 | 要求 |
| --- | --- |
| SQL 不可用或准入失效 | 不接受新的业务成功/持久 ACK |
| Redis 丢消息 | 业务意图仍在 SQL；有界扫描恢复 |
| 支付/Provider 超时 | unknown；原业务键 query，不伪造失败或另起副作用 |
| 已提交后响应丢失 | 原键回执重放；先检查当前调用权限 |
| Provider 签发晚到但权益已撤销 | 保留事实，进入原有补偿撤销，不重新激活 |
| 插件禁用 | 新执行拒绝，历史金融恢复按冻结协议受限进行 |
| worker 崩溃/过期 claim | 原 work/批次恢复；旧 fencing 不能提交新结果 |
| 原周期批次迟到 | 按冻结周期结算或明确隔离，不挂当前周期 |
| 凭据/安装 epoch 改变 | 旧工作重验并拒绝不匹配，不自动重贴新身份 |
| 有界对账扫描截断 | 报 incomplete，不宣称账平，不后台自动修账 |

建议指标包括各领域 pending/unknown/quarantined 数量和最老年龄、恢复重试、授权到期/拒绝、原周期预留以及接口拒绝原因。不设未经容量测试的 QPS 或“毫秒级”承诺。

## 15. 目录组织与命名

这是渐进目标，不要求一次建立所有目录：

```text
api/app/
  Core/
    Kernel/                  # minimal framework-neutral contracts and values
    Http/                    # existing transport infrastructure, not pure Kernel
  Domains/
    Identity/
    Subscription/
      Contracts/             # public use cases and their DTOs
      Services/              # existing authoritative application services
      Internal/              # only if a transaction participant needs extraction
    Billing/
      Contracts/
      Internal/
    UsageV2/
    Network/
    CredentialProvider/
    Installation/
    InternalApi/             # current service ingress, not a second domain core
    Content/
    Support/
  Providers/                 # composition root and scoped bindings
  Http/Controllers/          # existing direct HTTP ingress
  Jobs/                      # work-item adapters; business recovery stays in domains
  Services/Plugin/           # actual plugin runtime
  Services/Module/           # inventory and controlled lifecycle delegation
  Models/                    # keep current canonical persistence models initially
```

不为“架构干净”进行全仓移动或保留双份转发类。现有 PHP namespace、数据库模型与业务能力的名称不必同时改变。第一次接入某接口时再创建相应文件，并列出实际调用者。

## 16. 分批实施

本设计不是重新启动 C1-C5，也不把原路退款、全部 Node 协议或通用沙箱变成此次抽象化的验收前置条件。

### 16.1 起点与阶段总览

起点不是一个空框架：当前 native 已有订阅、付款、账本、钱包退款、Provider 和用量主链。K0-K5 主要提升边界清晰度、调用一致性、可扩展性和可验证性，不能把已有业务重新包装成各阶段“首次新增”。

阶段状态按累计结果描述；每阶段都应保持基线已支持的业务。某项能力已经满足目标时复用现有实现和适用证据，不为凑阶段新增转发层或重复测试。

| 阶段 | 主要交付 | 完成后的项目状态 | 相对前一阶段增加的能力 |
| --- | --- | --- | --- |
| K0 边界冻结 | 当前能力/消费者/数据 owner/事务清单，接口试点范围及冲突处理 | 有可执行改造基线的 native 单体 | 团队能准确判断改哪里、谁负责、如何验收；运行时能力不变 |
| K1 最小读侧试点 | 最小 Kernel、共同权益契约、真实消费者、装配与读侧检查 | 已有一条端到端接口化业务路径 | 指定权益消费者通过稳定接口复用同一规则，测试可替换实现而不复制业务 |
| K2 外部能力收口 | 当前 Payment/Provider 扩展点及其装配/生命周期/故障契约 | 核心业务与当前外部协议边界明确 | 在已支持语义内接入/更换协议实现，不修改订阅/账本规则；停用恢复仍安全 |
| K3 事务协作收口 | 写用例与 SQL-only 参与者、锁依赖图、金融/权益一致性检查 | 具备明确跨域提交责任的模块化交易内核 | 多模块能安全组合完成付款、升级与履约，不靠独立提交或通用事件补一致性 |
| K4 入站统一 | 现有 API/Internal API/CLI/Worker 对公开用例的委托清单 | 当前支持范围内可被多入口一致调用的业务 Core | 新的合法消费者可以复用公开能力，不重新编写价格、权限、状态和恢复规则 |
| K5 架构验收 | 边界检查、契约与业务回归、精确版本证据和文档 | 在明确范围内完成架构改造的开发候选 | 后续改动有自动回归/依赖约束，支持按模块持续开发和评审 |
| R1 生产交付门禁 | 固定制品、实际部署信任/商户、新安装/更新/恢复及运维验收 | 经批准后可发布的限定生产版本 | 对已经验证的部署、渠道、协议和容量承担明确运行承诺 |

R1 是后续生产交付阶段，不是本轮文档任务或 K0-K5 重构的隐含授权。多租户、全部支付渠道、原路退款、HA 和通用插件沙箱不随阶段自动获得。

### 16.2 K0：边界冻结

**要做什么：**

- 固定实施基线，核对代码、Current 契约和实际消费者，不沿用旧 C1 判断。
- 对本轮涉及的每个入口登记：身份、输入输出、领域 owner、事务 owner、幂等、数据写入和恢复路径。
- 冻结 Kernel 最小范围、业务模块公开面和第一条权益查询试点；保留明确不做清单。
- 处理已知当前文档冲突，特别是钱包退款不修改权益或任何 work 的政策。

**完成后的项目状态：** 仍是原 native 实现，没有新增运行时能力，但团队已经有一致的改造范围、责任表和验收依据。不能仅凭两份草案已经写出就宣称 K0 冻结完成。

**新增能力：** 新任务能够定位到明确模块和事务边界；评审可以判断一个改动是在做适配、修改业务，还是越权写其他域。

**完成门槛：** 本轮消费者和责任清单齐备、关键冲突已处理或被明确阻断、范围获得评审确认。K1 实施前不得残留影响该试点的权限/数据权威歧义。

**仍不具备：** 运行中的新 Kernel、业务端口重组、多租户或新的支付/Node 能力。

### 16.3 K1：最小 Kernel 与共同权益试点

**要做什么：**

- 只建立试点实际需要的上下文、错误分类和接口；不提前统一 Repository、Clock 或事件总线。
- 在 Subscription 内建立 `EntitlementQueries` 与明确 DTO，优先由现有 resolver 直接实现。
- 先接入一个真实查询消费者，再覆盖 K0 登记的这项能力的当前消费者；用户/管理员 façade 与内部 locked 读取保持区分。
- 显式装配实现，增加读侧契约检查和 Kernel 禁止反向依赖的静态约束。

**完成后的项目状态：** Core 有一条完整的“现有入口 -> 公开能力 -> 权威实现”路径；不是只有接口文件、示例 Controller 或未使用的基础库。

**新增能力：** 调用者依赖稳定权益契约，可在测试中注入受控实现；实现调整不要求消费者重新理解订阅、Terms、周期和预留算法。此能力是依赖隔离，不是任意切换业务数据库。

**完成门槛：** 登记的消费者全部接入或保留经过明确审阅的内部参与边界；跨用户、封禁、到期、预留量、版本和秘密输出检查通过。Node 最终重验及原签名字段不改变。不能以一个测试 mock 通过代表真实消费链通过。

**仍不具备：** 所有写路径接口化、统一全部模块或新增业务功能。端口抽取不宣称全仓已经框架无关。

### 16.4 K2：外部能力与扩展边界收口

**要做什么：**

- 复用当前支付接口、Registry 和 Provider transport，核查业务是否仍引用具体渠道类或协议字段。
- 对真实存在的越界依赖做窄适配；已有正确扩展点只补不足的契约/检查，不再包装一遍。
- 明确能力支持、配置、启停、健康与授权的区别，以及 timeout/unknown、原操作 query 和缺失能力处理。
- 验证停用后的历史金融恢复、永久包 pin、Provider 秘密直交付与已加载代码版本约束。

**完成后的项目状态：** 已支持业务规则与当前渠道/协议实现之间形成清晰边界。扩展改动的正常落点是对应 adapter，而不是订阅或账本算法。

**新增能力：** 在现有契约支持的语义内，可以增加合规支付或 Provider 协议实现；切换配置/启停的条件明确。这里的“更换”是受控装配与发布，不是对已有金融 dispatch 的包任意热替换。

**完成门槛：** 真实当前提供方通过契约与负向检查；声明支持但未实现的能力拒绝；禁用、unknown、冻结配置、签名和秘密边界不退化。新增真实提供方另有自己的联调范围。

**仍不具备：** 所有支付商即插即用、任意多币种/手续费、原路退款、通用安全沙箱。接口可以扩展不代表这些产品能力已经实现。

### 16.5 K3：写用例与事务协作收口

**要做什么：**

- 明确建单、普通收款、升级接受、履约、退款、重置和用量结算的唯一提交负责人。
- 保留公开自有事务入口；按需要提取现有 `applyLocked()` 等 SQL-only 参与契约，不用外层事务包装公开服务。
- 记录账户/订阅/历史/资金锁并集与 current-read 依赖，保留免费接受和真实付款的不同证明。
- 统一跨模块错误和恢复责任的表达，不强制合并领域 work/outbox/幂等表。

**完成后的项目状态：** 核心写业务可以跨模块协作，但不会因模块化而产生“一边已扣钱、另一边权益状态不明确”的新增提交缺口；既有异步履约仍用持久回执恢复。

**新增能力：** 新业务协调者能够复用明确的事务参与能力；团队可以安全修改一侧实现，并用原子边界和并发测试验证影响。不是向插件开放任意跨域事务或账本写入。

**完成门槛：** 相关数据库 CI 验证多支付竞争、免费/钱包/混合付款、升级来源预算、退款并发、重置与原周期用量，以及提交前后崩溃恢复。网络调用不能进入业务 SQL 事务；结果未知不得盲目重发副作用。

**仍不具备：** 分布式事务、外部网络 exactly-once、自动精准回退历史权益。退款继续仅到钱包且不修改权益/work。

### 16.6 K4：所有当前受支持入口统一委托

**要做什么：**

- 按 K0 清单逐项接入直接 API、Internal API、CLI、Scheduler 与 Worker；共享公开用例而不是共享 HTTP Controller。
- 将价格、生命周期和资金规则从发现的入口重复逻辑中移回领域 owner；没有重复逻辑的入口只核对，不制造重构。
- 同步现有实际消费者的 DTO、operation allow-list、错误、授权和原键恢复方式。
- 禁止用通用模块调用接口暴露 SQL-only 参与者、任意类名或其他内部能力。

**完成后的项目状态：** 当前已支持的业务，无论通过哪种合法入口调用，都由同一权威用例决定结果。入口差异只保留在身份、传输、输入输出和访问策略上。

**新增能力：** 新的合法 API 客户端、运营工具或未来前端可以在既有操作范围内复用 Core；增加入口不需要重写订单/订阅逻辑。

**完成门槛：** 清单内入口逐项可追踪到用例和权限策略；真实消费者契约通过；同业务经不同入口不出现状态/金额/归属语义差异。服务身份、最终 actor、管理员路径与权限仍分别校验。

**仍不具备：** 完整管理 API、新管理/用户前端、管理员浏览器通道或任何未实现 operation。发现 API 缺口时单列功能任务，不用“入口统一”暗示已经补齐。

### 16.7 K5：架构验收与开发版本收尾

**要做什么：**

- 将已明确的依赖方向、DTO、插件边界和内部参与接口限制加入实际可运行的检查。
- 集中运行本轮影响的契约、业务和长驻进程 CI；汇总修复，复测受影响范围。
- 完成当前实现说明、接口使用规则、精确源码/制品及已知限制记录。
- 通过正常 PR 审阅和合并流程交付，不以缺席/跳过的检查代替通过。

**完成后的项目状态：** 在明确范围内形成“小 Kernel + 业务模块 + 能力适配”的开发候选；相关 CI 通过后可申请合入，实际合入后才成为主线能力。

**新增能力：** 后续模块开发有自动依赖/契约检查和可重复回归，团队能够独立修改明确边界内的实现并评估影响。

**完成门槛：** K1-K4 的实际消费者、权威实现和失败路径有对应证据；没有未解决的关键一致性/权限回归；保留范围外和生产专项限制。代码完成、精确提交已验证、已合并三种状态分别记录。

**仍不具备：** 生产发布资格。生产 PKI、真实支付商户、固定版本新安装/更新/恢复等未验证事项不能被“架构改造通过”覆盖。

### 16.8 R1：生产交付门禁

R1 不增加通用抽象，目标是对已经选定且完成验证的功能组合形成真实交付。需要单独确认部署目标、外部身份/商户和允许执行的验收范围。

**要做什么：**

- 固定 Core、Provider、Node、Gateway（使用时）和 Deploy 的版本组合与制品来源。
- 核验实际 TLS/PKI、受信代理、服务身份、秘密配置和支持支付渠道的真实商户接入。
- 经独立 Deploy 验证新安装、正常更新、必要备份恢复和失败停止条件；不由 Core 再造安装器。
- 在明确协议/平台和业务范围内完成账户 -> 购买 -> 收款 -> 履约 -> Node 使用 -> 用量 -> 续费/重置/撤销 -> 钱包退款主链验收，并确认告警、恢复流程和运行负责人。
- 记录容量验证边界、操作手册、发布/恢复限制；正式发布由获授权维护者执行。

**完成后的项目状态：** 对选定版本组合和支持范围形成可发布版本；只有审批及实际发布完成后才称“已发布”。不笼统宣称所有部署形态生产可用。

**新增能力：** 新环境可按固定流程交付，常规更新与已验证恢复可执行，运行故障有可追踪证据和处置路径。

**完成门槛：** 外部信任和商户、固定制品以及部署/恢复的实际证据齐备；阻断项处理完毕；发布审批完成。R1 环境准备可以提前，但最终验收必须针对最终交付版本。

**仍不包含：** 多运营方共享库隔离、HA/Cluster、全部内核/协议/平台、原路退款、无限容量、通用插件沙箱；这些只有另立功能和验收任务才可纳入。

### 16.9 批次关系、当前进度与汇报口径

推荐按三个连贯开发批次推进，避免六次重复全量验收：

- 批次 A：K0 + K1，证明最小边界和真实权益消费路径。
- 批次 B：K2 + K3，收口外围协议与核心交易一致性；明确文件/契约边界后可并行开发，统一集成。
- 批次 C：K4 + K5，核对入口与真实消费者，集中架构/业务验收和主线交付。

默认先完成前置契约再推进依赖阶段；不需要改动的已满足目标项直接登记证据。没有估算依据时不承诺固定工期，也不按类/接口数量统计完成率。

2026-10-17：批次 A 已形成 K0 责任与消费者清单、K1 权益查询接口及当前消费者接线的候选实现，尚未完成 CI 验收、评审或合并。实际子集见 [权益查询契约](../../../contracts/v2/core-entitlement-queries-v1.md)；责任与后续边界见 [能力清单](core-capability-map.md)。K2-K5 仍待实施。现有支付接口、事务保护和 native 功能属于原业务基线，不计为本轮新增实现。

每阶段汇报至少列出：

| 维度 | 汇报要求 |
| --- | --- |
| 实现 | 实际改动的用例、消费者和接口；不能只报新增多少文件 |
| 项目状态 | 基线已保留的业务、该阶段新获得的工程能力，以及仍不可用的范围 |
| 验证 | 精确提交、相关检查的通过/失败/跳过与未执行项 |
| 集成 | 未提交、候选分支、PR、已合并分别说明 |
| 发布 | 未发布/已发布、固定版本组合及部署验收范围 |
| 剩余问题 | 阻断项、可延期项、下一阶段前置条件和业务政策未决项 |

重型测试、数据库、真实进程/流量、race 与完整构建仍默认 CI；本地仅做必要静态检查。纯设计文档不触发业务环境测试。

## 17. 验收与架构约束

### 17.1 静态门禁

建议新增专门边界检查，先记录当前例外再禁止增加：

1. `Core/Kernel` 禁止引用 `Illuminate`、`Domains`、Models、具体 SDK。
2. 公开 DTO 禁止泄露 Request、Eloquent、连接或 callable。
3. 业务规则不引用具体支付插件；付款只通过当前验证后的 Registry/接口。
4. 入站适配器不得直接写资金、Terms 或用量结算表。
5. 内部参与者不得从 HTTP operation Registry 或插件通用动作暴露。
6. 只有装配层可以选择实现；禁止 `app($requestClass)` 一类动态注入。
7. 参与者代码不得执行网络；公开自有事务入口不得被外层事务包装。
8. 新增依赖不得恢复已退役源码或 legacy/shadow fallback。

这些是拟新增检查，不是当前已生效的 CI。简单文本扫描只能发现一部分违例，事务和动态调用仍须代码审阅及行为测试。

### 17.2 行为验收矩阵

| 范围 | 必测行为 | CI 所有者 |
| --- | --- | --- |
| 权益查询 | 禁用账户、跨用户、到期边界、暂停、原周期预留、失效上下文 | API / MySQL |
| 建单/履约 | 同键重复/冲突、响应丢失、只履约一次、损坏快照拒绝 | MySQL |
| 金融接受 | 多支付赢家、迟到真实收款、钱包/渠道组合、完整资金账户锁并集 | MySQL |
| 升级/退款 | 现金预算竞争、非现金不可退款、退款不修改任何权益/work | MySQL |
| 周期/用量 | Terms 边界、并发 reset、旧周期迟到、预留/结算原子、隔离保留额度 | MySQL / Native C2 |
| Provider/Node | unknown 原键查询、撤销后晚到、元数据变更重验、材料直交付和有限租约 | Native C2 / Node |
| Payment 插件 | 停用不新建、历史查询、包 pin、旧 worker 已加载版本拒绝 | API / MySQL |
| Internal API | 当前服务/actor/permission、closed input、allow-list、原键恢复与脱敏 | API / Gateway |
| Octane/Worker | actor 不串请求，安装/epoch 不陈旧，工作项不复用事务上下文 | API / Core 镜像 |

实际工作流沿[开发基线](../../development/native-development-baseline.md)的所有权执行；不另起重复全矩阵。本地只做必要静态检查，数据库、真实进程/流量及完整构建默认 CI。

### 17.3 完成定义

“接口文件已建立”不算完成。每个接口必须有实际消费者、权威实现、权限/事务/幂等契约、失败行为和验证记录；替换或删除旧调用时有可核对清单。

本设计的成功标准是：同一业务规则不被入口复制，具体协议变化不修改核心业务，交易一致性与恢复能力不退化，团队能明确找到每项事实和状态转换的 owner。

## 18. 风险与待确认选择

| 项目 | 本设计默认 | 何时需要新决策 |
| --- | --- | --- |
| SaaS 租户形态 | 单运营方安装，多个终端用户 | 要做多个独立运营商共用平台时单独立项 |
| 模块发布 | Core 内第一方必选模块同版本发布 | 真实出现独立团队发布/SLA需求时，不凭“可插拔”提前拆服务 |
| 业务规则变更 | 维持当前续费、暂停、退款和折抵政策 | 产品明确要求延期生效、暂停补时或原路退款时 |
| 持久化替换 | 当前数据库和规范表继续使用 | 有实际新存储需求且语义等价经过验证时 |
| 历史数据 | 不承担旧开发版本兼容；未知/真实数据仍保护 | 明确指定真实数据迁移范围后独立设计 |
| 插件信任 | 当前 PHP 插件可信，Credential Provider 独立 | 引入不可信插件时必须单独设计进程/权限隔离 |
| 文档漂移 | 先校正已识别的退款旧条款，不改正确业务 | K0核对其他当前契约与实际代码后逐项处理 |

以上默认用于让设计可以继续，不代表用户已批准多租户、业务政策变更或生产上线。

## 19. 后续新功能开发与维护

普通业务在所属模块内持续开发；新渠道在当前协议适配器内实现；只有确有共享基础需求才调整 Kernel。小内核不是冻结业务，模块化也不要求每个功能新增接口、插件或微服务。

具体落点、功能说明模板、六步开发流程、到期提醒/支付渠道/流量加购示例以及维护检查见 [Core 新功能开发与维护](../../development/core-feature-development.md)。该指南区分现有 native 能力和待实施的端口/检查；不要求等到 K5 才开发新业务，也不允许绕过现有权威另建实现。

K0-K5 的交付包含可供后续开发使用的模块地图、真实示例、外部接入指南、事务示例、入口规范和实际检查，不只统计抽象类数量。
