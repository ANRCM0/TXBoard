# Native Node snapshots and applied-state retry v1 (Candidate)

This slice closes ordinary native-v1 control gaps after authority-denial stop. Core remains the configuration/authorization source; Node distinguishes desired snapshots from successfully applied kernel state. Xboard/local transports keep their current wire contracts. Isolated Usage-v2 retains frozen-producer fail-stop and immutable receipt rules.

Native Client keeps a complete, independently cloned config/user body alongside its ETag, bound to the configured endpoint/credential/Node identity. Existing GetConfig/GetUsers APIs preserve nil=304 and allocated-empty=valid empty users. New complete-snapshot methods reuse the corresponding body on304; a304 without any matching body resets the tag and retries exactly once, then fails explicitly. Only a complete valid200 matching protocol and Node ID commits body+ETag. Config200 followed by users failure or normalization/application failure does not lose that config: the next poll can re-deliver its complete body. ForNode has independent cache. Reset/reconnect can force a complete current read. Mutable maps/slices returned to consumers cannot alias transport cache.

Poll results carry a Service-local desired-event generation captured at poll start. Accepted WS config/users/deltas advance that generation; a normal response from an earlier generation is discarded and schedules reconciliation after discarding. A completed authority denial remains terminal even if a newer WS event occurred. This prevents local in-flight REST from overwriting a later push, not a globally monotonic Core revision or atomic two-endpoint snapshot. Periodic polling remains active when WS is connected and eventually reconciles missed events. No error falls back to an invented empty user list.

Desired state and applied state are separate. Desired config/users may be retained for retry; deduplication against the kernel uses only confirmed applied hashes and actual running state. Start/Reload/user mutation success updates applied state. A failed attempt never marks a requested config/users hash applied; receiving the same push or later complete304 snapshot must retry. Combined config/users updates cannot be declared applied if only one part succeeded. A failed partially mutating user operation cannot leave stale/revoked users serving while claiming rollback: stop an uncertain kernel and retain the authoritative desired state for a full retry. No default network outage shutdown is introduced by this apply-error policy.

Unsupported/invalid config keeps a visible failure, preserves valid confirmed bookkeeping and remains retryable. If Reload plus fallback Start fails, same desired configuration remains pending and can recover after the fault disappears. Empty desired users stop the kernel and count as applied empty users, with config available for later legitimate user addition. Removing/rebinding a UUID must not silently swallow kernel errors. Certificate renewal must remain pending until its relevant kernel application succeeds. Runtime health must not present a desired hash as an applied confirmation.

The state applies on the Service main goroutine; metrics reads use the existing synchronization boundary. No uncontrolled background mutation of kernel or user/limiter indexes. Terminal denial dominates pending applies and queued data. Recovery of previous terminal traffic remains before listener admission.

Acceptance: config200/users503 then config304/users200 yields the actual new listener; cached snapshots are cloned and identity-scoped; missing-cache304 retries once; kernel first Start/Reload/user mutation failure then identical304/push retries and succeeds; real occupied-port failure recovers after the port is freed; delayed old poll after newer WS remove/UUID rotation does not revive old credentials; dropped push and disconnect/reconnect reconcile; empty users shut down; actual VLESS/VMess TCP connection/authentication verifies current config/users. Existing race/vet/build and authority-denial/reporting/Usage-v2 regressions remain required. Custom outbound/rule reload correctness, Xray strong revocation, finite offline leases, durable Core application revisions and complete real Machine/Workerman integration remain subsequent mandatory P0 work, not proven by these local hashes.
