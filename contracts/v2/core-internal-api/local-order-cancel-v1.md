# Isolated User order cancellation v1

Status: Current isolated slice. Synthetic local/testing only, independently default off.

`user.order.cancel` version `1` takes the closed input `{trade_no}` with ASCII `[A-Za-z0-9_-]` length 1..128. `CORE_INTERNAL_ORDER_CANCEL_ENABLED` must be strictly true together with global Internal, local/testing and the isolated-copy gate. Dedicated user-gateway identity and the current native User Bearer are required. Core preserves current ban, non-Admin User operation policy and native owner-scoped order lookup; a caller/service ID never grants ownership. Success is HTTP200 `{data:{ok:true},request_id,meta:{current_only:true,slice:internal-order-cancel/1}}`, private/no-store. Missing or foreign order is native404; OrderService false is native409 `ORDER_CONFLICT`.

The dispatcher calls the existing BillingController cancellation and OrderService without copying rules or introducing an outer transaction. The native transaction locks a PENDING order, calls `order.cancel.before`, changes status, refunds the creation-time prepaid wallet amount, restores one reserved coupon slot and writes optional isolated legacy capture in the same transaction. The native `order.cancel.after` runs after commit. Duplicate cancellation returns409 and does not refund or restore twice. Other states are refused by the native service. Capture remains default off; enabling it requires its existing strict isolated context.

No cancellation idempotency claim or compensation is introduced. Native service can return false after a post-commit hook failure; audit failure, expired deadline, response loss or transport failure may also hide an already committed cancellation. A 409 is therefore not proof of rollback. Gateway and SDK perform one attempt and never automatically replay, refund, restore or repair. Consumers must inspect current order state before deciding what to do next. Native trusted hooks retain their existing scope and timing.

Gateway fixed `userOrderCancel` uses the local mTLS client. Independent `GATEWAY_INTERNAL_ORDER_CANCEL_ENABLED=true` requires a strictly local/testing environment and configured Internal User TLS. A legacy Bearer JSON route `POST /gateway/v1/orders/:tradeNo/cancel` accepts exactly `{}`; its cancellation handler is absent by default (the existing parent order-write ban may return405) and requires that independent gate at boot and transport. SDK `orders.cancel(tradeNo)` uses POST, validates the closed `{ok:true}` receipt and never retries, including 409/503/network loss. The route has no Native fallback, does not inherit order-create enablement, and carries no SC-v2 claim. Payment method reads remain credentialed; no payment mutation, frontend or installer change occurs.

Request/response bounds, TLS1.3/mTLS, service nonce and current authorization reuse the existing isolated Internal boundary. Technical nonce, token use-time and audit writes are expected. No secret, callback, wallet balance or generic order model is returned. Production authorization fencing, PKI/SC-v2 and release rollout remain separate gates.

Caught native cancellation Exceptions now emit only the fixed `ORDER_CANCELLATION_FAILED` diagnostic without exception object, arguments, SQL or previous chain. Existing capture exception retains its fixed diagnostic. The catch remains Exception-only with the same false return and hook timing; non-Exception Errors and logs independently emitted by trusted hooks are outside this diagnostic change.

Core generates its own response request ID; it does not echo the input request_id. Cancellation consumer verifies the closed server UUID matches `X-Request-Id`, without equating it to the caller-generated input ID.
