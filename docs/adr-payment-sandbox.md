# ADR：支付沙箱测试与对账设计（GW-306）

- 状态：**已提出，待评审**
- 日期：2026-10-11
- 责任：TX（Laravel 主仓库实现沙箱 stub / 对账命令）+ GW（Gateway 侧结构性断言与文档）
- 关联任务：[task-backlog.md](./task-backlog.md) GW-306（本文档）；依赖 GW-305（[checkout/cancel 状态机 ADR](./adr-checkout-cancel.md)）；下游 GW-308（SDK 重试策略）、GW-309（[订单写灰度](./order-write-rollout.md)）、GW-310（快速购买，吸收重复回调）

## 1. 背景与问题

- GW-306 的验收原话有两句，都是硬门槛：**"支付回调不走 Gateway"** 与 **"交易对账一致，无法验证时不得放量"**。第二句直接挂在 GW-309 的 G0 禁入条件上（`GATEWAY_ORDER_WRITE_ENABLED` 不得为 true）。
- 现状与既有决策：
  - 支付回调是**支付提供商 → TXBoard Laravel 的独立入口**（`/api/v1/*` 之外的既有回调路由），验签、幂等、状态迁移、金额校验全部由 Laravel 完成（[implementation-plan.md](./implementation-plan.md)："绝不将支付回调经 Gateway 当作主题 API 转发"；[architecture.md](./architecture.md)：入口反代仅 `/gateway/v1/*`，回调/节点/管理/订阅保持原目的地）。
  - Gateway 上游白名单（`services/upstream.ts` 的 `allowlistedPaths`）中没有任何回调/支付写端点；`config/policies.ts` 的支付写禁令是结构性的（405、零上游调用）。本文档**不改任何路由**，只加断言。
  - GW-305 已定义订单业务态状态机 `0 pending → 1 paid / 2 cancelled`、事务内条件 UPDATE 守卫；checkout 终态 `paid` 映射上游状态 `1`。支付回调是**另一条通往 `status=1` 的路径**（用户走外部支付渠道，不经过 Gateway 的 checkout），必须与 checkout 共用同一状态机的守卫。
  - GW-302 的 `idempotency_keys` 表与三态状态机（in_progress/succeeded/failed_retryable、24h TTL、15min 陈旧 CAS）是本 ADR 回调幂等的复用对象，**不新建第二套幂等机制**。
- 核心风险（[implementation-plan.md](./implementation-plan.md) 支付沙箱验收清单 + airbuddy 借鉴项）：
  1. **重复回调**（同一 trade_no 多次支付通知，含支付商重发/网络重试）→ 重复开通/重复交付/重复扣款；
  2. **异步先后**（支付成功但回调晚到；用户关闭浏览器、前端超时）→ 用户看到的状态与真实资金状态不一致；
  3. **超时恢复**（支付超时后订单已自动取消，回调才到）→ 钱付了、单取消了，无处安放；
  4. **支付失败**（回调 fail）→ 订单与余额状态错乱；
  5. **金额校验**（回调金额与订单应付不一致，含币种/单位换算错误、篡改尝试）→ 少付多开通或拒付误判；
  6. **对账缺失** → 漏单/重复扣款无人发现，灰度放量无据。

## 2. 决策（Decision）

1. **沙箱环境**：按 [staging 手册](../staging/README.md) 的隔离栈（Laravel + MySQL + Redis，独立卷，不触碰生产）；支付提供商接入**本地沙箱 stub**（TX 责任），能按剧本注入：成功、失败、重复回调、延迟回调、错误签名、金额篡改。**验收必须在隔离沙箱完成，禁止使用真实支付商生产密钥或真实资金**。
2. **回调路径结构性隔离**（本文档的核心断言，见 §5）：支付回调不经过 Gateway——不是"配置上不转"，而是路由表/白名单里**根本没有这个端点**。验收以负向测试证明：任何以回调形态发往 Gateway 的请求都被拒且零上游调用。
3. **回调处理在 Laravel 内完成**，顺序固定：验签（provider 密钥，失败即拒并告警）→ 持有/存在性校验（trade_no 归属）→ **金额校验**（回调金额 == 订单应付，分为单位整数）→ 幂等（回调专用 operation）→ 状态机迁移（条件 UPDATE 守卫）→ 交付/开通（事务后异步，不进幂等表）→ 回执给支付商。任一步失败不产生资金副作用。
4. **幂等机制复用 GW-302**：回调进同一张 `idempotency_keys` 表，operation 枚举扩展 `payment.notify`（GW-302 §3.1 预留扩展位，不为回调新建机制）。回调幂等键 = `SHA-256(provider ‖ trade_no ‖ provider_event_id ‖ amount)`（Laravel 权威派生，服务端从已验签的回调载荷派生，不接受任何客户端/provider 可猜测键）。**重复回调在幂等层返回首次同一结果快照，根本到不了状态迁移。**
5. **超时/漏单恢复走"主动查单"（pull）**：Laravel 定时命令对"已创建超 N 分钟仍 `status=0` 且有活跃支付会话"的订单向支付商发起**状态查询**；查得 `paid` 则把结果喂给**同一个回调处理器**（复用 §3 全链路，幂等层保证与真实回调到达时行为一致）。不新建"补偿直写"旁路——旁路必然与回调路径漂移。
6. **对账三层、分级处置**（§4）：本地订单状态 vs 本地交易流水（`payment_transactions`）vs 支付商日结/结算 API。差异分三级：**可自动补偿**（状态滞后：我方 `0`/对方 `paid` → 查单确认后走回调处理器幂等迁移）、**自动告警**（金额不一致、重复扣款、签名失败 → P0 告警 + 冻结放量）、**人工队列**（无法判定归属的差异）。**对账差异不为零时 GW-309 G0 禁入条件不解除。**

## 3. 支付回调处理设计（Laravel，本文档定义契约，实现属 TX）

### 3.1 处理管线（固定顺序）

```
provider 回调 → ① 验签（HMAC/RSA per provider，密钥在 Laravel .env，Gateway 无关）
             → ② trade_no 存在性/归属（无此单 → 记告警 + 回 200（防支付商重试风暴），不落幂等）
             → ③ 金额校验（见 3.3）
             → ④ 幂等判定（operation=payment.notify，见 3.2）
             → ⑤ 事务：状态条件 UPDATE（status=0 → 1，受影响行数=1）+ 写流水
             → ⑥ 回 200 给支付商（幂等命中/成功同一响应）
             → ⑦ 事务后异步：订阅开通/权益/通知邮件（去重投递，不进幂等表）
```

- 步骤 ② 的"未知 trade_no"必须回 200 而非 4xx：支付商重试风暴比丢一条未知回调更危险；未知回调进对账人工队列。
- 步骤 ⑤ 与 GW-305 §3.1 的 checkout 守卫同构：`UPDATE orders SET status=1 WHERE trade_no=? AND status=0`，行数守卫 + `idempotency_keys` 唯一约束双保险。**已 `1/2/3` 的订单重放回调在幂等层（④）即返回首次快照，到不了 UPDATE。**

### 3.2 回调幂等矩阵（复用 GW-302 三态机）

| 场景 | 结果 |
| --- | --- |
| 同一 trade_no 同一 provider_event_id 首次回调 | 落库 in_progress → succeeded，订单 `0→1`，写一条流水 |
| 同一回调重复送达（重发/网络重试） | 幂等行 `succeeded` → 返回**首次同一结果快照**（200，同一 tradeNo），订单与流水零变化，**零二次开通** |
| 并发重复回调（10 并发同一事件） | `idempotency_keys` 唯一约束串行化：恰 1 单迁移，其余 9 返回首次快照或 `IDEMPOTENCY_IN_PROGRESS`（对回调即返回 200 + 同一 ack） |
| 同一 trade_no 不同 provider_event_id（支付商补单/部分支付） | 键含 event_id 与 amount：不同事件是不同键；金额不同触发 §3.3 校验，**不足额拒绝** |
| 回调先到、checkout 后到（或反之） | 订单状态机裁决：谁先把 `status=0` 迁到 `1` 谁生效，另一方被状态守卫/幂等拒绝；**只结算一次** |
| 回调在陈旧 in_progress 上重放 | 按 GW-302 §5.1 CAS 接管语义（15min 租约），接管后仍只迁移一次 |
| TTL（24h）过期后回调重放 | 幂等行视为不存在；但订单已在 `1` → 状态条件 UPDATE 行数为 0 → 走"已支付"幂等快照路径返回同一结果，**不产生第二笔流水** |

### 3.3 金额校验

- 比较对象：**回调 payload 中的金额（换算到分，整数）== 订单快照重算的应付金额（含优惠后，分）**。严格相等，不做容差（容差就是篡改面）。
- 不一致时：**拒绝迁移**（订单保持原态），记录 `amount_mismatch` 告警（含 trade_no，不含密钥/签名原文），进入对账 P0 人工队列。回调返回 200 但状态不动（避免支付商重试放大差异面，等人工/自动补偿）。
- 币种/单位错误（如支付商以元上报）属于典型注入用例：stub 提供"金额错一位"剧本，期望拒绝 + 告警 + 零迁移。
- 客户端/回调中携带的任何"应付金额"字段都不被信任；金额权威 = 订单快照重算（与 GW-305 §3.1 同一条规则）。

## 4. 支付沙箱测试矩阵（验收用例）

环境前置（每个用例都必须满足，缺一即用例无效）：隔离沙箱（独立 MySQL/Redis 卷）+ 支付商 stub（剧本可注入）+ **Gateway 侧仅只读路由可用、`GATEWAY_ORDER_WRITE_ENABLED` 未设**（证明回调不依赖 Gateway）+ 真实签名密钥的**沙箱对**。

| # | 用例 | 注入 / 动作 | 期望（硬判据） |
| --- | --- | --- | --- |
| PS-1 | **重复回调** | 同一 trade_no 同一 provider_event_id 回调 ×5，串行 | 恰 1 次 `0→1`；恰 1 条流水；开通/权益/邮件事件恰 1 次（异步去重）；5 次回调均回 200 同一 ack；余额（余额支付场景）扣减恰 1 次 |
| PS-2 | **并发重复回调** | 同一回调 10 并发同时到达 | 唯一约束串行化：恰 1 单迁移，其余返回首次快照/`IDEMPOTENCY_IN_PROGRESS`；流水恰 1 条；无死锁/超时放大 |
| PS-3 | **异步先后（回调晚到）** | 用户完成支付，回调延迟 30s/5min 到达；期间用户关闭浏览器/前端超时 | 期间订单保持 `0`（**不假装修已支付**）；只读订单接口（经 Gateway）如实返回 `0`；回调到达后 `0→1`；用户刷新后看到 `1` |
| PS-4 | **主动查单恢复（超时恢复-A）** | 支付成功但回调永久丢失（stub 丢弃）；Laravel 定时查单命令触发 | 查单得 `paid` → 喂回调处理器 → `0→1`，结果与 PS-1 等价（幂等行同一语义）；若此后真实回调才到 → 幂等返回首次结果，不重复迁移 |
| PS-5 | **超时后支付（超时恢复-B）** | 订单超过支付时限被自动取消（`0→2`）后，支付商才发起支付并发回调 | 回调到达时订单已在 `2`：状态条件 UPDATE 行数为 0 → **不迁移、不自动开通**；记 `paid_after_cancel` 告警 + P0 对账人工队列（退款流程属 TX 单独评审，见 §8 未决 2） |
| PS-6 | **支付失败** | 回调 `status=failed`（含余额不足、用户取消） | 订单保持 `0`（可再次 checkout，幂等行 `failed_retryable` 语义由 GW-302 覆盖）；**零资金副作用**；失败流水（若写）标记失败且不影响余额 |
| PS-7 | **错误签名** | 篡改签名/错误密钥的回调 | 验签失败即拒（4xx/按 provider 约定），**零状态变化、零幂等写入**；告警记录（不含密钥） |
| PS-8 | **金额篡改** | 回调金额 < 应付（少 1 分）/错一位（元 vs 分）/多付 | 一律**拒绝迁移** + `amount_mismatch` 告警；订单保持原态；进对账人工队列；多付情形同样不自动开通（不擅自入账） |
| PS-9 | **未知 trade_no** | 对不存在的 trade_no 发回调（伪造/跨站重放） | 回 200（防重试风暴）+ 告警 + 人工队列；**零迁移**；不泄露订单存在性差异 |
| PS-10 | **重复点击/重复下单后回调** | 同一用户快速重复下单（幂等键相同，GW-302 保证只一单）后支付其一 | 恰一单；回调作用于唯一 trade_no；重复成单率零 |
| PS-11 | **与 Gateway 的边界** | 任何回调形态请求发往 `/gateway/v1/*`（含猜测路径 `/gateway/v1/payment/notify`） | 405/404（按策略），**零上游调用**；见 §5 断言 |
| PS-12 | **对账演练** | 注入 4 类差异（见 §4.1）跑日终对账 | 差异检出率 100%，处置按分级正确，告警触发，报告产出 |

### 4.1 对账机制

**三层对账**（日终，Laravel 定时命令 + 落盘报告 + 指标，**不经 Gateway、不碰生产卷**）：

```
L1 本地订单态   ：orders.status（0/1/2/3） × trade_no
L2 本地流水     ：payment_transactions（trade_no, provider, amount, status, provider_event_id）
L3 支付商结算   ：支付商日结文件 / 结算 API（trade_no, amount, status）——沙箱为 stub 提供
```

**差异分级与处置：**

| 级别 | 差异形态 | 处置 | 告警 |
| --- | --- | --- | --- |
| **A 可自动补偿** | L1 `0` / L3 `paid`（漏回调，PS-4 同源） | 触发查单确认 → 走**同一回调处理器**（幂等迁移）→ 复对账 | info + 补偿计数指标 |
| **A 可自动补偿** | L2 与 L3 金额/状态字段滞后（同一事件不同快照时间） | 同左，以 L3 为准经处理器校正 | info |
| **B 自动告警（P0）** | L1/L2 不一致且 L3 无对应（疑似重复成单/状态漂移） | **冻结放量**：对账差异计数器 > 0 即阻断 GW-309 灰度晋级（与 G0 禁入条件联动） | P0 告警 + 人工队列 |
| **B 自动告警（P0）** | 金额不一致（任何两层间） | 不自动入账，人工队列 | P0 |
| **B 自动告警（P0）** | 签名失败 / 未知 trade_no 回调 | 人工队列（可能攻击面） | P0 |
| **C 人工队列** | PS-5（超时后支付）、归属无法判定 | 运营/财务人工处理；**不得自动开通、不得静默丢弃** | warn |

**自动补偿的铁律**：补偿永远走**同一个回调处理器**（§3.1 管线），不写"补偿直写 UPDATE"旁路。幂等层保证补偿与迟到回调相遇时行为一致（首次成功者生效，后者返回同一快照）。这条规则是对账正确性的全部支点——旁路补偿必然与回调路径漂移，历史上所有"双写"事故都源于此。

**产出物**：每份对账报告（按日，`reconcile/YYYY-MM-DD.json`，沙箱路径）含：对账范围、三层记录数、差异清单（分级）、处置结果、补偿计数；指标 `payment_reconcile_mismatch_total{level}` 暴露给现有告警栈（复用 GW-205 观测体系，TX 侧落 MySQL + 出指标端点约定，评审确认载体）。

## 5. Gateway 侧断言（本文档新增的验收内容，无代码改动）

1. **路由负例（结构性）**：`config/policies.ts` 的路由表与 `services/upstream.ts` 的 `allowlistedPaths` 中**不存在**任何回调/支付写端点——以现有 `policies.test.ts` 同款断言扩展：对 `/gateway/v1/payment/notify`、`/gateway/v1/payments/notify`、`/gateway/v1/orders/:tradeNo/pay` 等猜测路径，全部 404/405 且**零上游调用**（mock upstream 断言调用次数 = 0）。
2. **支付写禁令不变**：`POST /gateway/v1/orders` 在 `disabledWrite` 姿态下 405 零上游调用（现有测试，PS-11 复验）。
3. **只读如实反映状态**：PS-3 期间经 Gateway 的 `GET /orders` 必须如实返回 `status=0`——适配层（`adapters/txboard-v1.ts` 的 `toPublicOrderStatus`）不做任何"乐观推断"，不把 pending 渲染成 paid（负例：mock 上游 `status=0`，Gateway 响应不得含"已支付"语义）。
4. **对账不经 Gateway**：对账命令、查单调用全部发生在 Laravel 侧（TX 责任）；Gateway 侧断言"没有任何配置指向支付商端点"（代码审查 + 文档）。
5. 若未来确需经 Gateway 暴露支付状态查询，只可能是**只读透传**（`GET /gateway/v1/orders/:tradeNo` 的 status 字段，现状已覆盖），且必须经独立 ADR——**不在本 ADR 范围**。

## 6. 被否决的备选方案

| 备选 | 否决理由 |
| --- | --- |
| 回调经 Gateway 转发（主题统一入口） | 违反"支付回调不走 Gateway"验收原话与 architecture.md 路由隔离；验签密钥与 provider 特化逻辑会渗入 BFF |
| 回调独立幂等表/Redis 去重 | 同 GW-302/305：Redis 可丢状态，资金路径必须 MySQL 持久化；双机制必然漂移 |
| 补偿直写 UPDATE（旁路恢复漏单） | 与回调路径两套状态迁移逻辑，必然漂移；历史上重复开通事故的主因 |
| 对账差异由 Gateway 聚合 | Gateway 不碰数据库（实现计划不可变约束）；对账属 Laravel 资金域职责 |
| 金额容差比较（≤1 分） | 容差即篡改面；分单位整数比较无歧义 |
| 用生产支付商密钥"真实测一笔" | 真实资金 + 生产数据，沙箱 stub 已能覆盖全部剧本 |

## 7. 验收标准（输入 GW-308/309/310）

1. PS-1～PS-12 全部通过，且每项的硬判据（恰一次迁移/恰一条流水/恰一次开通/零重复扣款）有沙箱执行证据（CI 或手工记录，含 stub 剧本与对账报告）。
2. 重复/并发回调零重复交付：`payment_transactions` 行数 == 幂等行成功数 == 订单 `0→1` 次数。
3. 超时后支付（PS-5）100% 不自动开通且进人工队列。
4. 金额篡改（PS-8）100% 拒绝 + 告警，零误开通、零静默入账。
5. 日终对账演练（PS-12）差异检出率 100%，自动补偿走回调处理器（对账日志可见幂等命中），P0 差异触发告警并联动灰度冻结。
6. Gateway 负例（§5.1/5.2）进 `policies.test.ts` 快照，CI 绿。
7. **放量门禁（原话落地）**：对账差异不为零或沙箱用例未全绿时，`GATEWAY_ORDER_WRITE_ENABLED` 不得为 true（GW-309 G0 条件之一）。

## 8. 风险与回滚

- **风险**：支付商回调乱序/重发超出预期（同一事件多 event_id）→ 幂等键含 event_id+amount，天然按事件区分；对账 C 级人工队列兜底。
- **风险**：主动查单放大支付商限流 → 查单定时任务限速（批次+间隔，评审定参数），只查"有活跃会话且超时"的订单。
- **风险**：自动补偿误触发（L3 脏数据）→ 补偿仍走回调处理器全管线（验签/金额校验不过即拒），不会造成资金错误。
- **回滚**：本文档纯设计；Laravel 侧实现（operation 枚举项、回调处理器、对账命令）可独立停用/回滚（关命令、摘路由），`idempotency_keys` 行由 GC 自然过期；Gateway 侧零改动，回滚为空操作。
