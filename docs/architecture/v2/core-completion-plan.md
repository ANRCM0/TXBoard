# Core 完整基础能力交付计划

> 更新：2026-10-15 · 实施路线：C1—C5 · 本文是后续开发决策，不是完成声明。
>
> 用户最新要求：先完成 Core 的完整开发；现有站点数据兼容不作为新版本的必经路径。前端、安装器和 Node 的独立工作不能替代 Core 业务开发。C1 已完成实现与本地批次验收，最终 CI、审阅、合并与发布分别确认；其余阶段仍为待开发，实际结果以代码、PR 和[当前进度](current-progress.md)为准。

## 完成范围与现有边界

本计划中的“Core 完成”是：全新安装能够通过正式 API 管理账户和权限、发布套餐、购买支付、开通及续费订阅、发行和撤销访问资格、持久接收及结算用量、取消和退款，并能依照明确版本交付。Core 是这些业务的唯一持久权威，Gateway 和 Provider 只执行各自契约。

当前可复用的 Laravel 身份、权限、订单、支付商适配、节点管理、原生流量去重及授权代码继续保留。`Subscription`、`SubscriptionTerms`、`PlanRevision`、`PlanOffer`、`UsagePeriod` 和资金影子记录已存在，但影子实现不等于生产权威。不得通过删除 local/testing 限制、改一项环境变量或增加一个只读投影宣称完成切换。

当前约束仍由[Core 边界](core-boundaries.md)、[Core 数据模型](core-domain-model.md)、[Current 契约](../../../contracts/v2/README.md)及行为约束决定。下述生产模式、服务名和接口责任是后续实施决策；正式启用前必须同时更新对应 Current 契约和真实调用者。

不纳入本轮：管理前端、用户前端、优惠券等新增促销、礼品卡、复杂佣金与提现、HA/Cluster、高级网络拓扑、Agent/MCP、通用插件隔离改造。已有相关入口在原有模式中的行为不因此扩大；native 模式下尚未接入新权威的入口明确拒绝，不能偷偷写旧字段。

## 数据与权威模式决策

### 优先完成全新安装

1. 交付一个可持久验证的安装权威记录，包含安装标识、模式、schema/领域版本、authority epoch、初始化业务键和状态；以数据库事务创建，重复请求只返回同一结果。
2. 优先版本化扩展现有 `tx_authority_writer_fence` 及其证据结构，复用 admission/epoch 原理。现有 fence 只覆盖特定旧写入者和隔离演练，不能直接当作生产全局开关。确需新增字段或结构时，迁移同时定义旧证据保留与版本校验，不再建立另一套平行 fence。
3. 新安装显式选择 `native`；初始化须证明不存在订单、订阅、权益、用量、资金等业务数据及未决任务。允许保留的管理员引导和配置元数据须逐项列举。不能仅检查用户数量，也不能在已有影子数据上直接盖章。
4. 已有部署保持明确的 `legacy` 模式。启动配置只能声明进程期望模式，不能更改数据库权威；Web、Worker、定时任务必须校验同一持久记录和 epoch。native 模式记录缺失、损坏或不兼容时拒绝就绪，不自动降级 legacy。
5. 第一批业务写入后禁止修改初始化模式。迁移旧数据、回退旧版本和切换权威都不作为常规配置编辑，必须使用独立且可恢复的迁移流程。

### 共用规范模型，避免重复账本和订阅表

- 继续使用目标中的 Subscription、Terms、Transition、Slot、UsagePeriod、AccessSubject、PlanRevision/Offer 等规范表；为真实业务补充必要字段、唯一约束、版本和有效来源标识。已有影子证据保持原语义，不批量改名为 active。
- 提取可复用的纯值转换、日历策略、锁定顺序、幂等与时间线算法；生产服务拥有事务，影子服务继续留在隔离边界。不要从生产代码调用本来只供隔离演练的顶层事务方法。
- 复用现有 Order 标识、状态及支付入口。仅为缺失的购买明细、支付尝试、资金账户与流水等真实概念建规范记录，不为每个渠道、业务动作或阶段各建一套平行表。
- native 模式下 User 负责账户与身份；订阅权益来自 Subscription/Terms，用量来自 UsagePeriod/结算记录，余额来自资金流水。旧字段如仍被适配器使用，只能是由新权威生成的派生视图，禁止双向写入。

## C1：冻结已购买权益并接入真实履约

**交付目标：** 套餐或系统设置在下单后发生变化，不改变用户已经购买的权益。

- 新用户订单和管理员分配订单在同一事务内写入版本标记和不可变 `OrderPurchaseTerms`；保存原订单、账户、套餐、周期、类型、最终应付额、币种、配额、权限组、限速、设备数、重置策略、日历策略及开通事件。
- 履约读取集中验证快照哈希、闭合字段结构、镜像列及订单归属；损坏或必需快照缺失时拒绝履约。仅明确旧订单且无快照时走原履约路径。
- 支付校验、钱包抵扣、订单锁、重复回调和开通队列继续复用现有实现。新快照直接驱动真实开通，不只供展示或审计。
- 续费到期计算使用购买时冻结的UTC时区与月份溢出策略，开通事件类型随购买冻结并在履约事务内执行。持续重置策略在C1只作为购买证据记录，实际调度仍依原生Plan/system；C2统一权益读取与周期写入时再接管。

**完成条件：** 新订单、管理员分配和重试履约均消费同一冻结证据，套餐编辑不改变结果；相关订单与资金回归集中通过。该阶段不代表 Subscription 已接管 User，也不代表完整资金账本已交付。

## C2：原生 Subscription 生命周期及完整读写权威

**交付目标：** native 新安装的实际开通、授权和用量都由同一套订阅模型决定。

| 组成 | 必须交付的生产行为 |
| --- | --- |
| 套餐发布 | 生产 `PlanPublicationService` 发布不可变 Revision/Offer，独立维护销售/续费可用性；修改套餐只发布后继版本，已有购买保持冻结条款。 |
| 订阅履约 | `SubscriptionFulfillmentService` 从 C1 购买证据创建或续接真实 Subscription、Terms、Transition 和 UsagePeriod；订单完成与开通结果同事务、同业务键，仅开通一次。 |
| 生命周期 | `SubscriptionLifecycleService` 处理新购、同套餐续费、换套餐、到期、暂停/恢复、撤销及明确的重置；冻结并复用已有日历与折抵规则，不以续费隐式赠送新流量。 |
| 单订阅容量 | 复用持久 Slot 作为锁记录，所有开通/变更遵守一致锁序；活动订阅容量限制和并发操作不能绕过。 |
| 条款关联 | 支持真实 `plan_revision_id` 及聚合归属约束；Terms/Transition 追加且不可改写，已接受用量不能越过新条款边界。 |
| 权益读取 | `SubscriptionEntitlementResolver` 成为账户订阅 API、Node REST/WS、节点增量授权及订阅分发的共同权威，统一到期、封禁、配额、组和设备/速度限制。 |
| 用量与周期 | 将现有持久接收、去重、批次及计量实现接入 Subscription/Terms/Period 归属；结算和周期累计同事务。重置保留旧周期，离线旧批次按原周期结算，不能挂到当前订阅。 |
| 凭据归属 | 真实 AccessSubject 绑定订阅与 Provider 的非秘密引用；本阶段接入可用的 Provider 接口，缺失能力时明确不可发行凭据，禁止 Core 新建代理 UUID 兜底。 |
| 所有写入口 | 订单、管理员创建/编辑/分配、注册试用、定时到期/重置、套餐传播、批量操作、Worker 及现有扩展统一 admission/epoch。未实现的可选动作在 native 模式拒绝。 |

**完成条件：** 新安装经现有 API 完成注册/管理员分配或购买 → 实际订阅 → Node 授权 → 用量结算 → 续费/重置/撤销；数据库中的 User 权益旧字段不能影响 native 结果。生命周期、读者与写者必须作为一个相关批次集成，不能只上线半条链。

**前置依赖：** C1 购买输入、规范模型和持久 authority bootstrap。Provider 生产秘密管理在 C4 收口，但 C2 的真实授权链必须接入明确契约，不能以影子 Subject 代替可用访问资格。

## C3：支付尝试、资金账本与退款闭环

**交付目标：** 订单履约、实际收款和用户资金在重试及失败后仍可解释且只发生一次。

- 在已有订单和支付商适配上补齐不可变 OrderItem、报价归属和 `PaymentAttempt`；渠道请求、金额、币种、交易号及状态转换由 Core 校验，回调仍使用独立身份和验签链。
- 每个币种使用规范 MoneyAccount、Journal 和 Posting；至少两笔分录且借贷平衡。钱包可用额、保留额及余额投影与流水同事务更新；现有余额字段不再成为 native 扣款权威。
- 钱包抵扣、零元/全余额订单、充值、取消释放及升级折抵有明确分录和业务键，不生成虚构渠道收款，也不重复记收入。
- 多支付尝试同时成功时，订单锁裁决一次履约；额外实际收款保留为待退款或待核对负债，不丢弃第二笔事实。
- 支持完整及必要的部分退款、累计退款上限、引用原收款/账本及失败重试；退款后权益如何结束、保留或调整必须形成明确规则，不依赖当前套餐值猜测。
- 订单/支付/资金/开通请求与持久 outbox 同事务；队列失败可恢复，不要求 Webhook 请求同步完成所有副作用。
- 基础收入与账户对账接口能解释余额和未决资金。复杂佣金、提现及营销不纳入该批。

**完成条件：** 新购、续费、换套餐、钱包/渠道组合、取消和退款共用真实生产账本；重复通知与已取消订单迟到收款有确定结果。集中验证相关资金竞态，不扩展为所有协议矩阵。

## C4：正式 Internal API 与 Provider 生命周期

**交付目标：** 外部前端或 Gateway 能通过正式接口使用已经完成的 Core，凭据秘密由 Provider 持有。

- 将已有隔离 Internal API 切片提升为受生产配置和权限约束的注册入口，继续使用 `/txapi/*`，不复制领域规则。业务 service 同时服务现有直接调用和正式 Internal API。
- 交付账户会话、管理员身份/RBAC、套餐、订阅、购买订单、支付状态/取消/退款、Node/Machine、用量和必要设置接口；每次调用由 Core 重验身份、资源归属、权限及前置状态。
- 固定 User/Admin/Node/服务/支付回调各自身份，交付服务凭据、调用幂等、审计和请求追踪；安全通道不能仅凭 mTLS 或 operation 名信任管理员身份。
- Provider 交付生产注册、能力声明、发行、轮换、撤销、吊销回执和状态协调；Core 只保存非秘密引用和版本，秘密不得进入任意 DTO/日志/事件。
- 订阅链接支持归属、独立撤销、有效权益过滤和 Provider 渲染。Provider 失联或重试不形成第二套 Core 订阅事实。
- 生产证书/密钥、信任根与轮换流程接入正式安全通道；与现有有限签名 Node 授权衔接，明确支持的内核/协议范围。
- 更新机器可读能力、消费者契约与必要运维接口。Gateway 管理员接入只在对应正式权限及通道实现完成后开启。

**完成条件：** 一个真实 API 消费者完成账户/管理及购买订阅主要操作，真实 Provider/Node 消费结果；测试夹具和仅 local 路由不计作生产交付。前端页面不构成本阶段依赖。

## C5：初始化、升级与发布收口

**交付目标：** 发布一套能够安装、运行、正常更新和恢复的 Core 基础版本。

- 将 C2 引入的持久安装权威、schema 版本、worker epoch、Provider 能力和密钥前置条件纳入 readiness 及安装握手；新安装只选择已完整支持的 native 能力组合。
- Worker、队列和定时任务使用同一版本与模式；不允许旧 Worker 在新权威下继续执行旧字段写入。升级明确停写、排空及启动顺序，失败保持可诊断状态。
- 形成版本化迁移清单及可恢复数据库 schema 变更；应用回滚不跨越已不可逆的业务权威版本。复用独立 Deploy 的安装/更新/备份能力，不在 Core 再实现安装器。
- 集中执行新安装 → 管理配置 → 支付开通 → 真实 Node 使用 → 续费/重置/撤销 → 退款，以及一次正常更新和必要恢复；复用仍适用的现有证据，不按每个协议重复整套验收。
- 输出正式 Current 契约、环境配置、API 说明、版本组合、发布记录及运维手册。主题分支经 PR、必要审阅和 CI 后合并，镜像由主仓现有发布流程生成。

**完成条件：** C1—C4 实际生产路径交付、批次验收和修复结束、PR 合并与固定镜像就绪，新安装操作可重复。未做的扩展或生产环境专项明确列出，不用“全量完成”掩盖限制。

已有站点的自动回填、秘密导入和全站权威切换是 **C5-M 可选迁移子项目**。保留已有影子、对账、fence 和恢复成果，后续需要时完成来源对账、队列排空、秘密迁移及最终切换；它不阻塞全新安装的 C2—C5 交付，也不要求本轮长期维护两套新业务实现。

## 批次与协作执行

1. 先收尾 C1；随后以 C2 的“开通—读取—授权—用量”为连续主批次，不再回到单纯影子审计循环。
2. C3 可在 C2 契约固定后并行实现资金模块，统一集成订单履约；C4 的 API/Provider 可以按文件边界并行，但不能先开放未完成的领域能力。
3. 按[批次开发流程](../../development/development-workflow.md)连续实现一个或多个相关阶段，统一测试与修复；开发中仅做必要检查。权限、资金与数据库约束保留针对性验证。
4. 多团队遵守[PR 协作方案](../../development/multi-team-development.md)：公共 schema、契约、authority 和锁序由集成负责人协调，领域团队提交相关 PR，禁止自行切换全局权威。
5. 每批报告已实现的业务、实际剩余事项和是否已发布；文档、模型、影子结果、测试夹具、合并和正式发布分别记录。
