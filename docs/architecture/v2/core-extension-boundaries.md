# Core 内核业务与插件扩展边界

> ADR-CF-002 · 决策日期：2026-10-16 · 状态：架构方向已确认，相关实现按 C3/C4 交付。
>
> 本文细化 [Core First 边界](core-boundaries.md)：支付渠道属于插件，支付事实与资金一致性属于 Core。它不是插件重构、生命周期保护或 C3/C4 已验收完成的声明。与历史目标文档冲突时，以本文和 [Native 开发基线](../../development/native-development-baseline.md)为准；具体接口仍须由版本化契约和真实消费者共同实现。

## 1. 划分原则

**Core 拥有业务事实、授权与一致性；扩展提供可替换的协议、渠道、策略建议和交付能力。**

- 停用或替换扩展后，余额、订单、已接受用量、资源归属和权益历史仍必须正确解释。这些事实及其状态转换规则归 Core。
- 更换厂商、协议或发送方式，不应改变订单、账本和订阅的含义。这类连接与转换归扩展。
- 某项能力不是每个站点都用，不代表它应该离开 Core。钱包、退款和用量结算即使暂未启用，仍是核心领域规则。
- 插件可以请求 Core 执行业务操作，但必须由 Core 重验调用者、权限、资源归属、业务键及当前状态；不能直接把插件结果当作已付款、已授权或已履约。
- 业务归属、代码目录、包来源、部署进程是不同维度。第一方随包附带的插件仍是插件；独立部署的服务也不自动成为插件。

## 2. 责任矩阵

| 业务面 | Core 内核负责 | 插件或外部能力负责 |
| --- | --- | --- |
| 账户与权限 | 账户、会话、管理员/RBAC、资源归属、封禁、授权和审计 | 外部身份源接入、身份协议转换；最终账户绑定及权限仍由 Core 决定 |
| 套餐与报价 | Plan、不可变 Revision/Offer、最终报价及购买快照、销售和续费规则 | 外部销售渠道；未来可提供营销策略建议，不得改写已接受的报价 |
| 订阅与权益 | Subscription/Terms、开通/续费/换套餐/到期/暂停/撤销、配额和容量规则 | 按有限授权执行特定凭据或交付操作，不自行开通权益 |
| 订单与支付事实 | 订单、支付意图/尝试、收款事实去重、订单付款分配、赢家裁决和持久履约任务 | 具体支付商下单、签名/验签、查询、回调协议和结果标准化 |
| 钱包与账本 | 账户、借贷分录、可用/保留额、充值入账、混合支付、取消释放及资金对账 | 提供真实外部资金结果，不另建权威余额或账本 |
| 退款 | 退款审批/权限、原付款关联、累计上限、负债/账本、幂等和退款后的权益规则 | 在能力支持时执行原渠道退款、验签/查询退款结果；不决定可退额度 |
| 网络资源与授权 | Node/Machine/Group/Route、非秘密 AccessSubject、访问政策和有限授权 | Credential Provider 管理代理凭据与协议材料；Node 执行授权 |
| 用量 | 持久接收、去重、预留、原 Session/周期归属、结算和额度扣减 | Node 采集、持久重报；第三方采集适配不得另定结算周期 |
| 订阅链接与分发 | 链接归属、访问令牌生命周期、撤销、当前权益过滤、有限交付授权 | Credential Provider 按授权渲染，并直接向受权接收方交付代理材料 |
| 通知与集成 | 业务事件、必要的持久投递协调、权限和审计；业务结果不依赖通知成功 | 邮件、短信、Telegram、外部 Webhook、第三方系统适配 |
| 展示 | 服务端身份/权限和正式 API；主题唯一活跃状态 | Theme、插件管理界面和独立前端展示，不形成第二套业务权威 |
| 模块与基础运行 | Module Runtime、库存、权限授予、生命周期委派、基础设置、持久操作和故障恢复 | 插件私有配置/资源及自身运行逻辑；不接管 Core 安装和业务状态 |

优惠券、礼品卡、复杂佣金、提现不在当前 C3/C4 范围。是否开放策略扩展以后另定契约；即使将策略做成插件，最终报价、资金义务和购买证据仍由 Core 校验并持久化，不能因此新建平行财务系统。

## 3. 支付：渠道可插拔，财务不可旁路

### 内核与渠道分工

| 动作 | Core | 支付插件 |
| --- | --- | --- |
| 开始付款 | 校验订单/充值、金额币种、归属和可用渠道，建立永久业务键及 attempt | 按明确渠道契约生成跳转、二维码或外部下单请求 |
| 绑定配置 | 冻结插件身份、包/契约版本、商户账户、付款输入及必要的加密配置 | 解释自身配置，提供稳定商户标识和协议能力 |
| 接收通知或查询 | 路由到原冻结渠道；校验标准结果与 attempt、账户、金额、币种、交易号的绑定 | 按原配置验签/查询，输出标准化渠道事实及协议 ACK |
| 确认收款 | 去重、保存实际收款、记账并裁决订单付款归属 | 不直接修改订单、余额、Subscription 或履约状态 |
| 取消、迟付或多次成功 | 释放预留；保留所有真实收款；将不能用于履约的款项记为明确负债 | 继续验证原交易结果，不把取消误报为资金不存在 |
| 执行退款 | 冻结退款目的地与额度，记录状态/分录，决定权益后果并协调未知结果 | 仅在声明并实现的能力范围内执行和查询原渠道退款 |

```text
用户或管理请求
  -> Core 校验业务与权限，持久化付款/退款意图
  -> Payment Registry 选择明确身份和契约版本的支付插件
  -> 插件执行渠道协议，返回标准化结果
  -> Core 重验冻结绑定，持久化收款/退款事实、账本及后续任务
  -> Core 领域服务履约或调整权益
```

Registry 不能从用户输入加载任意 PHP 类、URL 或商户配置。扩展声明 capability 只说明支持某种操作，不授予管理员权限。只有插件协议验证通过且 Core 业务校验通过，才允许形成相应的资金状态转换；旧式 `notify()` 返回数组本身不等于 native 收款凭证。

外部网络请求不占用业务 SQL 事务。未知结果使用原业务键查询和恢复，不能盲目创建第二笔支付或退款；不承诺外部网络 exactly-once。没有实现查询或原渠道退款的插件必须明确报告不支持。退款到钱包是另一种明确目的地，不能冒充原渠道退款成功。

### 停用、升级和卸载

1. 停用首先阻止新的渠道付款或退款请求，不删除 Core 中的订单、收款、余额、未决义务及审计。
2. 原交易的通知验证、查询和结果确认属于显式恢复/排空能力，不是恢复插件全部权限。允许的操作、冻结版本、保留期限和失败状态必须在契约中写清楚。
3. 存在未决支付、退款或尚需保留的验证依赖时，不能通过破坏性升级、卸载、删除密钥或覆盖配置切断恢复。须阻断操作，或先完成经验证的依赖交接；不能只看 plugin `enabled`。
4. 重放旧通知仍校验原商户和原尝试，不因当前渠道配置改变而接受另一账户的结果。财务证据的保留不依赖插件是否仍在活动清单中。

这些是本轮支付插件重构的交付约束。候选 PluginManager 已加入持久排他保护和历史 dispatch pin，但尚未完成版本化依赖交接，也未经本候选集成 CI 证明。保留当前未决业务的恢复依赖是业务正确性要求，不是为旧开发版本新增兼容层。

## 4. 插件边界不等于安全沙箱

当前 PHP 插件在 Laravel/Octane 宿主内运行，是可信进程内代码。契约要求它不直接写 Core 领域表，不等于已经通过技术手段禁止读取数据库、宿主文件或秘密。包校验、enabled guard、权限检查和故障处理也不能替代进程隔离。通用插件沙箱不属于本轮已交付能力。

Credential Provider 是单独的秘密边界：代理 UUID、私钥及可直接使用的代理配置由 Provider 保管，Core 只保存非秘密引用、版本、承诺和回执。不能因为支付插件在进程内，就把代理秘密搬回 Core。

Core 自身会话、服务身份与支付商户认证配置按各自边界保护；为验证和恢复支付而加密保存必要商户配置，不属于将代理秘密放回 Core。支付秘密不能进入公开 DTO、事件、库存、健康诊断或日志，管理读取也必须受明确权限约束。

## 5. 独立组件不是另一套业务内核

| 组件 | 定位 | 不拥有的权威 |
| --- | --- | --- |
| Gateway | 可选 BFF、固定 API/服务身份客户端和传输适配 | 不直接读写 Core 数据库，不拥有用户权限、订单、余额或订阅密钥 |
| TX-Node | 独立 Agent/Data Plane、代理内核执行、用量采集和重报 | 不自行开通权益、不改写计费归属、不接管控制平面 |
| Credential Provider | 独立代理秘密服务，按契约发行/轮换/撤销/渲染 | 不决定套餐、付款、配额和账户权限 |
| TXBoard-Deploy | 独立宿主安装、更新及恢复编排 | 不另建业务规则，不把安装器做成 Core 插件 |
| TX-F | 独立管理/用户前端，当前开发仍暂缓 | 不另建业务 API 权威；本地工作不获得推送授权 |

这里的 Node Agent 是数据面运行角色，不是已退役的产品 Agent/MCP。支付 Provider 与 Credential Provider 也不是同一契约；不能因名称相似而共享凭据或秘密政策。

## 6. 当前代码映射与 C3/C4 收口

- 现有 [PaymentService](../../../api/app/Services/PaymentService.php) 已通过 PluginManager/hooks 选择支付插件；[Epay](../../../api/plugins-core/Epay/Plugin.php) 和 [AlipayF2f](../../../api/plugins-core/AlipayF2f/Plugin.php) 是内置支付插件。随包发布不使渠道协议变成 Core 领域。
- 本批 C3 候选已将具体 EPay 协议移到 `plugins-core/Epay/NativeAdapter.php`，Core 经 [typed 支付契约](../../../contracts/v2/native-payment-provider-v1.md)和 Registry 调用，不保留平行 Core EPay adapter。当前仅该插件实现 native 契约，不把历史 `PaymentInterface` 输出自动当作已验证收款事实。
- Core 保留共享 attempts、收款事实、钱包、账本、退款约束与履约。充值与购买复用同一渠道契约和收款权威，不分别实现一套支付状态机。
- C4 的直接 API、Internal API、Worker 和 CLI 委托同一 Core 领域服务。跨进程的服务认证不能代替实际调用者授权，也不能给插件开通通用 SQL、Shell 或任意网络执行入口。
- 后续实现需同步更新契约、包/DTO、真实调用者、生命周期保护与针对性测试。当前 [交付计划](core-completion-plan.md) 和[进度](current-progress.md)继续区分候选实现、CI 验证、合并和发布，本文不提升其完成状态。
